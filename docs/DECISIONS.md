# Decisions (append-only)

D1. Android-first, iOS deferred until app self-funds $99/yr. iOS interception = Shortcuts automation (one-sec style), no per-reel count on iOS. Mac never purchased; iOS builds via GitHub Actions macOS runner.
D2. Detection fully on-device (AccessibilityService). Server stores counts only — privacy is a product pitch.
D3. Sync = delta events with client UUID batch_id, server dedup. Rejected: absolute-count POSTs (BrainPal's concurrency bug class).
D4. History kept as daily aggregates forever; raw events pruned 7d. Rejected: 24h wipe (kills streaks/graphs).
D5. Realtime battles = 30s polling + FCM push. Rejected for free phase: WebSockets (RAM per connection kills free instance).
D6. GitHub Actions is primary CI. Ephemeral Jenkins (webhook→Lambda→EC2 start/stop→S3) is a separate learning track, never release-blocking. Rejected: fixed 2h scheduled Jenkins window (breaks per-push feedback; EBS bills while stopped; doesn't cover iOS).
D7. Free tiers: Render/Fly + Neon + Upstash + FCM. First paid upgrade expected ~5-10K DAU.
D8. Monetization: free 3 months, then ₹100/mo Pro. Self-funding at ~2.5-3K DAU @ 2% conversion.
D9. Guilt pack = remote-updatable JSON, categorized/weighted; global-first English now, language packs later. Mix guilt with pride/streak lines to avoid uninstall-from-shame.
D10. Day boundary computed server-side from users.timezone. Client clock never trusted for dates.
D11. Reel-advance detection = time-debounce, forward-only (DOWN). Mechanism: activity-reset quiet-gap — reset the timer on every DOWN, count only the first DOWN after a gap > minAdvanceIntervalMs (Instagram: 200ms). Rejected: fixed refractory — observed fling settle (~640ms) and genuine inter-swipe gaps (~108ms) overlap, so no single fixed window separates them; activity-reset collapses any-length fling burst to 1 and fails toward mild undercount, never the ~8x overcount of raw events. Direction via AccessibilityEvent.scrollDeltaY (API 28+); on min-SDK 26/27 direction is best-effort (rejected raising min SDK for this). CALIBRATED 2026-07-22 on-device @ 200ms: slow 20/20, rapid 19/20 (single undercount = the intended mild-undercount failure mode), mixed 10/10; comments/profile/idle pauses produced zero false counts. Well within the ±2/50 exit bar — Phase 1 detection exit criterion MET. 200ms kept.
D14. Client persists counts in Room (scrollkiller.db), mirroring the server daily_counts shape: table daily_counts(date, platform, count), composite PK (date, platform). Increment is an atomic SQLite UPSERT (INSERT ... ON CONFLICT DO UPDATE SET count = count + 1) — rejected Room @Upsert (it REPLACES the row, can't express count+1). Day boundary is INTERIM device-local date (LocalDate.now(), native on min-SDK 26); server timezone-truth replaces it in Phase 3 (invariant #2 / SCHEMA.md "Day boundary") — marked with a TODO(Phase 3) in CountRepository. TodayCounter (in-memory) removed. Room codegen via KSP.
D15. Instagram reel-advance signal is androidx.viewpager.widget.ViewPager (support-lib v1) — it reports the non-zero scrollDeltaY. The inner RecyclerView fires alongside but always reports deltaY=0 (settle noise), so keying on it alone yields SAME and never counts. containerHints = [ViewPager, ViewPager2, RecyclerView]; RecyclerView retained provisionally (comments list is also a RecyclerView) — calibration (D11) showed comments-open produced zero false counts, so it stays for now; drop it if a future IG build overcounts there.
D12. Multi-platform via PlatformSpec registry from day one (packageName, containerHints, minAdvanceIntervalMs, strategy); only Instagram enabled now, YT/Snapchat/etc. specs added in Phase 2 after view-tree inspection. Emitted advances carry Platform.id matching the daily_counts.platform enum in SCHEMA.md so Room/sync stay platform-agnostic. Coupling: config XML packageNames allowlist must be widened alongside the registry.
D13. Accessibility onboarding = disclosure-first, then deep-link to Settings.ACTION_ACCESSIBILITY_SETTINGS. Android forbids apps from programmatically enabling accessibility services, so deep-linking IS the sanctioned flow; our job is making it guided and honest (invariant #5). App re-checks enabled state on onResume to flip to Home on return.
D17. Surface gating + overlay attach-once (device-found bugs, 2026-07-22). THREE changes. (a) DIAGNOSTICS ARE PERMANENT NOW: the rich node-tree dump (scrolled node's className + viewIdResourceName + full ancestor-id walk; window-state/content root class + resource-id) lives in SurfaceDiagnostics, gated behind BuildConfig.DEBUG (enabled buildConfig=true; AGP 8 defaults it off) so release builds compile it out. We kept deleting and re-writing these each calibration — no longer. Filter `adb logcat -s ScrollKiller`, lines prefixed `DIAG`. (b) SURFACE GATING: counting was gated only on package + scrolled-view class (containerHints), which fire across the whole app, not just Reels; the bubble was gated on PACKAGE ALONE. Added PlatformSpec.surfaceMarkers (viewIdResourceName substrings identifying the doom surface, e.g. clips_viewer_view_pager) + SurfaceMatcher (ancestor walk for scrolled nodes; bounded DFS root scan for window changes). NEW SINGLE SOURCE OF TRUTH: onDoomSurface (foreground is a tracked platform AND on its doom surface) — BOTH the counting gate and bubble visibility read it, so they can't disagree. Updated from scroll ancestry + window-STATE root scans; NOT from the content-changed flood (too frequent to scan per event — content-changed is DEBUG logging only). EVIDENCE-FIRST: surfaceMarkers ships EMPTY; the matcher is a pass-through when empty, so behaviour is unchanged (old package/containerHints gating) until a labeled device surface tour (feed→reels→stories→profile→DMs→reels) reveals the discriminator, which we then fill in. FALLBACK (only if IG ids turn out obfuscated/absent on the shipping build): implement the surface predicate as a window-content heuristic (like/comment/share node cluster, or fullscreen video pager) in SurfaceMatcher — heuristics only after the log proves ids unusable. Added typeWindowContentChanged to the config XML for the within-app fragment-swap surface signal. (c) OVERLAY CHURN FIX: OverlayController used to addView/removeView on every foreground-app change — the device log showed the bubble window constructed/destroyed repeatedly (VRI cycles) and the system "displaying over other apps" notification re-firing each switch. Now the view is added ONCE at onServiceConnected (ensureAttached, starting GONE; lazy re-attach from setVisible if the permission is granted later) and only toggled VISIBLE/GONE via setVisible; removeView happens solely on destroy. D16's CHEAP invariant held: the count Flow is still collected only while VISIBLE. De-dup-by-package (D16 fix) was DROPPED — entering Reels within IG is a same-package window-state-changed we must re-scan for; setDoomSurface transition-gates the show/hide so re-evaluating every window-state event is idempotent and flicker-free.
D16. Floating live-counter bubble = a draggable overlay (🧠 + today's count) drawn via SYSTEM_ALERT_WINDOW/TYPE_APPLICATION_OVERLAY, shown only while a tracked platform is foreground. OWNERSHIP: WindowManager work lives in OverlayController; the AccessibilityService stays event-only (CLAUDE.md no-God-class rule) — it just maps window-state-changed → forPackage → overlay.show(platform)/hide(). ONE SOURCE OF TRUTH: the bubble collects the SAME CountRepository.observeToday() Flow the Home screen uses — no second counter. CHEAP: TextView updated on count change only (distinctUntilChanged), no animation loop, no polling, and the Flow is collected ONLY while the bubble is visible (collection cancelled on hide) so it does zero work off-IG. OPTIONAL: show() no-ops when Settings.canDrawOverlays is false, so detection never depends on the permission; overlay is a skippable SECOND onboarding step (OverlayPermissionScreen), deep-linking Settings.ACTION_MANAGE_OVERLAY_PERMISSION, re-checked on resume, skip persisted in prefs. Tap (movement < scaledTouchSlop) opens Home; drag repositions via updateViewLayout. Plain android.view TextView, NOT Compose — a Compose overlay from a Service needs SavedStateRegistry/lifecycle plumbing and is heavier; rejected for this. SCOPE CHANGE: to hide on LEAVING a tracked app, the service must receive the window-state-changed for the app switched TO — that event belongs to the destination package, so we removed android:packageNames from accessibility_service_config.xml (now all packages) and added typeWindowStateChanged. Privacy held: window-state-changed carries only the foreground package/class name (never content), untracked scroll events are dropped by PlatformRegistry.forPackage() (now the sole gate, no XML allowlist to mirror), and canRetrieveWindowContent is still used only for reel container class names. Accessibility disclosure description updated to say we also read which app is in the foreground (invariant #5 honesty). Known edge: an IME/dialog whose package ≠ the tracked app fires window-state-changed and briefly hides the bubble — accepted for v1, on the HANDOFF manual-test checklist. FIX (device-found, 2026-07-22): window-state-changed is far noisier than assumed — our OWN overlay window + Activity fire it as com.scrollkiller, and a tracked app fires many per scroll, so hiding on every non-tracked event made the bubble tear itself down ~350ms after appearing (device log showed the 138×93 TextView overlay added then removed repeatedly). Gate now acts only on a genuine foreground-app change: skip our own package, de-dup repeats of the same foregroundPackage, and the bubble view is IMPORTANT_FOR_ACCESSIBILITY_NO so it stops emitting its own events. IME/third-package popups can still cause a brief hide (recovered on the next tracked-app event) — that residual is the accepted v1 edge.
D18. Brain-state visual = pure function of today's count, in one place: com.scrollkiller.brain.BrainState (thresholds CRACKING_AT=50, FRIED_AT=150; forCount() → HEALTHY 0..49 / CRACKING 50..149 / FRIED 150+). Arc = 🧠 green → 🤯 amber → 💀 red (accentArgb on the enum). BrainState is pure Kotlin (no Android/Compose imports) so BOTH render paths derive from it with no second mapping: Home (Compose) via Color(accentArgb), the overlay bubble (plain TextView) via accentArgb.toInt() as a background tint. CHEAP held (D16): the bubble maps count→state inside the existing distinctUntilChanged Flow collector — state changes only, no animation loop. Home keeps the count number (tinted) alongside the brain; state labels live in strings.xml (localizable), mapped in the UI layer only. Rejected emoji options: same-🧠-plus-color (too subtle) and a face-melt arc (off-motif) — chose the strongest at-a-glance degradation. Guarded by BrainStateTest (boundary table).
D19. Phase-2 block screen = full-screen overlay over the reel surface when a platform's daily count crosses its limit. Limit lives in one place: PlatformSpec.dailyLimit (default 100; user setting later). Decision is a pure function BlockPolicy.overlayFor(count, limit, gatingActive, unlocked) → BUBBLE|BLOCK (unit-tested). SAFETY GATE (user-chosen "dormant until Reels-only"): originally gatingActive = spec.surfaceMarkers.isNotEmpty(); SUPERSEDED by D24 — the caller now passes spec.blockEnabled (a verified-markers switch), so the block NEVER fires while markers are unverified — it can't cover the feed. Consequence: the block does not trigger on-device until a device tour verifies markers and blockEnabled is flipped (verified meanwhile by BlockPolicyTest + layout preview). ARCHITECTURE: the service's single doom-surface signal now carries the Platform (doomPlatform, was Boolean) and routes overlay.onSurface(platform)/offSurface(); OverlayController became the on-surface coordinator owning the bubble AND a new BlockScreenController, choosing bubble vs block from the per-platform count (CountRepository.observeToday(platform) + new DAO observeCountForDatePlatform — same Room source, a projection not a second counter; refines D16 which used the total). BLOCK WINDOW: plain android.view + inflated overlay_block.xml (NOT Compose — D16 rationale), TYPE_APPLICATION_OVERLAY, MATCH_PARENT, FOCUSABLE so it traps touches + Back; add/removeView on show/hide (a focusable window must not linger; block is low-frequency so no D17-style churn). ROBUSTNESS: re-shows idempotently when IG returns to foreground, tears down on offSurface + service destroy/unbind. NEVER A TRAP: Exit → launcher home (ACTION_MAIN/CATEGORY_HOME), Back mapped to Exit; always leaves. Unlock = TEMPORARY bypass-until-leave-surface, a placeholder the challenge result replaces next checkbox. Guilt line = random from a static string-array (guilt_pack.json loader is its own checkbox). PLAY POLICY: (1) Accessibility API policy is the existential risk — a full-screen app-blocker is the most scrutinized use; mitigation is store-side, code stays defensible (user-set limit, always exitable). (2) Overlay-over-another-app is scrutinized as disruptive — defensible because user-configured + dismissible. (3) No impersonation: unmistakably ScrollKiller's own UI (💀 + "Reels are Locked"), never mimics IG/system chrome. No new permission (SYSTEM_ALERT_WINDOW already declared).
D25. Surface-tour DEBUG tooling + IG Stories false-match fix (2026-07-23). Symptom: IG "counts all downward scrolls" — expected, that's SHADOW (D24) counting while only logging the marker check. To find the real Reels/Shorts ids: extended SurfaceDiagnostics (NOT a parallel logger in the event-only service — D17) with (a) logHierarchy(root, spec) — a downward, depth-6, 120-node-budgeted, indented tree dump ("[depth] Class — resourceId — viewId", flagging any node matching a surfaceMarker with "← MATCHES surfaceMarker"); (b) logScrollDecision(...) — a crystal-clear per-scroll "[DECISION] [DETECTED]/[IGNORED] … gating=… onSurface=… — note" line that, in SHADOW, explicitly says "counted … would be IGNORED once ENFORCED". Both gated by ReelScrollAccessibilityService.DEBUG (= BuildConfig.DEBUG, a visible toggle; compiled out of release for privacy/Play — logs only structural class/viewIdResourceName, never node text). The spec's RESOURCE_ID_MAP / findResourceIdInHierarchy map onto the existing PlatformSpec.surfaceMarkers (the per-platform known-container-id list) + SurfaceMatcher.matchedMarker/matchedMarkerId — no duplicate map that could drift from the gate. BUG FOUND writing the test: candidate marker "reel_viewer" was DROPPED from Instagram (IG Stories are internally "reels" and use reel_viewer ids → would false-match); IG now keys on "clips_viewer" only. Also tightened TikTok (dropped generic "viewpager"), broadened YouTube ("shorts_player"/"shorts_container"). SurfaceMatcherTest pins the discrimination at the pure-string level (Reels/Shorts match; feed/stories don't). Still UNVERIFIED until the on-device tour — see D24.

D20. Raw scroll_events table (Phase 2) — invariant #4 / D4 realized on-device. DB bumped v1→v2 with a hand-written migration whose CREATE matches Room's generated schema exactly (column order, AUTOINCREMENT, NOT NULL) so the on-open identity check passes. Every detected advance now DUAL-WRITES: it increments the daily_counts aggregate (the counter source of truth that powers every UI/bubble Flow) AND inserts a raw ScrollEvent(platform, appPackage, timestamp, countedAs=PlatformSpec.unitNoun). Raw events are pruned >7d (CountRepository.maybePrune, throttled to once/hour so we don't DELETE on every advance); aggregates kept forever. The aggregate stays authoritative — raw is for recent breakdown/detail and future Phase-3 sync deltas, never a second counter. Timestamp/day-key remain device-local (interim; Phase-3 server-truth, invariant #2).

D21. Bubble idle-dismiss (Phase 2, problem #3) — the bubble was surface-gated (shown the whole time on a tracked app) which felt "too early". Now it appears ONLY on real scroll activity and self-hides after a 2s quiet gap. Mechanism: the service pokes OverlayController.onScrollActivity() on each COUNTED advance (post-debounce, so not per raw event); that shows the bubble and (re)arms a single Handler postDelayed(2s) hide. The count Flow keeps the number fresh only WHILE the bubble is visible — a count change alone never re-shows a bubble the user let go idle (visibility is owned by the idle timer, the number by the Flow). Surface gating still governs Flow collection (zero work off-surface); idle governs visibility within the BUBBLE state. The block is exempt (being over the limit is not "idle"). A Settings toggle (SettingsPrefs `bubble_enabled`, default on) can disable the bubble entirely — read by the overlay before showing.

D26. Instagram Reels marker LOCKED + flipped to ENFORCED (surface tour, 2026-07-24). The tour proved a clean, non-colliding discriminator: the Reels viewer emits `srcId=clips_viewer_view_pager` → MATCH(clips_viewer), while every sibling surface is NO_MATCH — home feed (list under `swipeable_tab_view_pager`), profile grid (`clips_grid_recyclerview`), DMs (`sticky_header_list` under `bottom_sheet_container`), and Stories (`reel_viewer_*` — Stories are internally "reels", which is exactly why we key on "clips_viewer" ONLY, never "reel_viewer"; guarded by SurfaceMatcherTest). So Instagram: gating SHADOW→ENFORCED, surfaceMarkers=["clips_viewer"], counts ONLY on the reel surface. blockEnabled stays FALSE (the block is a later, separately-gated step — D19/D24). Consequence: IG feed/profile/DMs/Stories scrolling now produces 0 counted advances (ENFORCED drops off-surface). YouTube was ALSO flipped/kept ENFORCED with the tour-proven marker `reel_recycler` (narrowed from D24's candidate list — the unverified `shorts_*` guesses were dropped because the YT home feed carries a Shorts SHELF whose ids could false-match; see D28).

D27. Container-class matching is package-agnostic (simple class name), not fully-qualified. BUG the tour found: YouTube Shorts counted ZERO. The transcript showed `srcId=reel_recycler verdict=MATCH(reel_recycler) counted=false reason="android.support.v7.widget.RecyclerView is not a tracked container"` — YouTube's Shorts pager is the LEGACY support-library RecyclerView, and the old `className.endsWith("androidx.recyclerview.widget.RecyclerView")` check never matched it. Fix: PlatformSpec.matchesContainer() now compares the SIMPLE class name (substringAfterLast('.')) against simple-name hints ("RecyclerView"/"ViewPager"/"ViewPager2"), so a support-lib widget matches an AndroidX hint of the same name. All specs' containerHints changed to simple names. This class of mismatch would recur on every app that hasn't migrated to AndroidX, hence the general fix rather than adding YouTube's FQN. Guarded by PlatformRegistryTest (both android.support.v7 and androidx RecyclerView hit; ViewPager v1 vs ViewPager2 stay distinct — preserves D15). NOTE: this only gets YouTube scrolls to the debounce; whether Shorts emits a usable scroll DIRECTION (deltaY≠0) is unconfirmed — re-tour will tell; if it only ever emits SAME/deltaY=0, YT needs its own advance signal.

D28. Overlay surface state is PER-EVENT + hysteresis, NOT a whole-window scan (supersedes D17/D24's window-STATE root-scan gate for the overlay). BUG the tour found: on the YouTube HOME FEED the window verdict flipped ON_SURFACE while `srcId=browse_fragment_layout_coordinator_layout` — the feed embeds a Shorts SHELF, so a tree-wide marker scan (SurfaceMatcher.windowMatchesSurface) false-positives on the feed. Counting was already correct (it evaluates the scrolled node's own ancestry per-event); the fix makes the bubble/block visibility key off that SAME per-event surface signal. Mechanism: a scroll whose ancestry matches a marker calls onSurfaceEvent(platform) → sets the overlay "on surface" and (re)arms a SURFACE_HYSTERESIS_MS=3s timer; the timer expiring (or leaving the tracked app) drops it. Hysteresis bridges the gap between swipes so the bubble doesn't flicker; a non-matching container scroll (feed/profile/DMs) never arms it. onForegroundChanged no longer scans the window tree — it only fires clearSurface() when the foreground package is untracked (left the app). Also: TikTok and Snapchat were NOT toured, so rather than ship guessed ENFORCED markers they were set to SHADOW (they were ENFORCED-with-candidates under D24) — SHADOW logs the marker check on-device for a future tour while still counting; the tradeoff is app-wide counting (fine for TikTok ≈ all-FYP; an accepted overcount for Snapchat Chat/Stories until its tour), and blockEnabled stays false so nothing is enforced on the user. Guarded by PlatformRegistryTest (IG/YT ENFORCED, TikTok/Snap SHADOW).

D29. Overlay is attach-once + SURFACE-DRIVEN visibility; entering a surface counts the landing reel (supersedes D21's per-scroll idle-dismiss). (a) BUBBLE VISIBILITY: D21 showed the bubble on each counted scroll then removed it after a 2s idle gap; the ask was to eliminate window churn (repeated ViewRootImpl construct/destruct + re-fired "displaying over other apps"). The bubble is now VISIBLE the whole time we're on the reel surface (D28's hysteresis holds "on surface" across the between-swipe gap) and GONE on offSurface — added ONCE at onServiceConnected, only ever toggled VISIBLE/GONE, detached solely on destroy/unbind (D17's attach-once, now with no idle add/remove path at all). OverlayController.onScrollActivity/showBubbleWithIdle/idle Handler deleted; startCollecting cancels any prior collector defensively. (b) ENTRY-COUNT: the reel you LAND on fires no scroll event, so it used to count zero. onSurfaceEvent now credits one advance on entering a surface, tracked as a "session" (enteredPlatform) that ends only on leaving the tracked app (clearSurface) — NOT when hysteresis merely drops the overlay — so watching one reel a while then swiping never re-counts it; an ENTRY_GUARD_MS=3s guard stops a quick flicker out-and-back (e.g. an IME from another package) double-counting. Net: total = landing reel + swipes (off-by-one UP vs before), well within the ±2/50 bar. The block is exempt from hysteresis-hide only in that blockEnabled is still false everywhere; when enabled later, revisit whether the 3s hysteresis should also gate the block.

D24. Surface-gating modes + candidate markers (Phase 2; supersedes D17/D19's "ship empty markers" for the counting gate). Rather than leave surfaceMarkers empty (pass-through) OR blindly enforce guessed markers (which would silently ZERO detection if wrong), a per-platform GatingMode governs the counting surface gate: PASSTHROUGH (markers ignored; count on containerHints — legacy), SHADOW (markers evaluated + LOGGED as SCROLL_DETECTED/SCROLL_IGNORED/SHADOW_MISS but counting happens regardless — validate a candidate on a real device with zero regression risk), ENFORCED (count ONLY on a marker match; a wrong guess fails toward UNDERcount, never counts a home feed — so ENFORCED REQUIRES non-empty markers, asserted in PlatformRegistryTest). Instagram = SHADOW with candidate markers ["clips_viewer","reel_viewer"] so its calibrated Phase-1 detection is untouched while we confirm the Reels discriminator. New platforms = ENFORCED with candidate markers (undercount-safe). A SEPARATE blockEnabled flag (not "markers present") gates the full-screen block, and ships FALSE for every platform — so D19's "never the feed" is preserved and strengthened: the block stays dormant until a device tour verifies markers and blockEnabled is flipped per-platform. NEXT on-device: run the labeled SurfaceDiagnostics tour per platform, replace the candidate marker strings, flip IG→ENFORCED and set blockEnabled, re-run the ±2/50 calibration.

D30. Overlay bubble hide is alpha + NOT_TOUCHABLE, never View.GONE (device-found surface churn, 2026-07-24; refines D17/D29). SYMPTOM the device log showed post-D29: a BLASTBufferQueue constructor immediately followed ~3–5s later by a destructor, repeating for the whole session (VRI#2/#3/#5/#6/#7), at 138×93 / 159×93 sizes — i.e. the bubble TextView's *surface* being created and torn down every hysteresis cycle (the 3s SURFACE_HYSTERESIS_MS window), at content-width-varying sizes (🧠 N as the digit count changes). ROOT CAUSE: D29's "add once, only toggle VISIBLE/GONE" removed the addView/removeView churn but NOT the surface churn — when a WindowManager root view goes View.GONE, WindowManagerService hides the window and FREES its surface (BLASTBufferQueue); the next View.VISIBLE re-allocates a fresh one. So the on-surface→hysteresis-expiry→on-surface cycle still constructed/destructed a surface every few seconds. FIX: the bubble root now stays View.VISIBLE for the service's lifetime and "hidden" means OverlayController.setBubbleShown(false) = alpha 0 (draw-time only, no relayout to zero size → surface not freed) + FLAG_NOT_TOUCHABLE (so the transparent overlay passes touches through to the app underneath instead of eating taps in its corner); "shown" = alpha 1 + clear NOT_TOUCHABLE. Both go through updateViewLayout, which keeps the window visible, so the single surface persists across every toggle. Idempotent (bubbleShown guard skips no-op relayouts; reset on attach/destroy so a re-attach after destroy re-hides correctly). ensureAttached now creates the view alpha 0 with NOT_TOUCHABLE in the initial LayoutParams (was visibility=GONE). NOTE the surface still legitimately resizes when the digit count changes width (5→50) — that's a resize of the existing surface, not a destroy/create, and only on a real count change, not per hysteresis cycle. D16's CHEAP invariant unaffected (Flow still collected only between onSurface/offSurface).

D32. YouTube ships BETA and is BARRED from driving limits/blocks; Maturity added (2026-07-25). DECISION GATE outcome: option (b), not (a). The D31 probe round was built so three device captures (YTPROBE_SWIPE/IDLE/TAP) would pick YT's advance strategy from evidence rather than assumption; the captures were not delivered, so there is nothing to lock — and per the operator's standing rule YouTube is not permitted to block Phase 2. WHAT IS KNOWN and unchanged: YT's SURFACE is proven (`reel_recycler`, D26/D27, ENFORCED) but its ADVANCE SIGNAL is not — every Shorts event reports scrollDeltaY=0 → SAME → debounced, so the only thing that counts is D29's landing-Short entry credit. YT's number is a known severe UNDERCOUNT. MECHANISM: a new `Maturity {STABLE, BETA}` on PlatformSpec, and eligibility to block is DERIVED from it — `blocksAtLimit = blockEnabled && maturity == STABLE`. The overlay now asks `blocksAtLimit`, never the raw `blockEnabled`. Derived rather than a second independent flag ON PURPOSE: "we don't trust this count" and "this count may enforce a limit" are the same decision, and two knobs invite a future edit that sets one and forgets the other; PlatformRegistryTest asserts no BETA platform is ever block-eligible. SCOPE: TikTok and Snapchat were marked BETA too — they were never toured and run SHADOW (app-wide counting), and Snapchat is a known OVERcount (Chat/Stories/Map counted as "snaps"), which is the worst possible input to a limit. Only Instagram (calibrated 49/50, D11) is STABLE. UI: a recessive "BETA" pill next to the platform name on the Today breakdown and the Apps bars — an honesty marker ("approximate, and it can't lock your screen"), deliberately `surfaceVariant`, not an alarm colour. Counting, gating, storage and sync are UNTOUCHED — a Beta platform still counts and still shows; it just cannot enforce. TO PROMOTE YT: run the three captures, implement the supported strategy as a per-platform DetectionStrategy (IG stays DELTA_Y_FORWARD), recalibrate, set STABLE.

D33. Guilt lines move from a `<string-array>` to a bundled, remote-shaped assets/guilt_pack.json (2026-07-25) — realizes D9. WHAT WAS WRONG: `R.array.block_guilt_lines` was 4 lines picked with `.random()` — no categories, no weighting, and a ~1-in-4 chance of showing the same line twice in a row. D39. Count reads are optimistic: in-memory first, Room reconciled by max (2026-07-25). SYMPTOM: a visible beat between the swipe and the bubble's number moving, on both IG and YT. DIAGNOSIS, structural â€” the on-device timing run is Run 2 of the HANDOFF and had NOT been done when this was written (the device was PIN-locked), so this ADR records an argument, not a measurement: of the three candidate layers, (a) the debounce is not a latency source on Instagram â€” SwipeDetector resets its quiet gap on EVERY DOWN, so the first DOWN of a swipe counts immediately; (b) the bubble's own refresh is not one either â€” it updates on every distinct emission; (c) the read path was, and is the only layer that is structurally unbounded: record() was fire-and-forget into Dispatchers.IO, so the number the user saw was gated on TWO separate SQLite commits (the daily_counts upsert and the raw scroll_events insert are separate suspend DAO calls, hence separate transactions) plus Room's InvalidationTracker noticing the table changed, re-running the query on its own executor, and only then emitting. Under Instagram/YouTube foreground load that is tens to low hundreds of ms. YouTube has one ADDITIONAL detect-side cost that this change does NOT address: IDENTITY_SCAN_MIN_MS = 250ms rate-limits the content-change identity evaluation, so a real advance can sit up to 250ms before anyone looks at it. That is a rate limit, not D11 calibration, and it is left alone pending the measurement. FIX: record() now bumps an in-memory PendingCounts SYNCHRONOUSLY on the caller's thread before dispatching the write, and every read Flow merges Room's rows with it. Room stays the source of truth and the only thing that survives process death; the in-memory map is a read-through cache of writes already issued â€” nothing increments it that does not also go to Room in the same call, so it is not a second counter. RECONCILIATION is max(room, pending) per platform (TodayMerge, pure and unit-tested), which works because PendingCounts holds a running TOTAL for the day rather than a delta: both sides converge as writes land, and an emission arriving mid-flight (Room reflecting advance N while N+1 is already pending) keeps the larger, so the count is MONOTONIC within a day and can never visibly flicker backwards. Summing instead of maxing would double every count â€” the property is enforced by test. The two ways a count legitimately goes DOWN are handled by dropping the pending state, never by the merge: clearAll() resets it (LAST, after both deletes â€” resetting first would leave an advance detected mid-clear in pending with its Room row already gone, and because pending is a running total that orphan would ride along as a permanent +1 forever), and a day rollover simply no longer matches PendingCounts.date. The day key is now resolved in record() on the caller's thread rather than inside the coroutine, so both halves file the advance under the day it was DETECTED on, not the day the IO thread happened to run on. D42. Daily freshness comes from a deterministic DECK, not from new content (2026-07-27). GuiltRotation already guaranteed variety within a session (no repeat until the pool cycles). What it could not give was variety across DAYS: with a fixed pool, day three is day one reshuffled, and the guilt stops landing roughly when the user can predict it. The obvious fix — author new lines daily — is a content treadmill nobody runs. So each day the eligible pool is narrowed to a DECK: 60% of the pool (floor 6), chosen by a seeded shuffle over FNV-1a(dayKey|installId). Pure function of (pool, day, install); nothing is persisted and nothing needs to be — two surfaces asking on the same day get the same deck, a process restart mid-day does not shift it, and a test can ask for any date. The install id (a locally-generated UUID in SettingsPrefs, NOT a device identifier — it is a rotation seed, not an identity) is mixed in so two people do not rotate in lockstep; without it a shared joke about the app's Monday line would be a real thing. FNV-1a hand-rolled rather than String.hashCode because this seed decides what content a user sees for the life of the install, and leaning on a platform hash means a future ART change silently reshuffles everyone. Lines that sat out yesterday are PRIORITISED into today's deck (stable partition, so today's shuffle order survives within each group); deprioritised rather than banned, since a two-day ban on a small pool would empty the deck. The reference set is yesterday's BASE DRAW (the pre-rotation shuffle), not yesterday's final deck — the latter is defined in terms of the day before it and so on back to the install, i.e. circular, and no finite cut of that chain is exact. That is a strictly weaker guarantee than "yesterday's deck", so it is the one written down and tested, alongside a separate test asserting the deck still churns against yesterday's REAL deck — otherwise a future rule change could satisfy its own definition while leaving the content static. The pool is canonicalised (sorted by id) before shuffling so reordering guilt_pack.json — an edit with no intent behind it — cannot reshuffle every user's rotation. Scales without code change: the deck is a fraction, so the pack can grow to hundreds of lines. Ships 72 lines, ~18 per tier, which is the minimum at which a 60% deck visibly rotates (asserted in tests).

D43. Lines carry their AUDIENCE; region/language packs are structural now, content later (2026-07-27). Own GuiltLocale type, not java.util.Locale: that carries scripts, variants, extensions and a platform-dependent matching algorithm, none of which we want deciding whose jokes someone sees. D44. ONE picker, one pinned line, every surface — and the panel names the platform in words (2026-07-27). D45. The no-hardcoded-lines rule is enforced by the build, not by review (2026-07-27). D46. Guilt lines REPEAT on a cadence that tightens with the count, capped by a display gap (2026-07-27). D41 fired one line per tier crossing — 50, 70, 100, 150, then silence for the rest of the day. At 400 reels the app had already said everything it was going to say, which is exactly backwards: the further in you are, the more present it should be. So firing became a repeating cadence driven by the daily total, on a NEW axis kept deliberately separate from intensity. GuiltTier still decides how HARD a line hits (which pool it is drawn from); GuiltCadence now decides how OFTEN one arrives. Neither file knows the other's numbers, so "the app gets meaner" and "the app gets more insistent" stay tunable apart — and they compound at the top by design: at 800 reels the lines are both the most savage the pack has and as frequent as the display allows. The schedule is one ordered table (GuiltCadence.SCHEDULE) and nothing else reads a threshold or an interval directly: from 100 every 10 scrolls, 250 every 7, 320 every 5, 400 every 4, 500 every 3, 600 every 2, 800+ every scroll. Declared ascending because that is how it is discussed and reviewed; the descending scan intervalFor() needs is derived rather than being a second ordering to keep in step (same shape as GuiltTier). Below 100 intervalFor returns NULL rather than a sentinel — "this count does not repeat" is the absence of an interval, and Int.MAX_VALUE would silently become a real cadence the day someone's count got large enough. Fifty and seventy therefore keep D41's behaviour exactly: they fire on the TIER CROSSING and then go quiet, because a repeating nag at 55 reels is the opposite of the design. Crossings still fire at 100 and 150 too, so an escalation announces itself instead of waiting out an interval it happens to land mid-way through. WHEN is GuiltFiring, a pure stateful class fed every count emission; the schedule itself is a lookup table but this is where every subtle edge lives, so it is separately unit-tested (25 assertions across baselining, pending suppression, rollover and clears). Three of those edges are load-bearing. (1) BASELINING: the first observation of a day or of a process records the count and fires nothing, because otherwise walking into Reels at 300 reads as `300 - 0 >= 7` and fires instantly, and again on every tab back in. The baseline PERSISTS across surface exits — OverlayController no longer resets anything in offSurface() — which is what makes re-entering at an unchanged count silent: the cadence measures SCROLLS, not arrivals, and time alone never fires. (2) A COUNT THAT GOES BACKWARDS within a day means a data clear, so it re-baselines rather than being treated as progress; otherwise the next scroll reads as hundreds at once and fires immediately, at a tier the user is no longer in. Same path handles the day rollover, which resets the cadence with the count per the daily-rollover rule. (3) SUPPRESSION IS PENDING, NOT DROPPED: when the display gap blocks a fire, no state is consumed, so the interval stays due and the tier stays un-fired and the line goes out on the first emission after the gap elapses. Dropping it would mean the faster you scroll the fewer lines you see — exactly backwards — and it is also what stops a gapped TIER CROSSING from being swallowed entirely. THE DISPLAY GAP is 5.5s (GuiltCadence.MIN_GAP_MS), and it is deliberately much larger than the ~1.5s the brief suggested. The schedule governs ELIGIBILITY in scrolls; the gap governs DISPLAY in seconds, and at the top of the curve those genuinely disagree — at 800+ every scroll is eligible and a fast scroller produces one about every second. A gap shorter than the 4s a line is displayed for means each line is overwritten before it can be read, so at the exact moment the app is trying hardest to be heard nothing on screen is legible; worse, the pill never collapses and the bubble stops being a counter at all. The counter is the product and the lines are commentary on it, so commentary must not evict the thing it is commenting on. 5.5s is therefore the full 4s display plus a guaranteed 1.5s counter-only window, derived from its two parts rather than written as a literal so the guarantee survives anyone re-tuning the display duration — which is also why DISPLAY_MS moved out of OverlayController and into GuiltCadence beside it, since split across two files the two numbers drift and the guarantee quietly stops holding. Practical ceiling at 800+ is ~11 lines a minute, which is already relentless. The clock is SystemClock.elapsedRealtime, not wall time: the gap is a DURATION, and a user changing the device date — which the handoff explicitly asks a tester to do for the daily-rotation run — must not be able to jam it open or shut. The day key stays wall-clock-derived, correctly, because it is a date. FIRING IS THE OVERLAY'S ALONE (GuiltLines.fire), even though Home also observes the count: a fire is something you SHOW, the bubble's nudge is what showing it means, and two callers would race for the same fire with the bubble silently losing a nudge whenever the ViewModel won — which is reachable, because stateIn's WhileSubscribed(5s) keeps Home collecting for five seconds after the user switches to Instagram. Home reads current() instead, which returns whatever fire() last pinned, so "Home shows the latest fired line" falls out of the existing pin rather than needing a second mechanism. current() keeps its lazy draw for the case where the overlay never runs at all (bubble switched off, or the overlay permission never granted) — without it Home would show a stale line forever. One consequence, accepted: if a tier crossing is gap-suppressed, current() will lazily repin a correct-tier line for the panel immediately and fire() will then draw a second one when the gap elapses. Both are current-tier, the one-line-at-a-moment invariant holds throughout, and the panel updating instantly on a crossing is arguably the better behaviour anyway. CONTENT SELECTION IS UNTOUCHED: fire() calls the same draw path as everything else, so a rapid-fire line is still tier-correct, still comes from today's deck, and still cannot repeat back-to-back — the no-repeat rotation is what keeps "every scroll" from degenerating into the same three lines. NO WINDOW CHURN: showNudge is text on the already-attached view plus one re-placement, exactly like a digit-count change (D30/D38 hold), which matters far more now that it runs dozens of times a day instead of four. No detection change, no intensity-threshold change; GuiltThresholds' 50/70/100/150 and GuiltCadence's table are separate tables that happen to share two numbers.

D47. Counts are a TOKEN, no-repeat is a WEEK, and the pack is too small — say so (2026-07-27). Three things, one root cause: D46 made lines repeat all day, and content written for a single moment does not survive that. (a) THE COUNT-IN-TEXT BUG. Lines were authored with the number baked in, so at 312 scrolls the app announced "One-fifty" while its own counter, an inch away, read 312. A line may now reference the count exactly one way: a {count} token substituted at render time, with {minutes} alongside it because a duration claim ("that is half an hour") is the same bug in different units — derived from the count through TimeEstimate and equally wrong at the wrong count. Without {minutes} the eight strongest existential lines would have had to be deleted rather than fixed. Rendering happens on EVERY render, not once at fire time: a line pinned at 310 and still on screen at 314 reads 314, because the alternative is the app contradicting the number beside it, which is the entire bug. THE GUARD IS THE INTERESTING PART. The obvious rule — "no bare integers" — would have passed the entire broken pack: every single offender was spelled out (Fifty, Seventy, A hundred, One-fifty). The brief asked for a bare-integer check; a bare-integer check would have caught nothing. So GuiltText.offendingNumber bans digits AND scale words (twenty…ninety, hundred, thousand, century, dozen) AND time units not preceded by {minutes}. Small words (one, two, three…) are deliberately allowed, because in this pack they are always idiomatic — "one more", "one of them", "one full lecture" — and a guard that fires on those gets switched off within a week. The guard runs in two places for two different failure modes: the PARSER drops an offending line (a bad remote pack degrades, per D33's tolerate-and-drop posture, rather than shipping the bug), and a TEST fails the build on the bundled pack (our own content silently shrinking is not an acceptable outcome). It found three offenders my own manual audit had missed — "Century scored", "another hour between friends", and one false positive ("any minute now") which was rewritten rather than exempted: a blunt guard everyone trusts beats a clever one with an exception list. 27 of 72 lines were rewritten; 26 now carry a token. (b) SEVEN-DAY NO-REPEAT. GuiltRotation's no-repeat was session-scoped and pool-cycle-based, which at the D46 cadence means a pool cycles in minutes — "no repeat" had quietly stopped meaning anything. It is now a rolling 7-day window over a persisted guilt_shown table (lineId PK, shownAt wall-clock millis; DB v2→v3, migration SQL matched byte-for-byte against Room's exported 3.json). LAST shown, not a log: the only questions asked are "inside the window?" and "which is stalest?", both answerable from one row per line, and a full log would grow without bound at the top of the cadence for no extra information. The selector must answer synchronously on a render path inside an AccessibilityService, so Room is read ONCE at process start into an in-memory GuiltHistory and written through afterwards. Between process start and that load landing the window is briefly unenforced — a deliberate, bounded hole, since the alternative is blocking a render on a database read; GuiltHistory.seed MERGES on max rather than overwriting, so a line shown during the gap does not get its timestamp dragged backwards by what disk said. Wall clock here, monotonic for D46's display gap: the history is persisted and must survive reboots, the gap is a duration and must survive clock changes. Both now travel in one GuiltNow so the distinction is visible at every call site instead of being two Longs nobody can tell apart. (c) RECONCILING WITH THE DAILY DECK (D42). D42 narrowed each tier's pool to ~60% a day to manufacture freshness. The 7-day exclusion delivers that property far more strongly — seen means excluded, not deprioritised — and the two cannot both narrow: 60% of a pool that has already had a week of shown lines removed is how a healthy pack reaches the exhaustion fallback. So the narrowing is DELETED and the seed survives as an ORDERING. Exclusion is the hard rule; the daily seed is the tiebreak. GuiltDeck.forDay/baseDraw/deckSize are gone rather than left vestigial, because a narrowing function nothing calls is a trap for the next reader. In the common path the order is inert (GuiltRotation draws by weight and ignores it); it earns its keep in the fallback, where many lines tie at "shown today" and something has to break the tie deterministically and differently per install. (d) GRACEFUL, LOUD EXHAUSTION. When a tier's whole pool is inside the window, the draw falls back to the least-recently-shown QUARTER of it — a slice, not the sorted pool, because the weighted draw that follows ignores order and would happily pick the line from a minute ago. Never-shown lines sort first (lastShownAt returns Long.MIN_VALUE, not null). The fallback fires an onPoolExhausted callback — a callback, not a log call, so GuiltSelector stays Android-free and a test can assert it — which GuiltLines turns into a warning that quotes GuiltPoolMath: "tier EXTREME has 18 lines and every one was shown in the last 7d. At 400 scrolls/day this tier needs ~434. EXPAND THIS TIER." Naming the target rather than just complaining is the difference between a log line someone acts on and one they filter out. (e) THE POOL-SIZE MATH, WHICH IS THE UNCOMFORTABLE PART. GuiltPoolMath derives consumption by running the REAL GuiltFiring over a simulated day — not a reimplementation, so it cannot drift from what ships, and it re-derives itself if the cadence or the tier thresholds are ever retuned. The finding: tier 4 absorbs essentially the entire cadence, because it starts at 150 and never ends. Fires/day — T1: 1, T2: 1, T3: 5, T4: 1 at 150 scrolls, 18 at 300, 62 at 500, 196 at 800. Tiers 1 and 2 fire exactly ONCE a day by construction (they sit below the schedule's first row, so only their tier crossing fires), so 7 lines each sustains any user forever and the shipped 18 is ample. Tier 3 spans exactly 100–149 at every 10, so it is permanently capped at 5/day: 35 lines sustains a week for ANY user, and the shipped 18 does not — a real but small and FINITE shortfall. Tier 4 is unbounded: 126 lines for a 300-scroll/day user, 434 for 500, 1,372 for 800. Against a shipped pool of 18. The recommendation is therefore deliberately not "author 1,372 lines": target 40 for tier 3 (closes it permanently), 150–200 for tier 4 (sustains the realistic heavy user at ~300/day, an 8–11× expansion), and accept the least-recently-shown fallback above that with the log telling us who is hitting it. The alternative worth considering, and explicitly NOT taken this session because D46 was to stay intact, is to flatten the cadence above ~500 — the top of the schedule consumes content faster than any human can write it, and a 2-scroll interval at 600 is a product choice that could be revisited more cheaply than a thousand lines can be authored. The numbers are pinned in GuiltPoolMathTest, including one test that asserts the CURRENT inadequate coverage rather than the target, so it passes today and fails the moment the pack grows — at which point the numbers here get updated with it. The build is deliberately NOT failed on the shortfall: blocking every unrelated change until a thousand lines exist would be the wrong lever.

D48. The cadence PLATEAUS at every 5 scrolls, and the pool targets become numbers the build tracks (2026-07-27). D47 ended by naming two levers for the tier-4 content shortfall and taking neither: expand the pack, or flatten the top of the cadence. Both are now taken, and the order matters — flattening first changes what expanding has to cost, so sizing the content bill before capping the cadence would have sized the wrong bill. (a) THE FLATTENING. GuiltCadence.SCHEDULE loses its 400→every-4, 500→every-3, 600→every-2 and 800→every-scroll rows. It is now three rows: 100→every 10, 250→every 7, 320→every 5, and every 5 from there to infinity. FLOOR_SCROLLS = 5 names the plateau and GuiltCadenceTest asserts intervalFor never returns less than it at ANY count, so a future tuning row cannot quietly reintroduce a bill the pack cannot pay. The rows are DELETED rather than clamped to the floor: a row whose interval the floor would override is a row that lies to the next reader about what the app does, and this codebase's whole convention is that the table IS the curve. Note what this necessarily gives up — the instruction was to keep 100→10 through 500→3 and cap only above that, but 400→4 and 500→3 are THEMSELVES faster than every 5, so "never fires faster than every 5 even at 800+" and "keep the 400 and 500 rows" cannot both hold. The stated invariant won, because the alternative reading (500→3 kept, a 600→5 row added) is non-monotone: the app would nag every 3 scrolls at 550 and every 5 at 650, which contradicts D46's founding principle that the further in you are the more present the app should be, and would have required deleting the well-formedness test that encodes it. The cost of the reading taken is that a 400–500/day user now gets a line every 5 scrolls instead of every 4 or 3. The display gap was already the binding constraint for anyone scrolling fast (MIN_GAP_MS caps the SHOWN rate at ~11/minute regardless of eligibility), so the product loss at the top is smaller than the table suggests; the content saving is not. (b) WHAT IT BOUGHT, derived by GuiltPoolMath running the real GuiltFiring, not by hand. Tier 4 fires/day: 1 at 150 scrolls, 18 at 300, 57 at 500 (was 62), 117 at 800 (was 196). Seven-day pool need: 7, 126, 399 (was 434), 819 (was 1,372). Tiers 1-3 are UNCHANGED by the flattening and always were going to be — tiers 1 and 2 sit below the schedule's first row and fire once each per day on their tier crossing forever, and tier 3 spans exactly 100-149 at every 10, so it is capped at 5/day whatever the top of the curve does. The honest reading of these numbers is that flattening does not rescue the ceiling: 819 lines is no more writable than 1,372. What it does is make the MIDDLE of the curve affordable, which is where the users are. That is the finding, and the ADR states it rather than presenting a 40% cut as a solution. (c) THE TARGETS, as code. GuiltPoolMath.EXPANSION_TARGETS is T1 18, T2 18, T3 40, T4 150. They live beside the math that justifies them rather than in this file, because a target in an ADR is a sentence nobody re-reads and a target in the object the exhaustion log already quotes is a number that shows up in logcat. Each is a choice about WHO is covered, not about what the cadence demands: T1/T2 are already met and permanently so; T3's 40 CLOSES the tier — consumption is capped at 5/day by the band's finite width, so 35 sustains a week for any user at any rate and 40 leaves room, making it the cheapest complete win in the pack at 22 lines; T4's 150 sustains a 7-day no-repeat for ~320 scrolls/day and explicitly does NOT chase 800/day, which would cost 819. (d) THE BUILD TRACKS THE GAP, NOT THE GOAL. GuiltPoolMathTest gains two tests. One asserts the targets are the right size FOR THE CADENCE — 40 must exceed tier 3's permanent ceiling, 150 must cover 300-350 scrolls/day — so a future cadence edit that invalidates a target fails there rather than being discovered when someone starts writing. The other asserts the shipped pack is short in EXACTLY tiers 3 and 4, with a message that prints every tier's lines/target and what it currently sustains. That is green today and red the day the content lands, which is the same posture D47 chose and for the same reason: failing the build on "not written yet" would block every unrelated change until a content task nobody is mid-way through completes. The content expansion is deliberately NOT done in this session and is not a blocker for anything — it is a parallel task, with community submissions as the long-term tier-4 supply. (e) THE LOG NAMES BOTH NUMBERS NOW. D49. The block goes live — on Instagram, on the user's own limit, and always exitable (2026-07-27). The app has counted, nagged and guilted since Phase 1 and has never once stopped anyone. The machinery to do it has existed since D19 — BlockScreenController, overlay_block.xml, the GUARDIAN mascot, BlockPolicy — and has been structurally dormant the whole time, because blockEnabled shipped false on every platform and blocksAtLimit therefore never returned true. That dormancy was correct and deliberate: D19/D24 refused to blackout a screen on markers nobody had verified on a device, and D32 refused to enforce on a count nobody had calibrated. Both preconditions are now met for Instagram AND ONLY INSTAGRAM, so the flip is one platform wide. (a) WHY IG AND NOTHING ELSE. Two independent things have to be true and they guard different failure modes. The surface marker `clips_viewer` was device-toured on 2026-07-24 (D26) and IG is GatingMode.ENFORCED, which is what makes "the block can land only on the reel player" a property of the code rather than a hope — every sibling surface was NO_MATCH, and the near-miss is real: Stories are internally "reels" and emit reel_viewer_*, so a marker of "reel_viewer" or a broadened "reel" would put a full-screen block over someone's Stories. That exact string is now pinned in PlatformRegistryTest. Separately the count is calibrated 49/50 (D11), which is why IG is Maturity.STABLE and therefore why blocksAtLimit — not the raw blockEnabled — is true. YouTube is the instructive case: its surface IS proven (D26) and its advance strategy IS resolved (D34), but it has never been calibrated, so it stays BETA and cannot block however anyone edits blockEnabled. TikTok and Snapchat were never toured at all, and Snapchat is a known OVERcount, which is the worst possible input to a limit. Three tests hold this shut: exactly one platform may have blocksAtLimit and it is Instagram by name; any platform with blockEnabled must be ENFORCED with non-empty markers; and the three unmeasured platforms are asserted false on BOTH flags positively, so promoting one requires coming here and meaning it. (b) THE LIMIT IS THE USER'S. PlatformSpec.dailyLimit is demoted to a DEFAULT; SettingsPrefs.dailyLimit(context, platform) is what the overlay reads, and it is read per count emission rather than cached, because a limit that took effect "next time you open Instagram" is a setting that looks broken. Storage is PER-PLATFORM even though one platform can block today: "100 reels" and "100 Shorts" are different commitments, and a single shared budget would mean promoting YouTube later silently halves everyone's Instagram allowance — per-platform now costs one string concatenation and removes that migration entirely. Every tunable number lives in BlockLimits (default 100, range 20–300, step 10, grace 5 minutes) rather than as literals at the four call sites that need them — the overlay reads the limit, Settings writes it, PlatformSpec defaults it and a button prints the grace, and four homes for one product number is exactly how a slider ends up offering a range the policy does not honour. The Settings slider is rendered once per blocksAtLimit platform rather than as a hardcoded Instagram row, so a BETA platform can never show a limit control it would not honour. clampLimit runs on the way IN to storage and on the way OUT, since a value can arrive from a restored backup or a build with a different range. Writing it turned up a real bug: snapping adds half a step before dividing, so a garbage Int.MAX_VALUE overflowed to negative and clamped to the MINIMUM limit — the one wrong answer that covers someone's screen 280 reels early. Range is now coerced BEFORE snapping, which cannot overflow and stays in range because both ends are themselves on-step. (c) "5 MORE MINUTES", AND WHY IT IS PERSISTED. D19's Unlock was a bypass held in memory and reset on leaving the surface. It is replaced by a timed reprieve: an absolute wall-clock deadline written to SharedPreferences per platform. Persisted because the app made a promise measured in minutes, and a reprieve that a service restart or a crash silently revokes is a promise broken at the worst possible moment; surviving app-exit because a user who steps out to answer a message inside their own five minutes has not used them up. Wall clock rather than elapsedRealtime, the same split D47 drew: persisted state that must survive a reboot is dated, and only a duration measured inside one process (D46's display gap) may use the monotonic clock. The accepted consequence is that winding the device clock BACKWARDS extends the user's own reprieve — a self-harm cheat, not a way to get trapped, and defending it would cost more than it is worth. NOTHING SCHEDULES THE RE-BLOCK: there is no timer, because the render path already compares the deadline against now on every count emission, so the next reel after the grace lapses blocks and no reel before it does. A timer would be a second source of truth for the same instant and would have to be cancelled correctly on every exit path. The boundary belongs to the block (nowMs >= graceUntilMs re-blocks), so five minutes means five, and 0 reads as "expired" rather than needing a separate has-a-reprieve flag. (d) THE BUG THAT WOULD HAVE MADE THE FEATURE LOOK BROKEN. The overlay's surface state is kept alive by a 3-second hysteresis armed by each marker-matched scroll (D28). Once a full-screen block covers Instagram the user CANNOT scroll, so nothing re-arms it — and Instagram is DELTA_Y_FORWARD, so its content-changed path does not re-arm either. The plain runnable therefore fired, dropped the doom surface, called offSurface(), and tore the block down three seconds after raising it, handing the reels straight back. It now RE-POSTS itself while overlay.isBlocking instead of expiring: a showing block means the user is by construction still on the surface, and re-posting rather than simply returning means the normal 3-second behaviour resumes by itself the moment the block comes down, with nothing having to remember to re-arm it. This is deliberately NOT a guard inside offSurface(): that method is also the path that runs when the user LEAVES the tracked app, and a guard there would be a way for the block to outlive leaving Instagram — the opposite of invariant 6. (e) ALWAYS EXITABLE IS NOW AN INVARIANT, AND IT CHANGED THE CODE. Written into CLAUDE.md as invariant 6 rather than left as a class comment, because from this session the app can cover another app's screen. Three concrete consequences. Exit DISMISSES BEFORE starting the launcher intent and does not depend on it succeeding: on a locked-down device where the intent throws, the user must be looking at Instagram rather than at an overlay that would not go away. The Back listener stays on the ROOT with the root focused — a ViewGroup's OnKeyListener only runs when the ViewGroup itself is the focused view, so the obvious "give Exit initial focus for TalkBack" change would have silently stopped Back being handled at all, and an unhandled Back on a WindowManager-added view does nothing, which is precisely the trap. TalkBack order is solved in the LAYOUT instead: Exit moved above "5 more minutes", so traversal reaches the way out before the way to keep scrolling, and the visual hierarchy now matches what an anti-doomscroll app should be nudging toward. Back also consumes ACTION_DOWN as well as ACTION_UP so the framework never sees a half-handled Back. (f) THE WINDOW MODEL: TWO WINDOWS, NOT ONE. The instruction was to make the block the bubble window escalating — attach-once, no add/remove ever. It is deliberately not done that way, and the alternative was put to the user before any code was written. The bubble window is NOT_FOCUSABLE and passes touches through; the block must be FOCUSABLE and trap them. Escalating one window means toggling exactly that flag on the window the user spends all day underneath, and a failure mid-toggle leaves a full-screen focusable overlay up with no block UI on it — an input trap, which is the one outcome invariant 6 exists to prevent. Two windows are failure-isolated: a block that fails to add leaves the bubble untouched, and the bubble can never become focusable at all. D30's no-churn property is not in tension here, and the existing D19 comment already said why — that concern was a construct/destruct cycle every 3–5 seconds on the hysteresis timer, whereas a block is raised and dismissed on the order of twice a day. The bubble window remains attach-once and untouched. (g) THE BLOCK LINE IS DRAWN ONCE PER EPISODE. render() runs on every count emission, and the naive GuiltLines.block(context, count) there would draw a NEW line each time and stamp each one into the 7-day history — an unbroken block would eat a tier's whole pool in a handful of emissions and land the app in D47's exhaustion fallback for the rest of the week, for lines nobody ever finished reading. So GuiltLines now holds a block EPISODE: the draw is pinned for the life of one block and released by endBlockEpisode(), while the RENDER is not — the raw text is re-substituted on every call so {count} and {minutes} stay live even though the sentence does not change. Same split as the ambient pin and for the same reason: a line must never contradict the number beside it. The episode is released on exit, on the reprieve, on leaving the surface, on a locale change (the held line is in a language the user just declined) and on destroy — all through one hideBlock() helper, so a dismissal path cannot forget. (h) PLAY POLICY, the whole list, because this is the highest-risk combination in the codebase — a full-screen overlay over another app, driven by an AccessibilityService. (1) The Accessibility API policy requires the DECLARED function to match the actual one, and accessibility_service_description said only that the service counts. It now states that it also shows a full-screen block, that the user can always leave it, and that they can always ask for a few more minutes. The in-app disclosure (invariant 5) already covered blocking; the system-facing description did not, and that is the one Play reads. (2) EXIT USES A LAUNCHER INTENT AND MUST NOT BECOME performGlobalAction(GLOBAL_ACTION_HOME). Driving another app's navigation through the accessibility API is a materially stronger "misuse of the Accessibility API" signal than starting the launcher, for an outcome the user cannot tell apart — recorded here so nobody simplifies it later. (3) No impersonation: the block is unmistakably ScrollKiller's own screen, own mascot, own colours, no Instagram mark; D44 already drew that line. (4) Play removes apps that make a device unusable, and invariant 6 plus the acceptance runs are the mitigation — the runs are what make it real rather than asserted, which is why HANDOFF puts the Exit run FIRST, before a block is ever deliberately raised. (5) KNOWN LIMITATION, not a violation: on Android 12+ any app may call setHideOverlayWindows(true) and the system will hide our TYPE_APPLICATION_OVERLAY, so if Instagram ever does the block silently will not appear. That argues against ever marketing this as unbypassable. (6) Android filters touches on overlays sitting over system permission dialogs — correct behaviour, worth knowing during testing when a taps-do-nothing moment shows up. (7) Android 13+ gates accessibility for sideloaded builds behind "Allow restricted settings" — test friction, in HANDOFF. (i) ONE DELIBERATE ASYMMETRY: the block does NOT respect the bubble's Settings toggle. Switching the passive counter off is a statement about a pill over your video, not a withdrawal of the daily limit you set. The overlay PERMISSION still gates both, so a user who refuses it gets neither, and detection plus the in-app counter are unaffected either way. No detection change, no tier/intensity/cadence change, no pack change. 211 tests pass.


D50. The challenge engine, and "Walk 20 steps" end to end (2026-07-27). D49's block shipped and verified, but the only way past it was a free tap — a reprieve with no cost, which makes the block a speed bump rather than a decision. This adds the other half of the BrainPal unlock mechanic: you get your time back by doing something physical, which breaks the scroll trance in a way tapping cannot. Scope was deliberately ONE challenge built completely rather than four half-wired ones, behind an abstraction that makes the next three cheap. (a) THE ABSTRACTION, AND WHY IT HAS TWO ENUMS. ChallengeSpec {id, type, target, sensorStrategy, promptRes} + ChallengeRegistry, modelled on PlatformSpec/PlatformRegistry deliberately — that file already proved the pattern for a thing whose per-instance details genuinely differ but whose plumbing is identical. ChallengeType (WALK/JUMP/FACE_DOWN/FOREHEAD) and SensorStrategy (STEP_EVENTS/STEP_CUMULATIVE/ACCEL_PEAKS/ORIENTATION_HOLD) are SEPARATE for exactly the reason PlatformSpec splits `platform` from `advanceStrategy`: what the user DOES and how we MEASURE it are different questions and they do not map one-to-one. WALK alone already needs two measurement paths depending on hardware, and a future JUMP and FACE_DOWN would both read the accelerometer while being nothing alike to perform. The unimplemented entries ship DECLARED AND UNUSED, the same way AdvanceStrategy.EVENT_PULSE does, so the next challenge picks its shape from a written menu instead of inventing one. ChallengeRegistry.IMPLEMENTED names the two strategies the engine actually honours, and ChallengeRegistryTest asserts every ENABLED spec falls inside it — a spec added without its sensor code would otherwise ship a challenge that can never complete: the user walks, the ring never moves, and the only way out is the button they were told they did not need. That fails the build instead. promptRes is a format string taking `target`, so "Walk 20 steps" cannot drift from the 20 the engine counts to — the rule D49 applied to the snooze button, reapplied. (b) THE REWARD IS DELIBERATELY UNEQUAL, AND THIS WAS THE DESIGN CALL OF THE SESSION. The challenge and the free tap grant their reprieve through the identical D49 mechanism, so had they granted the same five minutes the challenge would have been STRICTLY DOMINATED — nobody walks twenty steps for what one tap gives free — and the feature would have shipped dead without anyone noticing for months. So CHALLENGE_GRACE_MINUTES = 15 against GRACE_MINUTES = 5, and the gap IS the incentive: the two buttons sit next to each other reading "5 more minutes" and "Walk 20 steps — get 15 minutes", so the user is choosing between a small free thing and a larger earned one rather than being nagged toward the harder path. BlockLimitsTest asserts CHALLENGE_GRACE_MS > GRACE_MS so a later tuning edit cannot quietly reintroduce the dead version. The alternative considered and NOT taken — cap free taps per day and leave both at five minutes — is a stronger long-term product but needs a persisted per-day counter, a day-rollover reset and a new empty state on the block; it is a better second move than a first one. Everything else about the reprieve is D49's unchanged: same persisted per-platform wall-clock deadline, survives leaving Instagram, survives a service restart, re-blocks on the next reel after it lapses, no timer anywhere. (c) DETECTOR FIRST, COUNTER AS THE FALLBACK, AND THE TWO EDGES THAT ARE THE ACTUAL WORK. TYPE_STEP_DETECTOR fires one event per step and holds no state, which is inherently incremental and low-latency — exactly what a live ring wants — so it is preferred. TYPE_STEP_COUNTER is the fallback for devices shipping only that, and it carries both edges. First, it reports steps since BOOT and is SHARED with every other app on the device, so the first reading of a challenge is a number in the thousands with nothing to do with this challenge; treating it as progress would complete every challenge instantly. It is recorded as a baseline and scores zero — the same "first observation baselines and fires nothing" rule GuiltFiring already lives by. Second, that counter RESETS ON REBOOT, so a device restarted mid-challenge sends a total smaller than the baseline and the naive subtraction yields negative progress and a ring drawn backwards; going backwards means the counter restarted, not that the user un-walked, so it re-baselines from the new value — again precisely GuiltFiring's handling of a count that drops within a day. Both live in ChallengeProgress, which is pure Kotlin with no Android imports, which is why both are unit-tested rather than discovered on a phone. The SPEC's sensorStrategy is therefore a PREFERENCE, not a promise: a spec cannot know what hardware it will run on, so StepSensorSource resolves the real strategy per device at start. (d) BATCHING IS SWITCHED OFF, AND IT IS NOT A MICRO-OPTIMISATION. registerListener is called with maxReportLatencyUs = 0. Step sensors are exactly the kind the platform likes to batch — buffering events in hardware and flushing them in a lump to save power — and a batched flush makes the ring sit at 0/20 while the user walks across the room and then jump to 12/20 all at once. The user reads that as broken, gives up, and taps the free five minutes instead. Zero latency costs a little power for the seconds a challenge is on screen and buys the only feedback the mechanic has. Progress also CLAMPS at target, because a burst arriving at once must not render 140% of a circle. (e) INVARIANT 6 SHAPED THE UI, IT DID NOT JUST SURVIVE IT. The challenge is an ALTERNATIVE to Exit, never a replacement, and the non-obvious consequence is that the challenge panel carries its OWN Exit button: a full-screen challenge offering only "Back" would be a second screen the user has to escape before they can escape, which is the trap in a different costume. Exit is first in both panels for the same TalkBack traversal reason D49 established. The challenge is a CHILD SWAP inside the block window — block_panel and challenge_panel toggled VISIBLE/GONE, the same shape as the bubble's expand (D37) — so it is not a second window, not a rebuild, and the root keeps its focus and therefore its Back-key listener, which means Back still maps to Exit throughout the challenge. That last point is the same trap D49 found: a ViewGroup's OnKeyListener only runs when the ViewGroup itself is focused, so nothing in the challenge panel may take touch-mode focus. (f) UNAVAILABLE MEANS INVISIBLE. Android 10+ gates the step sensors behind the ACTIVITY_RECOGNITION runtime permission, and some devices have no step hardware at all. When either fails, the challenge button is simply NOT on the block screen — which looks exactly like the build verified this morning. A button that cannot do its job has no business on a screen covering another app, and pointing at Settings from there would be a signpost rather than a fix, because an AccessibilityService has no Activity and therefore cannot request a runtime permission at all. So the request lives in the Settings tab, with ActivityResultContracts.RequestPermission — which is the structural difference between MotionStatus and its siblings OverlayStatus/AccessibilityStatus, both of which can only deep-link to system settings. MotionStatus.hasPermission returns TRUE on API 26–28 without asking anyone, since ACTIVITY_RECOGNITION only became dangerous in API 29 and the platform's step sensors needed no grant before that; returning false there would hide the challenge from devices that run it perfectly well. The Settings row itself is shown only when the device HAS a step sensor: asking for a permission that would unlock nothing is worse than staying quiet. (g) SENSOR RELEASE IS A ONE-WAY-IN, ONE-WAY-OUT DISCIPLINE. A step sensor left registered by a background AccessibilityService is a battery complaint nobody ever traces back to us. ChallengeController.stop() is idempotent and is routed through OverlayController.hideBlock() — the same single funnel D49 built for endBlockEpisode(), and for the same reason: every dismissal path (Exit, the free tap, completion, cancel, leaving the surface, service destroy) goes through one place, so none of them can forget. Cancel DROPS progress rather than banking it: a challenge you can chip away at across five separate blocks, two steps here and three there, is a slow tap. (h) THE RING IS THE APP'S FIRST HAND-DRAWN VIEW, and the exception is earned. A horizontal ProgressBar reads as "loading" — something being done TO you that you wait out — while a ring filling as you walk reads as effort you are putting in, which is the entire psychology of the mechanic: the block is asking for something and the feedback has to look like the something is being given. It is ~40 lines of Canvas.drawArc against a styled ProgressBar that would still be the wrong shape. Fixed colours rather than theme attributes, like overlay_block.xml and overlay_bubble_bg, because it draws outside the Compose theme. Two details that are wrong by default: the arc rect is inset by half the stroke, since an arc is drawn CENTRED on its path and a full-bleed rect clips the outer half of the line; and the sweep starts at -90° so it begins at twelve o'clock rather than three. (i) PLAY AND PRIVACY. ACTIVITY_RECOGNITION is a normal runtime permission — no declaration form, unlike background location — but it does need an honest in-app rationale, which the Settings row's copy provides. The accessibility_service_description is deliberately NOT changed: the accessibility service's function is unchanged, and step data is read by the app from SensorManager, not through the accessibility API. Step counts are read, compared to a target and discarded — never stored, never synced, never logged — which keeps the architecture invariant that no content or behavioural data leaves the device. docs/STORE_COPY.md gains an entry: the challenge must never be marketed as unskippable, because Exit and the free tap are both still there by design. No detection change, no cadence change, no pack change, no change to how the block decides to fire. 229 tests pass (+18: ChallengeProgressTest 11, ChallengeRegistryTest 6, BlockLimitsTest +1).


D51. The app must never run half-dead in silence (2026-07-27). A device run looked like a block regression and was not one. Detection was flawless throughout — clips_viewer MATCH, counted=true, the counter climbed to 108 — the block fired IN CODE well over a hundred times, and Android refused the window every single time: `AppOps: Operation not started op=SYSTEM_ALERT_WINDOW`. The overlay permission had been revoked by a debug reinstall. THE BUG IS NOT THAT THE PERMISSION WAS MISSING. The bug is that nothing said so: the user scrolled 108 reels past a limit of 100 with the product's core feature dead and received no signal of any kind. (a) THE ROOT CAUSE IS AN INHERITED JUDGEMENT, WHICH IS WHY IT WAS INVISIBLE. Two places check the overlay permission and both fail soft by design. OverlayController.ensureAttached() logs at debug and returns, and that is CORRECT: the bubble is cosmetic, D16 deliberately made it optional so that detection never depends on it, and a user who declines the permission should still get counting. BlockScreenController.show() copied that shape — same check, same Log.d, same silent return — and should not have. The block is not decoration; it is the thing the app is for. The same fail-soft that is right for a floating pill is exactly how the product silently stopped existing while every other subsystem reported success. No test could have caught it: every unit test passed, the block policy returned BLOCK correctly, and the failure lived entirely in the gap between "we decided to show a window" and "the window appeared". (b) THE LAYERING, AND NAMING WHICH LAYER IS GUARANTEED. The obvious fix — "post a notification when the block is refused" — rebuilds the same bug one level up, because on API 33+ a notification needs POST_NOTIFICATIONS and can be denied, and if the accessibility service is off then nothing is running to post anything at all. A fallback whose failure mode is silent failure is not a fallback. So the design is three layers with an explicit statement of which one cannot fail: THE HOME BANNER is guaranteed — it is drawn by the app the user is looking at, needs no permission and no running service, and covers every case including "we could not even warn you". THE NOTIFICATION is the nudge, best-effort, and covers the case that actually matters (the user is inside Instagram, not inside our app). LOGCAT is developer-only and is what we had; it is why 108 happened. Anything that treats the notification as the safety net has misunderstood the incident. (c) PermissionHealth IS THE SINGLE SOURCE OF TRUTH. A pure data class over three booleans with derived answers — canDetect (accessibility), canBlock (accessibility AND overlay), canWarnOutOfApp, isFullyActive, isDegraded, isHealthy, firstMissing — read by BOTH the block path and the UI, so Home can no longer claim to be fine while the overlay is being refused. It is pure Kotlin so the whole state machine is unit-tested, and PermissionHealthReader does the Android-side reading by COMPOSING the existing AccessibilityStatus and OverlayStatus helpers rather than reimplementing them; a second implementation of "is the service on" is how the Activity and the service end up disagreeing. isFullyActive deliberately IGNORES notifications: notifications are how a failure is reported, not part of the job, and an app calling itself "not fully active" over a missing alert channel would be crying wolf about the one banner that has to be believed the first time. That case is isDegraded instead, and the banner renders it in a quieter tone. canNotify checks BOTH the runtime grant and NotificationManagerCompat.areNotificationsEnabled, because a user can switch the app's notifications off without revoking the permission and a notification posted into a disabled channel is precisely the silent failure being eliminated; it also returns true below API 33, where the platform required no grant at all. (d) PermissionGap IS ORDERED, AND THE ORDER IS THE FEATURE. ACCESSIBILITY → OVERLAY → NOTIFICATIONS, worst first, and firstMissing returns the earliest absent one. The banner offers exactly ONE Fix button routed from it, because three buttons would ask the user to prioritise a system they cannot see; the app knows the severity order and points at the one thing worth fixing. With everything broken it must point at accessibility — fixing the overlay first would change nothing, since nothing is running to use it. The enum's declared order is asserted in a test rather than left implicit, because reordering it is a one-line edit that would silently aim the Fix button at the wrong screen. (e) WARN EARLY AND AT THE LIMIT, ONE NOTIFICATION. The instruction was to warn when a block is prevented; the chosen behaviour also warns ONCE PER DAY on entering a reel surface with the block already dead. On the incident that is the difference between finding out at reel 1 and finding out at reel 108, which is the entire point of the session. Both use the same notification id, so the at-limit warning REPLACES the early one rather than stacking — they are the same problem at two moments, and two notifications about one broken permission is how a warning becomes noise. The early warning needs persisted state (a day key in SettingsPrefs) because onSurface runs on every surface entry and the system restarts an AccessibilityService far more often than a day rolls over; an in-memory flag would re-warn on every restart, and a once-a-day alert that fires ten times is one the user turns off — silencing the very thing telling them the app is broken. The AT-LIMIT warning needs NO rate limiter at all: it is called from the render path on every count emission, and setOnlyAlertOnce(true) makes every post after the first update the text silently. That is a property of the notification rather than state we have to keep correct, which is the better kind of solution. It also fires only for a platform whose blocksAtLimit is true — warning that the block is dead on a BETA platform that was never going to block would be a lie. (f) IT CANCELS ITSELF ON RECOVERY. The healthy branch of the render path calls cancel(), so a fixed permission clears the warning at the next count emission with nothing polling. A "ScrollKiller can't block" notification still sitting in the shade after the user has already fixed it is its own small dishonesty and teaches people our warnings are stale. cancel() is guarded by a `posted` flag so the normal healthy path — which calls it on every emission — does not make a binder call per reel to dismiss a notification that was never posted. (g) REJECTED: BLOCKING ANYWAY VIA A FULL-SCREEN ACTIVITY. An Activity needs no SYSTEM_ALERT_WINDOW, so "start an Activity instead" looks like it would make the block permission-proof. It does not work and should not be attempted. Background activity starts are blocked from Android 10 and an AccessibilityService is not on the exemption list; the documented workaround — a notification with setFullScreenIntent — requires USE_FULL_SCREEN_INTENT, which from Android 14 is restricted to calling and alarm apps and is auto-denied for us at targetSdk 35. Recorded here so it is not re-proposed as the obvious fix. (h) PLAY AND COPY. POST_NOTIFICATIONS is a normal runtime permission with no declaration form, requested from a Settings row using D50's motion-access pattern rather than a third onboarding step, so the app does not ask for three permissions before it has shown the user anything. The notification is a genuine app-health alert — it posts only when the app cannot do the job the user asked for, names ScrollKiller, and deep-links to a system Settings page for ScrollKiller; it must never be repurposed for re-engagement. docs/STORE_COPY.md gains a line: never claim the block "always" works, because it depends on a permission the user can revoke at any moment — a third independent reason the never-unbypassable entry stands. (i) WHAT WAS DELIBERATELY LEFT ALONE. The bubble's fail-soft in ensureAttached() is unchanged: it is genuinely optional and D16's reasoning still holds, and the banner covers it. The three remaining challenges were explicitly excluded from this session — an integrity fix outranks new surface area. No detection change, no cadence change, no block-policy change, no pack change. 238 tests pass (+9, PermissionHealthTest).
