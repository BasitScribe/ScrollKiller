# Decisions (append-only)

D1. Android-first, iOS deferred until app self-funds $99/yr. iOS interception = Shortcuts automation (one-sec style), no per-reel count on iOS. Mac never purchased; iOS builds via GitHub Actions macOS runner.
D2. Detection fully on-device (AccessibilityService). Server stores counts only — privacy is a product pitch.
D3. Sync = delta events with client UUID batch_id, server dedup. Rejected: absolute-count POSTs (BrainPal's concurrency bug class).
D4. History kept as daily aggregates forever; raw events pruned 7d. Rejected: 24h wipe (kills streaks/graphs).
D5. Realtime battles = 30s polling + FCM push. Rejected for free phase: WebSockets (RAM per connection kills free instance).
D6. GitHub Actions is primary CI. Ephemeral Jenkins (webhook→Lambda→EC2 start/stop→S3) is a separate learning track, never release-blocking. Rejected: fixed 2h scheduled Jenkins window (breaks per-push feedback; EBS bills while stopped; doesn't cover iOS).
D7. Free tiers: Render/Fly + Neon + Upstash + FCM. First paid upgrade expected ~5-10K DAU.
D8. Monetization: free 3 months, then ₹100/mo Pro. Self-funding at ~2.5-3K DAU @ 2% conversion.
D9. Guilt pack = remote-updatable JSON, categorized/weighted; global-first English now, language packs later. Mix guilt with pride/streak lines to avoid uninstall-from-shame.
D10. Day boundary computed server-side from users.timezone. Client clock never trusted for dates.
D11. Reel-advance detection = time-debounce, forward-only (DOWN). Mechanism: activity-reset quiet-gap — reset the timer on every DOWN, count only the first DOWN after a gap > minAdvanceIntervalMs (Instagram: 200ms). Rejected: fixed refractory — observed fling settle (~640ms) and genuine inter-swipe gaps (~108ms) overlap, so no single fixed window separates them; activity-reset collapses any-length fling burst to 1 and fails toward mild undercount, never the ~8x overcount of raw events. Direction via AccessibilityEvent.scrollDeltaY (API 28+); on min-SDK 26/27 direction is best-effort (rejected raising min SDK for this). CALIBRATED 2026-07-22 on-device @ 200ms: slow 20/20, rapid 19/20 (single undercount = the intended mild-undercount failure mode), mixed 10/10; comments/profile/idle pauses produced zero false counts. Well within the ±2/50 exit bar — Phase 1 detection exit criterion MET. 200ms kept.
D14. Client persists counts in Room (scrollkiller.db), mirroring the server daily_counts shape: table daily_counts(date, platform, count), composite PK (date, platform). Increment is an atomic SQLite UPSERT (INSERT ... ON CONFLICT DO UPDATE SET count = count + 1) — rejected Room @Upsert (it REPLACES the row, can't express count+1). Day boundary is INTERIM device-local date (LocalDate.now(), native on min-SDK 26); server timezone-truth replaces it in Phase 3 (invariant #2 / SCHEMA.md "Day boundary") — marked with a TODO(Phase 3) in CountRepository. TodayCounter (in-memory) removed. Room codegen via KSP.
D15. Instagram reel-advance signal is androidx.viewpager.widget.ViewPager (support-lib v1) — it reports the non-zero scrollDeltaY. The inner RecyclerView fires alongside but always reports deltaY=0 (settle noise), so keying on it alone yields SAME and never counts. containerHints = [ViewPager, ViewPager2, RecyclerView]; RecyclerView retained provisionally (comments list is also a RecyclerView) — calibration (D11) showed comments-open produced zero false counts, so it stays for now; drop it if a future IG build overcounts there.
D12. Multi-platform via PlatformSpec registry from day one (packageName, containerHints, minAdvanceIntervalMs, strategy); only Instagram enabled now, YT/Snapchat/etc. specs added in Phase 2 after view-tree inspection. Emitted advances carry Platform.id matching the daily_counts.platform enum in SCHEMA.md so Room/sync stay platform-agnostic. Coupling: config XML packageNames allowlist must be widened alongside the registry.
D13. Accessibility onboarding = disclosure-first, then deep-link to Settings.ACTION_ACCESSIBILITY_SETTINGS. Android forbids apps from programmatically enabling accessibility services, so deep-linking IS the sanctioned flow; our job is making it guided and honest (invariant #5). App re-checks enabled state on onResume to flip to Home on return.
D17. Surface gating + overlay attach-once (device-found bugs, 2026-07-22). THREE changes. (a) DIAGNOSTICS ARE PERMANENT NOW: the rich node-tree dump (scrolled node's className + viewIdResourceName + full ancestor-id walk; window-state/content root class + resource-id) lives in SurfaceDiagnostics, gated behind BuildConfig.DEBUG (enabled buildConfig=true; AGP 8 defaults it off) so release builds compile it out. We kept deleting and re-writing these each calibration — no longer. Filter `adb logcat -s ScrollKiller`, lines prefixed `DIAG`. (b) SURFACE GATING: counting was gated only on package + scrolled-view class (containerHints), which fire across the whole app, not just Reels; the bubble was gated on PACKAGE ALONE. Added PlatformSpec.surfaceMarkers (viewIdResourceName substrings identifying the doom surface, e.g. clips_viewer_view_pager) + SurfaceMatcher (ancestor walk for scrolled nodes; bounded DFS root scan for window changes). NEW SINGLE SOURCE OF TRUTH: onDoomSurface (foreground is a tracked platform AND on its doom surface) — BOTH the counting gate and bubble visibility read it, so they can't disagree. Updated from scroll ancestry + window-STATE root scans; NOT from the content-changed flood (too frequent to scan per event — content-changed is DEBUG logging only). EVIDENCE-FIRST: surfaceMarkers ships EMPTY; the matcher is a pass-through when empty, so behaviour is unchanged (old package/containerHints gating) until a labeled device surface tour (feed→reels→stories→profile→DMs→reels) reveals the discriminator, which we then fill in. FALLBACK (only if IG ids turn out obfuscated/absent on the shipping build): implement the surface predicate as a window-content heuristic (like/comment/share node cluster, or fullscreen video pager) in SurfaceMatcher — heuristics only after the log proves ids unusable. Added typeWindowContentChanged to the config XML for the within-app fragment-swap surface signal. (c) OVERLAY CHURN FIX: OverlayController used to addView/removeView on every foreground-app change — the device log showed the bubble window constructed/destroyed repeatedly (VRI cycles) and the system "displaying over other apps" notification re-firing each switch. Now the view is added ONCE at onServiceConnected (ensureAttached, starting GONE; lazy re-attach from setVisible if the permission is granted later) and only toggled VISIBLE/GONE via setVisible; removeView happens solely on destroy. D16's CHEAP invariant held: the count Flow is still collected only while VISIBLE. De-dup-by-package (D16 fix) was DROPPED — entering Reels within IG is a same-package window-state-changed we must re-scan for; setDoomSurface transition-gates the show/hide so re-evaluating every window-state event is idempotent and flicker-free.
D16. Floating live-counter bubble = a draggable overlay (🧠 + today's count) drawn via SYSTEM_ALERT_WINDOW/TYPE_APPLICATION_OVERLAY, shown only while a tracked platform is foreground. OWNERSHIP: WindowManager work lives in OverlayController; the AccessibilityService stays event-only (CLAUDE.md no-God-class rule) — it just maps window-state-changed → forPackage → overlay.show(platform)/hide(). ONE SOURCE OF TRUTH: the bubble collects the SAME CountRepository.observeToday() Flow the Home screen uses — no second counter. CHEAP: TextView updated on count change only (distinctUntilChanged), no animation loop, no polling, and the Flow is collected ONLY while the bubble is visible (collection cancelled on hide) so it does zero work off-IG. OPTIONAL: show() no-ops when Settings.canDrawOverlays is false, so detection never depends on the permission; overlay is a skippable SECOND onboarding step (OverlayPermissionScreen), deep-linking Settings.ACTION_MANAGE_OVERLAY_PERMISSION, re-checked on resume, skip persisted in prefs. Tap (movement < scaledTouchSlop) opens Home; drag repositions via updateViewLayout. Plain android.view TextView, NOT Compose — a Compose overlay from a Service needs SavedStateRegistry/lifecycle plumbing and is heavier; rejected for this. SCOPE CHANGE: to hide on LEAVING a tracked app, the service must receive the window-state-changed for the app switched TO — that event belongs to the destination package, so we removed android:packageNames from accessibility_service_config.xml (now all packages) and added typeWindowStateChanged. Privacy held: window-state-changed carries only the foreground package/class name (never content), untracked scroll events are dropped by PlatformRegistry.forPackage() (now the sole gate, no XML allowlist to mirror), and canRetrieveWindowContent is still used only for reel container class names. Accessibility disclosure description updated to say we also read which app is in the foreground (invariant #5 honesty). Known edge: an IME/dialog whose package ≠ the tracked app fires window-state-changed and briefly hides the bubble — accepted for v1, on the HANDOFF manual-test checklist. FIX (device-found, 2026-07-22): window-state-changed is far noisier than assumed — our OWN overlay window + Activity fire it as com.scrollkiller, and a tracked app fires many per scroll, so hiding on every non-tracked event made the bubble tear itself down ~350ms after appearing (device log showed the 138×93 TextView overlay added then removed repeatedly). Gate now acts only on a genuine foreground-app change: skip our own package, de-dup repeats of the same foregroundPackage, and the bubble view is IMPORTANT_FOR_ACCESSIBILITY_NO so it stops emitting its own events. IME/third-package popups can still cause a brief hide (recovered on the next tracked-app event) — that residual is the accepted v1 edge.
D18. Brain-state visual = pure function of today's count, in one place: com.scrollkiller.brain.BrainState (thresholds CRACKING_AT=50, FRIED_AT=150; forCount() → HEALTHY 0..49 / CRACKING 50..149 / FRIED 150+). Arc = 🧠 green → 🤯 amber → 💀 red (accentArgb on the enum). BrainState is pure Kotlin (no Android/Compose imports) so BOTH render paths derive from it with no second mapping: Home (Compose) via Color(accentArgb), the overlay bubble (plain TextView) via accentArgb.toInt() as a background tint. CHEAP held (D16): the bubble maps count→state inside the existing distinctUntilChanged Flow collector — state changes only, no animation loop. Home keeps the count number (tinted) alongside the brain; state labels live in strings.xml (localizable), mapped in the UI layer only. Rejected emoji options: same-🧠-plus-color (too subtle) and a face-melt arc (off-motif) — chose the strongest at-a-glance degradation. Guarded by BrainStateTest (boundary table).
D19. Phase-2 block screen = full-screen overlay over the reel surface when a platform's daily count crosses its limit. Limit lives in one place: PlatformSpec.dailyLimit (default 100; user setting later). Decision is a pure function BlockPolicy.overlayFor(count, limit, gatingActive, unlocked) → BUBBLE|BLOCK (unit-tested). SAFETY GATE (user-chosen "dormant until Reels-only"): originally gatingActive = spec.surfaceMarkers.isNotEmpty(); SUPERSEDED by D24 — the caller now passes spec.blockEnabled (a verified-markers switch), so the block NEVER fires while markers are unverified — it can't cover the feed. Consequence: the block does not trigger on-device until a device tour verifies markers and blockEnabled is flipped (verified meanwhile by BlockPolicyTest + layout preview). ARCHITECTURE: the service's single doom-surface signal now carries the Platform (doomPlatform, was Boolean) and routes overlay.onSurface(platform)/offSurface(); OverlayController became the on-surface coordinator owning the bubble AND a new BlockScreenController, choosing bubble vs block from the per-platform count (CountRepository.observeToday(platform) + new DAO observeCountForDatePlatform — same Room source, a projection not a second counter; refines D16 which used the total). BLOCK WINDOW: plain android.view + inflated overlay_block.xml (NOT Compose — D16 rationale), TYPE_APPLICATION_OVERLAY, MATCH_PARENT, FOCUSABLE so it traps touches + Back; add/removeView on show/hide (a focusable window must not linger; block is low-frequency so no D17-style churn). ROBUSTNESS: re-shows idempotently when IG returns to foreground, tears down on offSurface + service destroy/unbind. NEVER A TRAP: Exit → launcher home (ACTION_MAIN/CATEGORY_HOME), Back mapped to Exit; always leaves. Unlock = TEMPORARY bypass-until-leave-surface, a placeholder the challenge result replaces next checkbox. Guilt line = random from a static string-array (guilt_pack.json loader is its own checkbox). PLAY POLICY: (1) Accessibility API policy is the existential risk — a full-screen app-blocker is the most scrutinized use; mitigation is store-side, code stays defensible (user-set limit, always exitable). (2) Overlay-over-another-app is scrutinized as disruptive — defensible because user-configured + dismissible. (3) No impersonation: unmistakably ScrollKiller's own UI (💀 + "Reels are Locked"), never mimics IG/system chrome. No new permission (SYSTEM_ALERT_WINDOW already declared).
D25. Surface-tour DEBUG tooling + IG Stories false-match fix (2026-07-23). Symptom: IG "counts all downward scrolls" — expected, that's SHADOW (D24) counting while only logging the marker check. To find the real Reels/Shorts ids: extended SurfaceDiagnostics (NOT a parallel logger in the event-only service — D17) with (a) logHierarchy(root, spec) — a downward, depth-6, 120-node-budgeted, indented tree dump ("[depth] Class — resourceId — viewId", flagging any node matching a surfaceMarker with "← MATCHES surfaceMarker"); (b) logScrollDecision(...) — a crystal-clear per-scroll "[DECISION] [DETECTED]/[IGNORED] … gating=… onSurface=… — note" line that, in SHADOW, explicitly says "counted … would be IGNORED once ENFORCED". Both gated by ReelScrollAccessibilityService.DEBUG (= BuildConfig.DEBUG, a visible toggle; compiled out of release for privacy/Play — logs only structural class/viewIdResourceName, never node text). The spec's RESOURCE_ID_MAP / findResourceIdInHierarchy map onto the existing PlatformSpec.surfaceMarkers (the per-platform known-container-id list) + SurfaceMatcher.matchedMarker/matchedMarkerId — no duplicate map that could drift from the gate. BUG FOUND writing the test: candidate marker "reel_viewer" was DROPPED from Instagram (IG Stories are internally "reels" and use reel_viewer ids → would false-match); IG now keys on "clips_viewer" only. Also tightened TikTok (dropped generic "viewpager"), broadened YouTube ("shorts_player"/"shorts_container"). SurfaceMatcherTest pins the discrimination at the pure-string level (Reels/Shorts match; feed/stories don't). Still UNVERIFIED until the on-device tour — see D24.

D20. Raw scroll_events table (Phase 2) — invariant #4 / D4 realized on-device. DB bumped v1→v2 with a hand-written migration whose CREATE matches Room's generated schema exactly (column order, AUTOINCREMENT, NOT NULL) so the on-open identity check passes. Every detected advance now DUAL-WRITES: it increments the daily_counts aggregate (the counter source of truth that powers every UI/bubble Flow) AND inserts a raw ScrollEvent(platform, appPackage, timestamp, countedAs=PlatformSpec.unitNoun). Raw events are pruned >7d (CountRepository.maybePrune, throttled to once/hour so we don't DELETE on every advance); aggregates kept forever. The aggregate stays authoritative — raw is for recent breakdown/detail and future Phase-3 sync deltas, never a second counter. Timestamp/day-key remain device-local (interim; Phase-3 server-truth, invariant #2).

D21. Bubble idle-dismiss (Phase 2, problem #3) — the bubble was surface-gated (shown the whole time on a tracked app) which felt "too early". Now it appears ONLY on real scroll activity and self-hides after a 2s quiet gap. Mechanism: the service pokes OverlayController.onScrollActivity() on each COUNTED advance (post-debounce, so not per raw event); that shows the bubble and (re)arms a single Handler postDelayed(2s) hide. The count Flow keeps the number fresh only WHILE the bubble is visible — a count change alone never re-shows a bubble the user let go idle (visibility is owned by the idle timer, the number by the Flow). Surface gating still governs Flow collection (zero work off-surface); idle governs visibility within the BUBBLE state. The block is exempt (being over the limit is not "idle"). A Settings toggle (SettingsPrefs `bubble_enabled`, default on) can disable the bubble entirely — read by the overlay before showing.

D26. Instagram Reels marker LOCKED + flipped to ENFORCED (surface tour, 2026-07-24). The tour proved a clean, non-colliding discriminator: the Reels viewer emits `srcId=clips_viewer_view_pager` → MATCH(clips_viewer), while every sibling surface is NO_MATCH — home feed (list under `swipeable_tab_view_pager`), profile grid (`clips_grid_recyclerview`), DMs (`sticky_header_list` under `bottom_sheet_container`), and Stories (`reel_viewer_*` — Stories are internally "reels", which is exactly why we key on "clips_viewer" ONLY, never "reel_viewer"; guarded by SurfaceMatcherTest). So Instagram: gating SHADOW→ENFORCED, surfaceMarkers=["clips_viewer"], counts ONLY on the reel surface. blockEnabled stays FALSE (the block is a later, separately-gated step — D19/D24). Consequence: IG feed/profile/DMs/Stories scrolling now produces 0 counted advances (ENFORCED drops off-surface). YouTube was ALSO flipped/kept ENFORCED with the tour-proven marker `reel_recycler` (narrowed from D24's candidate list — the unverified `shorts_*` guesses were dropped because the YT home feed carries a Shorts SHELF whose ids could false-match; see D28).

D27. Container-class matching is package-agnostic (simple class name), not fully-qualified. BUG the tour found: YouTube Shorts counted ZERO. The transcript showed `srcId=reel_recycler verdict=MATCH(reel_recycler) counted=false reason="android.support.v7.widget.RecyclerView is not a tracked container"` — YouTube's Shorts pager is the LEGACY support-library RecyclerView, and the old `className.endsWith("androidx.recyclerview.widget.RecyclerView")` check never matched it. Fix: PlatformSpec.matchesContainer() now compares the SIMPLE class name (substringAfterLast('.')) against simple-name hints ("RecyclerView"/"ViewPager"/"ViewPager2"), so a support-lib widget matches an AndroidX hint of the same name. All specs' containerHints changed to simple names. This class of mismatch would recur on every app that hasn't migrated to AndroidX, hence the general fix rather than adding YouTube's FQN. Guarded by PlatformRegistryTest (both android.support.v7 and androidx RecyclerView hit; ViewPager v1 vs ViewPager2 stay distinct — preserves D15). NOTE: this only gets YouTube scrolls to the debounce; whether Shorts emits a usable scroll DIRECTION (deltaY≠0) is unconfirmed — re-tour will tell; if it only ever emits SAME/deltaY=0, YT needs its own advance signal.

D28. Overlay surface state is PER-EVENT + hysteresis, NOT a whole-window scan (supersedes D17/D24's window-STATE root-scan gate for the overlay). BUG the tour found: on the YouTube HOME FEED the window verdict flipped ON_SURFACE while `srcId=browse_fragment_layout_coordinator_layout` — the feed embeds a Shorts SHELF, so a tree-wide marker scan (SurfaceMatcher.windowMatchesSurface) false-positives on the feed. Counting was already correct (it evaluates the scrolled node's own ancestry per-event); the fix makes the bubble/block visibility key off that SAME per-event surface signal. Mechanism: a scroll whose ancestry matches a marker calls onSurfaceEvent(platform) → sets the overlay "on surface" and (re)arms a SURFACE_HYSTERESIS_MS=3s timer; the timer expiring (or leaving the tracked app) drops it. Hysteresis bridges the gap between swipes so the bubble doesn't flicker; a non-matching container scroll (feed/profile/DMs) never arms it. onForegroundChanged no longer scans the window tree — it only fires clearSurface() when the foreground package is untracked (left the app). Also: TikTok and Snapchat were NOT toured, so rather than ship guessed ENFORCED markers they were set to SHADOW (they were ENFORCED-with-candidates under D24) — SHADOW logs the marker check on-device for a future tour while still counting; the tradeoff is app-wide counting (fine for TikTok ≈ all-FYP; an accepted overcount for Snapchat Chat/Stories until its tour), and blockEnabled stays false so nothing is enforced on the user. Guarded by PlatformRegistryTest (IG/YT ENFORCED, TikTok/Snap SHADOW).

D29. Overlay is attach-once + SURFACE-DRIVEN visibility; entering a surface counts the landing reel (supersedes D21's per-scroll idle-dismiss). (a) BUBBLE VISIBILITY: D21 showed the bubble on each counted scroll then removed it after a 2s idle gap; the ask was to eliminate window churn (repeated ViewRootImpl construct/destruct + re-fired "displaying over other apps"). The bubble is now VISIBLE the whole time we're on the reel surface (D28's hysteresis holds "on surface" across the between-swipe gap) and GONE on offSurface — added ONCE at onServiceConnected, only ever toggled VISIBLE/GONE, detached solely on destroy/unbind (D17's attach-once, now with no idle add/remove path at all). OverlayController.onScrollActivity/showBubbleWithIdle/idle Handler deleted; startCollecting cancels any prior collector defensively. (b) ENTRY-COUNT: the reel you LAND on fires no scroll event, so it used to count zero. onSurfaceEvent now credits one advance on entering a surface, tracked as a "session" (enteredPlatform) that ends only on leaving the tracked app (clearSurface) — NOT when hysteresis merely drops the overlay — so watching one reel a while then swiping never re-counts it; an ENTRY_GUARD_MS=3s guard stops a quick flicker out-and-back (e.g. an IME from another package) double-counting. Net: total = landing reel + swipes (off-by-one UP vs before), well within the ±2/50 bar. The block is exempt from hysteresis-hide only in that blockEnabled is still false everywhere; when enabled later, revisit whether the 3s hysteresis should also gate the block.

D24. Surface-gating modes + candidate markers (Phase 2; supersedes D17/D19's "ship empty markers" for the counting gate). Rather than leave surfaceMarkers empty (pass-through) OR blindly enforce guessed markers (which would silently ZERO detection if wrong), a per-platform GatingMode governs the counting surface gate: PASSTHROUGH (markers ignored; count on containerHints — legacy), SHADOW (markers evaluated + LOGGED as SCROLL_DETECTED/SCROLL_IGNORED/SHADOW_MISS but counting happens regardless — validate a candidate on a real device with zero regression risk), ENFORCED (count ONLY on a marker match; a wrong guess fails toward UNDERcount, never counts a home feed — so ENFORCED REQUIRES non-empty markers, asserted in PlatformRegistryTest). Instagram = SHADOW with candidate markers ["clips_viewer","reel_viewer"] so its calibrated Phase-1 detection is untouched while we confirm the Reels discriminator. New platforms = ENFORCED with candidate markers (undercount-safe). A SEPARATE blockEnabled flag (not "markers present") gates the full-screen block, and ships FALSE for every platform — so D19's "never the feed" is preserved and strengthened: the block stays dormant until a device tour verifies markers and blockEnabled is flipped per-platform. NEXT on-device: run the labeled SurfaceDiagnostics tour per platform, replace the candidate marker strings, flip IG→ENFORCED and set blockEnabled, re-run the ±2/50 calibration.

D30. Overlay bubble hide is alpha + NOT_TOUCHABLE, never View.GONE (device-found surface churn, 2026-07-24; refines D17/D29). SYMPTOM the device log showed post-D29: a BLASTBufferQueue constructor immediately followed ~3–5s later by a destructor, repeating for the whole session (VRI#2/#3/#5/#6/#7), at 138×93 / 159×93 sizes — i.e. the bubble TextView's *surface* being created and torn down every hysteresis cycle (the 3s SURFACE_HYSTERESIS_MS window), at content-width-varying sizes (🧠 N as the digit count changes). ROOT CAUSE: D29's "add once, only toggle VISIBLE/GONE" removed the addView/removeView churn but NOT the surface churn — when a WindowManager root view goes View.GONE, WindowManagerService hides the window and FREES its surface (BLASTBufferQueue); the next View.VISIBLE re-allocates a fresh one. So the on-surface→hysteresis-expiry→on-surface cycle still constructed/destructed a surface every few seconds. FIX: the bubble root now stays View.VISIBLE for the service's lifetime and "hidden" means OverlayController.setBubbleShown(false) = alpha 0 (draw-time only, no relayout to zero size → surface not freed) + FLAG_NOT_TOUCHABLE (so the transparent overlay passes touches through to the app underneath instead of eating taps in its corner); "shown" = alpha 1 + clear NOT_TOUCHABLE. Both go through updateViewLayout, which keeps the window visible, so the single surface persists across every toggle. Idempotent (bubbleShown guard skips no-op relayouts; reset on attach/destroy so a re-attach after destroy re-hides correctly). ensureAttached now creates the view alpha 0 with NOT_TOUCHABLE in the initial LayoutParams (was visibility=GONE). NOTE the surface still legitimately resizes when the digit count changes width (5→50) — that's a resize of the existing surface, not a destroy/create, and only on a real count change, not per hysteresis cycle. D16's CHEAP invariant unaffected (Flow still collected only between onSurface/offSurface).

D32. YouTube ships BETA and is BARRED from driving limits/blocks; Maturity added (2026-07-25). DECISION GATE outcome: option (b), not (a). The D31 probe round was built so three device captures (YTPROBE_SWIPE/IDLE/TAP) would pick YT's advance strategy from evidence rather than assumption; the captures were not delivered, so there is nothing to lock — and per the operator's standing rule YouTube is not permitted to block Phase 2. WHAT IS KNOWN and unchanged: YT's SURFACE is proven (`reel_recycler`, D26/D27, ENFORCED) but its ADVANCE SIGNAL is not — every Shorts event reports scrollDeltaY=0 → SAME → debounced, so the only thing that counts is D29's landing-Short entry credit. YT's number is a known severe UNDERCOUNT. MECHANISM: a new `Maturity {STABLE, BETA}` on PlatformSpec, and eligibility to block is DERIVED from it — `blocksAtLimit = blockEnabled && maturity == STABLE`. The overlay now asks `blocksAtLimit`, never the raw `blockEnabled`. Derived rather than a second independent flag ON PURPOSE: "we don't trust this count" and "this count may enforce a limit" are the same decision, and two knobs invite a future edit that sets one and forgets the other; PlatformRegistryTest asserts no BETA platform is ever block-eligible. SCOPE: TikTok and Snapchat were marked BETA too — they were never toured and run SHADOW (app-wide counting), and Snapchat is a known OVERcount (Chat/Stories/Map counted as "snaps"), which is the worst possible input to a limit. Only Instagram (calibrated 49/50, D11) is STABLE. UI: a recessive "BETA" pill next to the platform name on the Today breakdown and the Apps bars — an honesty marker ("approximate, and it can't lock your screen"), deliberately `surfaceVariant`, not an alarm colour. Counting, gating, storage and sync are UNTOUCHED — a Beta platform still counts and still shows; it just cannot enforce. TO PROMOTE YT: run the three captures, implement the supported strategy as a per-platform DetectionStrategy (IG stays DELTA_Y_FORWARD), recalibrate, set STABLE.

D33. Guilt lines move from a `<string-array>` to a bundled, remote-shaped assets/guilt_pack.json (2026-07-25) — realizes D9. WHAT WAS WRONG: `R.array.block_guilt_lines` was 4 lines picked with `.random()` — no categories, no weighting, and a ~1-in-4 chance of showing the same line twice in a row. D39. Count reads are optimistic: in-memory first, Room reconciled by max (2026-07-25). SYMPTOM: a visible beat between the swipe and the bubble's number moving, on both IG and YT. DIAGNOSIS, structural â€” the on-device timing run is Run 2 of the HANDOFF and had NOT been done when this was written (the device was PIN-locked), so this ADR records an argument, not a measurement: of the three candidate layers, (a) the debounce is not a latency source on Instagram â€” SwipeDetector resets its quiet gap on EVERY DOWN, so the first DOWN of a swipe counts immediately; (b) the bubble's own refresh is not one either â€” it updates on every distinct emission; (c) the read path was, and is the only layer that is structurally unbounded: record() was fire-and-forget into Dispatchers.IO, so the number the user saw was gated on TWO separate SQLite commits (the daily_counts upsert and the raw scroll_events insert are separate suspend DAO calls, hence separate transactions) plus Room's InvalidationTracker noticing the table changed, re-running the query on its own executor, and only then emitting. Under Instagram/YouTube foreground load that is tens to low hundreds of ms. YouTube has one ADDITIONAL detect-side cost that this change does NOT address: IDENTITY_SCAN_MIN_MS = 250ms rate-limits the content-change identity evaluation, so a real advance can sit up to 250ms before anyone looks at it. That is a rate limit, not D11 calibration, and it is left alone pending the measurement. FIX: record() now bumps an in-memory PendingCounts SYNCHRONOUSLY on the caller's thread before dispatching the write, and every read Flow merges Room's rows with it. Room stays the source of truth and the only thing that survives process death; the in-memory map is a read-through cache of writes already issued â€” nothing increments it that does not also go to Room in the same call, so it is not a second counter. RECONCILIATION is max(room, pending) per platform (TodayMerge, pure and unit-tested), which works because PendingCounts holds a running TOTAL for the day rather than a delta: both sides converge as writes land, and an emission arriving mid-flight (Room reflecting advance N while N+1 is already pending) keeps the larger, so the count is MONOTONIC within a day and can never visibly flicker backwards. Summing instead of maxing would double every count â€” the property is enforced by test. The two ways a count legitimately goes DOWN are handled by dropping the pending state, never by the merge: clearAll() resets it (LAST, after both deletes â€” resetting first would leave an advance detected mid-clear in pending with its Room row already gone, and because pending is a running total that orphan would ride along as a permanent +1 forever), and a day rollover simply no longer matches PendingCounts.date. The day key is now resolved in record() on the caller's thread rather than inside the coroutine, so both halves file the advance under the day it was DETECTED on, not the day the IO thread happened to run on.
