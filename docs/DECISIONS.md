MEASURED INSTEAD: three of the four masters (cracking/fried/guardian) were still RGB with NO ALPHA AT ALL — D36 shipped them opaque and said so — so their alpha bbox was the whole canvas, `union_trim()`'s "skip until every master has alpha" guard fired every run, and the trim had NEVER executed. FIX, in three parts. (a) BACKGROUNDS ARE NOW KEYED IN THE IMPORTER, and D36's "no auto-keying" is REVERSED on a distinction that matters: D36 refused a COLOUR key, correctly — the backgrounds are vignette-plus-glow gradients and any colour key wide enough to catch them also eats the character's dark outline. `key_background()` is not a colour key. It is a BORDER-SEEDED GEODESIC FLOOD: a pixel is background if it is reachable from the canvas border without ever crossing a neighbour-to-neighbour colour step larger than KEY_TOLERANCE. It keys on SMOOTHNESS, which is exactly the property separating a rendered gradient (neighbour deltas <=4 across the whole frame) from a cartoon silhouette (deltas of 60+). KEY_TOLERANCE=8 was picked off a STABILITY PLATEAU, not by eye: sweeping 4->48 per master, kept area sits flat at ~35% of canvas for 4..8 then jumps as the flood punches through a thin outline and drains the character's interior (fried leaks at 10, guardian at 12, cracking at 24 — the leak is visible as a brain with its pink fill gone). Flat means the segmentation found the real silhouette. 8 is the top of the range flat for EVERY master, and `assert_no_leak()` now FAILS the import if a future master leaks anyway. (b) THE UNION TRIM NOW RUNS, taking the crop from 100% x 100% of canvas to 71.7% x 87.4%. Still the union of all four alpha bboxes applied identically, for D36's reason: a per-image trim scales each state to fill its own canvas and the mascot would visibly change size when the count crossed a threshold. (c) OUTPUT IS NO LONGER SQUARE. `resize((px, px))` was safe only while the crop WAS the full square canvas — the moment the trim started working it would have stretched the character horizontally, since the union box is taller than wide. Output is emitted at the crop's natural aspect with its longer side at base_dp: 33x40dp bubble, 98x120dp hero. HERO_DP/BUBBLE_DP now mean HEIGHT, and every consumer binds height and lets width follow (Compose `Modifier.height`, ImageView `layout_height` + `adjustViewBounds`). A square box would still render correctly — both default to a fit, not a stretch — it would just reserve the empty columns this change exists to remove. The root here is a LinearLayout that stays View.VISIBLE for the service's lifetime; expanding toggles a CHILD's visibility, which RE-MEASURES the WRAP_CONTENT window — a resize of the existing surface, exactly like the digit-count changes and the nudge's maxWidth already were, not a construct/destruct pair. "One view" was never the invariant; it was D36's means to the one-window end, and it was also the thing making the mascot unfixable. D38. Overlay panel contains itself against the insets; ONE window, gravity stays TOP|START (2026-07-25). SYMPTOM: tapping the bubble expanded the breakdown panel straight off the screen edge whenever the pill had been dragged near one. ROOT CAUSE: the bubble's window is WRAP_CONTENT with FLAG_LAYOUT_NO_LIMITS. That flag is deliberate and load-bearing — it is what lets the compact pill be dragged flush against a real screen edge — but it also means WindowManager will NOT pull the window back on screen as it grows, and the panel is roughly 5x the pill's height and several times its width. Nothing in D37 repositioned the window when the shape changed, so the panel simply grew out of the display. FIX, in three pieces: (1) OverlayPlacement (pure, Android-free, unit-tested like BlockPolicy/BubbleBreakdown) decides x/y for each shape — COMPACT clamps the drag position into the usable rect; EXPANDED centres horizontally and keeps the pill's y, clamped so the bottom fits. (2) OverlayMetrics.usableBounds() resolves that rect: API 30+ from currentWindowMetrics + getInsetsIgnoringVisibility(systemBars | displayCutout), API 26-29 from the real display size minus the framework's status_bar_height/navigation_bar_height dimens. Insets IGNORING visibility, not live insets, because the overlay sits on a full-screen video player that hides the bars — live insets there are zero, so a panel placed against them would be under the status bar the moment the bars animate back. Never cached: rotation, unfolding and multi-window all move it. (3) OverlayController.applyPlacement() measures the view against that rect (the window is WRAP_CONTENT, so its size is only knowable by measuring, and measuring AFTER the layout pass would show one frame in the wrong place then jump) and writes params.x/y. WHY CENTRED and not anchored to the bubble: an anchored panel at the right edge is either half off-screen or shoved inward by a distance that varies with the panel's width, which reads as the panel moving at random; centred is one predictable place regardless of where the pill was parked. WHY gravity stays TOP|START in BOTH shapes: it makes params.x/y the window's absolute top-left, so the arithmetic never changes origin between shapes. CENTER_HORIZONTAL would express the expanded state more directly but would make x mean "offset from centre" there and "offset from the left edge" when compact — two meanings for one field the drag handler also writes. Compact drag position is tracked SEPARATELY (compactX/compactY) from params.x/y, because while expanded the latter hold the centred position and collapsing has to return the pill to where the user left it. Drag stores the CLAMPED position, not the raw finger position, so overshoot past an edge does not leave a dead zone or anchor the next expand off-screen. A drag COLLAPSES an open panel first: the panel's position is centred by definition, so dragging it would either fight the centring or move it away from where the user learned to expect it. Rotation/fold/multi-window handled via BubbleView.onConfigurationChanged -> controller (posted, so the view has re-laid-out for the new config before we measure). Degenerate case (view larger than the usable rect — huge font scale, tiny cover display): pin to left/top and let the far edge overflow, so the total and first bars stay visible. NO CHURN: every path is updateViewLayout on the already-attached window, skipped entirely when x/y are already right, so D30's single-surface property holds — expand/collapse/drag/rotate must still show one BLASTBufferQueue construct and then resizes only.

D39. Count reads are optimistic: in-memory first, Room reconciled by max (2026-07-25). SYMPTOM: a visible beat between the swipe and the bubble's number moving, on both IG and YT. DIAGNOSIS, structural — the on-device timing run is Run 2 of the HANDOFF and had NOT been done when this was written (the device was PIN-locked), so this ADR records an argument, not a measurement: of the three candidate layers, (a) the debounce is not a latency source on Instagram — SwipeDetector resets its quiet gap on EVERY DOWN, so the first DOWN of a swipe counts immediately; (b) the bubble's own refresh is not one either — it updates on every distinct emission; (c) the read path was, and is the only layer that is structurally unbounded: record() was fire-and-forget into Dispatchers.IO, so the number the user saw was gated on TWO separate SQLite commits (the daily_counts upsert and the raw scroll_events insert are separate suspend DAO calls, hence separate transactions) plus Room's InvalidationTracker noticing the table changed, re-running the query on its own executor, and only then emitting. Under Instagram/YouTube foreground load that is tens to low hundreds of ms. YouTube has one ADDITIONAL detect-side cost that this change does NOT address: IDENTITY_SCAN_MIN_MS = 250ms rate-limits the content-change identity evaluation, so a real advance can sit up to 250ms before anyone looks at it. That is a rate limit, not D11 calibration, and it is left alone pending the measurement. FIX: record() now bumps an in-memory PendingCounts SYNCHRONOUSLY on the caller's thread before dispatching the write, and every read Flow merges Room's rows with it. Room stays the source of truth and the only thing that survives process death; the in-memory map is a read-through cache of writes already issued — nothing increments it that does not also go to Room in the same call, so it is not a second counter. RECONCILIATION is max(room, pending) per platform (TodayMerge, pure and unit-tested), which works because PendingCounts holds a running TOTAL for the day rather than a delta: both sides converge as writes land, and an emission arriving mid-flight (Room reflecting advance N while N+1 is already pending) keeps the larger, so the count is MONOTONIC within a day and can never visibly flicker backwards. Summing instead of maxing would double every count — the property is enforced by test. The two ways a count legitimately goes DOWN are handled by dropping the pending state, never by the merge: clearAll() resets it (LAST, after both deletes — resetting first would leave an advance detected mid-clear in pending with its Room row already gone, and because pending is a running total that orphan would ride along as a permanent +1 forever), and a day rollover simply no longer matches PendingCounts.date. The day key is now resolved in record() on the caller's thread rather than inside the coroutine, so both halves file the advance under the day it was DETECTED on, not the day the IO thread happened to run on. ALL read Flows are now projections of observeTodaySummary() — observeTodayTotal, observeToday(platform), and the dashboard's breakdown (observeBreakdown() deleted; DashboardViewModel shares one stateIn for both tabs) — so no surface can miss the optimistic path and show a number another surface disagrees with, which is D35's invariant restated. Instrumentation: DEBUG-only CountLatency stamps DETECT -> OPTIMISTIC -> PERSISTED -> EMITTED -> RENDERED and prints one LATENCY line per advance, so the layers can be attributed instead of argued about. One open trace at a time (a hand-driven diagnostic, not a metrics system — a map keyed by sequence would mean threading an id through TodaySummary purely to serve debug builds); a superseded trace still logs. Zero cost in release.

D41. Guilt lines escalate by INTENSITY TIER off the daily total, and say nothing below 50 (2026-07-27). BELOW 50 THE APP SAYS NOTHING AT ALL — GuiltTier.forCount returns null and every surface renders no line (Home shows only the count and mascot; the bubble's panel hides its line row). That silence is the load-bearing part: fifty short videos is a normal amount of scrolling, and an app that comments on it has cried wolf by the time the number actually matters. Null rather than a fifth SILENT enum entry, because "there is no line" is genuinely the absence of a tier, and making it a value invites a surface to look up a pool for it and render whatever falls out of the fallback chain. Intensity is a BAND (intensityFloor..intensityCeiling, equal today) rather than a single number so a future pack can overlap tiers without touching selection code. An empty band widens DOWNWARD to the nearest lower intensity present — a pack thin at the top shows a tier-3 line at 160, which is merely underwhelming, whereas widening upward would show an EXTREME line to someone at 52, which is exactly the failure the tiers exist to prevent; upward is reachable only for a pack with nothing at or below the tier ceiling, and a test over the bundled asset proves it never fires. Also collapsed GuiltSurface from three entries to two: `bubble_cracking`/`bubble_fried` encoded escalation as separate SURFACES, which is now the wrong axis (escalation applies to every surface at once), leaving the genuine distinction of AMBIENT (what the app is currently saying) vs BLOCK (its own moment). D42. Daily freshness comes from a deterministic DECK, not from new content (2026-07-27). GuiltRotation already guaranteed variety within a session (no repeat until the pool cycles). What it could not give was variety across DAYS: with a fixed pool, day three is day one reshuffled, and the guilt stops landing roughly when the user can predict it. The obvious fix — author new lines daily — is a content treadmill nobody runs. So each day the eligible pool is narrowed to a DECK: 60% of the pool (floor 6), chosen by a seeded shuffle over FNV-1a(dayKey|installId). Pure function of (pool, day, install); nothing is persisted and nothing needs to be — two surfaces asking on the same day get the same deck, a process restart mid-day does not shift it, and a test can ask for any date. The install id (a locally-generated UUID in SettingsPrefs, NOT a device identifier — it is a rotation seed, not an identity) is mixed in so two people do not rotate in lockstep; without it a shared joke about the app's Monday line would be a real thing. FNV-1a hand-rolled rather than String.hashCode because this seed decides what content a user sees for the life of the install, and leaning on a platform hash means a future ART change silently reshuffles everyone. Lines that sat out yesterday are PRIORITISED into today's deck (stable partition, so today's shuffle order survives within each group); deprioritised rather than banned, since a two-day ban on a small pool would empty the deck. The reference set is yesterday's BASE DRAW (the pre-rotation shuffle), not yesterday's final deck — the latter is defined in terms of the day before it and so on back to the install, i.e. circular, and no finite cut of that chain is exact. That is a strictly weaker guarantee than "yesterday's deck", so it is the one written down and tested, alongside a separate test asserting the deck still churns against yesterday's REAL deck — otherwise a future rule change could satisfy its own definition while leaving the content static. The pool is canonicalised (sorted by id) before shuffling so reordering guilt_pack.json — an edit with no intent behind it — cannot reshuffle every user's rotation. Scales without code change: the deck is a fraction, so the pack can grow to hundreds of lines. Ships 72 lines, ~18 per tier, which is the minimum at which a 60% deck visibly rotates (asserted in tests).

So firing became a repeating cadence driven by the daily total, on a NEW axis kept deliberately separate from intensity. GuiltTier still decides how HARD a line hits (which pool it is drawn from); GuiltCadence now decides how OFTEN one arrives. Neither file knows the other's numbers, so "the app gets meaner" and "the app gets more insistent" stay tunable apart — and they compound at the top by design: at 800 reels the lines are both the most savage the pack has and as frequent as the display allows. The schedule is one ordered table (GuiltCadence.SCHEDULE) and nothing else reads a threshold or an interval directly: from 100 every 10 scrolls, 250 every 7, 320 every 5, 400 every 4, 500 every 3, 600 every 2, 800+ every scroll. Declared ascending because that is how it is discussed and reviewed; the descending scan intervalFor() needs is derived rather than being a second ordering to keep in step (same shape as GuiltTier). Below 100 intervalFor returns NULL rather than a sentinel — "this count does not repeat" is the absence of an interval, and Int.MAX_VALUE would silently become a real cadence the day someone's count got large enough. Fifty and seventy therefore keep D41's behaviour exactly: they fire on the TIER CROSSING and then go quiet, because a repeating nag at 55 reels is the opposite of the design. Crossings still fire at 100 and 150 too, so an escalation announces itself instead of waiting out an interval it happens to land mid-way through. WHEN is GuiltFiring, a pure stateful class fed every count emission; the schedule itself is a lookup table but this is where every subtle edge lives, so it is separately unit-tested (25 assertions across baselining, pending suppression, rollover and clears). Three of those edges are load-bearing. (1) BASELINING: the first observation of a day or of a process records the count and fires nothing, because otherwise walking into Reels at 300 reads as `300 - 0 >= 7` and fires instantly, and again on every tab back in. The baseline PERSISTS across surface exits — OverlayController no longer resets anything in offSurface() — which is what makes re-entering at an unchanged count silent: the cadence measures SCROLLS, not arrivals, and time alone never fires. (2) A COUNT THAT GOES BACKWARDS within a day means a data clear, so it re-baselines rather than being treated as progress; otherwise the next scroll reads as hundreds at once and fires immediately, at a tier the user is no longer in. Same path handles the day rollover, which resets the cadence with the count per the daily-rollover rule. (3) SUPPRESSION IS PENDING, NOT DROPPED: when the display gap blocks a fire, no state is consumed, so the interval stays due and the tier stays un-fired and the line goes out on the first emission after the gap elapses. Dropping it would mean the faster you scroll the fewer lines you see — exactly backwards — and it is also what stops a gapped TIER CROSSING from being swallowed entirely. THE DISPLAY GAP is 5.5s (GuiltCadence.MIN_GAP_MS), and it is deliberately much larger than the ~1.5s the brief suggested. The schedule governs ELIGIBILITY in scrolls; the gap governs DISPLAY in seconds, and at the top of the curve those genuinely disagree — at 800+ every scroll is eligible and a fast scroller produces one about every second. A gap shorter than the 4s a line is displayed for means each line is overwritten before it can be read, so at the exact moment the app is trying hardest to be heard nothing on screen is legible; worse, the pill never collapses and the bubble stops being a counter at all. The counter is the product and the lines are commentary on it, so commentary must not evict the thing it is commenting on. 5.5s is therefore the full 4s display plus a guaranteed 1.5s counter-only window, derived from its two parts rather than written as a literal so the guarantee survives anyone re-tuning the display duration — which is also why DISPLAY_MS moved out of OverlayController and into GuiltCadence beside it, since split across two files the two numbers drift and the guarantee quietly stops holding. Practical ceiling at 800+ is ~11 lines a minute, which is already relentless. The clock is SystemClock.elapsedRealtime, not wall time: the gap is a DURATION, and a user changing the device date — which the handoff explicitly asks a tester to do for the daily-rotation run — must not be able to jam it open or shut. The day key stays wall-clock-derived, correctly, because it is a date. FIRING IS THE OVERLAY'S ALONE (GuiltLines.fire), even though Home also observes the count: a fire is something you SHOW, the bubble's nudge is what showing it means, and two callers would race for the same fire with the bubble silently losing a nudge whenever the ViewModel won — which is reachable, because stateIn's WhileSubscribed(5s) keeps Home collecting for five seconds after the user switches to Instagram. Home reads current() instead, which returns whatever fire() last pinned, so "Home shows the latest fired line" falls out of the existing pin rather than needing a second mechanism. current() keeps its lazy draw for the case where the overlay never runs at all (bubble switched off, or the overlay permission never granted) — without it Home would show a stale line forever. One consequence, accepted: if a tier crossing is gap-suppressed, current() will lazily repin a correct-tier line for the panel immediately and fire() will then draw a second one when the gap elapses. Both are current-tier, the one-line-at-a-moment invariant holds throughout, and the panel updating instantly on a crossing is arguably the better behaviour anyway. CONTENT SELECTION IS UNTOUCHED: fire() calls the same draw path as everything else, so a rapid-fire line is still tier-correct, still comes from today's deck, and still cannot repeat back-to-back — the no-repeat rotation is what keeps "every scroll" from degenerating into the same three lines. NO WINDOW CHURN: showNudge is text on the already-attached view plus one re-placement, exactly like a digit-count change (D30/D38 hold), which matters far more now that it runs dozens of times a day instead of four. No detection change, no intensity-threshold change; GuiltThresholds' 50/70/100/150 and GuiltCadence's table are separate tables that happen to share two numbers.

D47. Counts are a TOKEN, no-repeat is a WEEK, and the pack is too small — say so (2026-07-27). Three things, one root cause: D46 made lines repeat all day, and content written for a single moment does not survive that. (a) THE COUNT-IN-TEXT BUG. Lines were authored with the number baked in, so at 312 scrolls the app announced "One-fifty" while its own counter, an inch away, read 312. A line may now reference the count exactly one way: a {count} token substituted at render time, with {minutes} alongside it because a duration claim ("that is half an hour") is the same bug in different units — derived from the count through TimeEstimate and equally wrong at the wrong count. Without {minutes} the eight strongest existential lines would have had to be deleted rather than fixed. Rendering happens on EVERY render, not once at fire time: a line pinned at 310 and still on screen at 314 reads 314, because the alternative is the app contradicting the number beside it, which is the entire bug. THE GUARD IS THE INTERESTING PART. The obvious rule — "no bare integers" — would have passed the entire broken pack: every single offender was spelled out (Fifty, Seventy, A hundred, One-fifty). The brief asked for a bare-integer check; a bare-integer check would have caught nothing. So GuiltText.offendingNumber bans digits AND scale words (twenty…ninety, hundred, thousand, century, dozen) AND time units not preceded by {minutes}. Small words (one, two, three…) are deliberately allowed, because in this pack they are always idiomatic — "one more", "one of them", "one full lecture" — and a guard that fires on those gets switched off within a week. The guard runs in two places for two different failure modes: the PARSER drops an offending line (a bad remote pack degrades, per D33's tolerate-and-drop posture, rather than shipping the bug), and a TEST fails the build on the bundled pack (our own content silently shrinking is not an acceptable outcome). It found three offenders my own manual audit had missed — "Century scored", "another hour between friends", and one false positive ("any minute now") which was rewritten rather than exempted: a blunt guard everyone trusts beats a clever one with an exception list. 27 of 72 lines were rewritten; 26 now carry a token. (b) SEVEN-DAY NO-REPEAT. GuiltRotation's no-repeat was session-scoped and pool-cycle-based, which at the D46 cadence means a pool cycles in minutes — "no repeat" had quietly stopped meaning anything. It is now a rolling 7-day window over a persisted guilt_shown table (lineId PK, shownAt wall-clock millis; DB v2→v3, migration SQL matched byte-for-byte against Room's exported 3.json). LAST shown, not a log: the only questions asked are "inside the window?" and "which is stalest?", both answerable from one row per line, and a full log would grow without bound at the top of the cadence for no extra information. The selector must answer synchronously on a render path inside an AccessibilityService, so Room is read ONCE at process start into an in-memory GuiltHistory and written through afterwards. Between process start and that load landing the window is briefly unenforced — a deliberate, bounded hole, since the alternative is blocking a render on a database read; GuiltHistory.seed MERGES on max rather than overwriting, so a line shown during the gap does not get its timestamp dragged backwards by what disk said. Wall clock here, monotonic for D46's display gap: the history is persisted and must survive reboots, the gap is a duration and must survive clock changes. Both now travel in one GuiltNow so the distinction is visible at every call site instead of being two Longs nobody can tell apart. (c) RECONCILING WITH THE DAILY DECK (D42). D42 narrowed each tier's pool to ~60% a day to manufacture freshness. The 7-day exclusion delivers that property far more strongly — seen means excluded, not deprioritised — and the two cannot both narrow: 60% of a pool that has already had a week of shown lines removed is how a healthy pack reaches the exhaustion fallback. So the narrowing is DELETED and the seed survives as an ORDERING. Exclusion is the hard rule; the daily seed is the tiebreak. GuiltDeck.forDay/baseDraw/deckSize are gone rather than left vestigial, because a narrowing function nothing calls is a trap for the next reader. In the common path the order is inert (GuiltRotation draws by weight and ignores it); it earns its keep in the fallback, where many lines tie at "shown today" and something has to break the tie deterministically and differently per install. (d) GRACEFUL, LOUD EXHAUSTION. When a tier's whole pool is inside the window, the draw falls back to the least-recently-shown QUARTER of it — a slice, not the sorted pool, because the weighted draw that follows ignores order and would happily pick the line from a minute ago. Never-shown lines sort first (lastShownAt returns Long.MIN_VALUE, not null). The fallback fires an onPoolExhausted callback — a callback, not a log call, so GuiltSelector stays Android-free and a test can assert it — which GuiltLines turns into a warning that quotes GuiltPoolMath: "tier EXTREME has 18 lines and every one was shown in the last 7d. At 400 scrolls/day this tier needs ~434. EXPAND THIS TIER." Naming the target rather than just complaining is the difference between a log line someone acts on and one they filter out. (e) THE POOL-SIZE MATH, WHICH IS THE UNCOMFORTABLE PART. GuiltPoolMath derives consumption by running the REAL GuiltFiring over a simulated day — not a reimplementation, so it cannot drift from what ships, and it re-derives itself if the cadence or the tier thresholds are ever retuned. The finding: tier 4 absorbs essentially the entire cadence, because it starts at 150 and never ends. Fires/day — T1: 1, T2: 1, T3: 5, T4: 1 at 150 scrolls, 18 at 300, 62 at 500, 196 at 800. Tiers 1 and 2 fire exactly ONCE a day by construction (they sit below the schedule's first row, so only their tier crossing fires), so 7 lines each sustains any user forever and the shipped 18 is ample. Tier 3 spans exactly 100–149 at every 10, so it is permanently capped at 5/day: 35 lines sustains a week for ANY user, and the shipped 18 does not — a real but small and FINITE shortfall. Tier 4 is unbounded: 126 lines for a 300-scroll/day user, 434 for 500, 1,372 for 800. Against a shipped pool of 18. The recommendation is therefore deliberately not "author 1,372 lines": target 40 for tier 3 (closes it permanently), 150–200 for tier 4 (sustains the realistic heavy user at ~300/day, an 8–11× expansion), and accept the least-recently-shown fallback above that with the log telling us who is hitting it. The alternative worth considering, and explicitly NOT taken this session because D46 was to stay intact, is to flatten the cadence above ~500 — the top of the schedule consumes content faster than any human can write it, and a 2-scroll interval at 600 is a product choice that could be revisited more cheaply than a thousand lines can be authored. The numbers are pinned in GuiltPoolMathTest, including one test that asserts the CURRENT inadequate coverage rather than the target, so it passes today and fails the moment the pack grows — at which point the numbers here get updated with it. The build is deliberately NOT failed on the shortfall: blocking every unrelated change until a thousand lines exist would be the wrong lever.

D48. The cadence PLATEAUS at every 5 scrolls, and the pool targets become numbers the build tracks (2026-07-27). D47 ended by naming two levers for the tier-4 content shortfall and taking neither: expand the pack, or flatten the top of the cadence. Both are now taken, and the order matters — flattening first changes what expanding has to cost, so sizing the content bill before capping the cadence would have sized the wrong bill. (a) THE FLATTENING. GuiltCadence.SCHEDULE loses its 400→every-4, 500→every-3, 600→every-2 and 800→every-scroll rows. It is now three rows: 100→every 10, 250→every 7, 320→every 5, and every 5 from there to infinity. FLOOR_SCROLLS = 5 names the plateau and GuiltCadenceTest asserts intervalFor never returns less than it at ANY count, so a future tuning row cannot quietly reintroduce a bill the pack cannot pay. The rows are DELETED rather than clamped to the floor: a row whose interval the floor would override is a row that lies to the next reader about what the app does, and this codebase's whole convention is that the table IS the curve. Note what this necessarily gives up — the instruction was to keep 100→10 through 500→3 and cap only above that, but 400→4 and 500→3 are THEMSELVES faster than every 5, so "never fires faster than every 5 even at 800+" and "keep the 400 and 500 rows" cannot both hold. The stated invariant won, because the alternative reading (500→3 kept, a 600→5 row added) is non-monotone: the app would nag every 3 scrolls at 550 and every 5 at 650, which contradicts D46's founding principle that the further in you are the more present the app should be, and would have required deleting the well-formedness test that encodes it. The cost of the reading taken is that a 400–500/day user now gets a line every 5 scrolls instead of every 4 or 3. The display gap was already the binding constraint for anyone scrolling fast (MIN_GAP_MS caps the SHOWN rate at ~11/minute regardless of eligibility), so the product loss at the top is smaller than the table suggests; the content saving is not. (b) WHAT IT BOUGHT, derived by GuiltPoolMath running the real GuiltFiring, not by hand. Tier 4 fires/day: 1 at 150 scrolls, 18 at 300, 57 at 500 (was 62), 117 at 800 (was 196). Seven-day pool need: 7, 126, 399 (was 434), 819 (was 1,372). Tiers 1-3 are UNCHANGED by the flattening and always were going to be — tiers 1 and 2 sit below the schedule's first row and fire once each per day on their tier crossing forever, and tier 3 spans exactly 100-149 at every 10, so it is capped at 5/day whatever the top of the curve does. The honest reading of these numbers is that flattening does not rescue the ceiling: 819 lines is no more writable than 1,372. What it does is make the MIDDLE of the curve affordable, which is where the users are. That is the finding, and the ADR states it rather than presenting a 40% cut as a solution. (c) THE TARGETS, as code. GuiltPoolMath.EXPANSION_TARGETS is T1 18, T2 18, T3 40, T4 150. They live beside the math that justifies them rather than in this file, because a target in an ADR is a sentence nobody re-reads and a target in the object the exhaustion log already quotes is a number that shows up in logcat. Each is a choice about WHO is covered, not about what the cadence demands: T1/T2 are already met and permanently so; T3's 40 CLOSES the tier — consumption is capped at 5/day by the band's finite width, so 35 sustains a week for any user at any rate and 40 leaves room, making it the cheapest complete win in the pack at 22 lines; T4's 150 sustains a 7-day no-repeat for ~320 scrolls/day and explicitly does NOT chase 800/day, which would cost 819. (d) THE BUILD TRACKS THE GAP, NOT THE GOAL. GuiltPoolMathTest gains two tests. One asserts the targets are the right size FOR THE CADENCE — 40 must exceed tier 3's permanent ceiling, 150 must cover 300-350 scrolls/day — so a future cadence edit that invalidates a target fails there rather than being discovered when someone starts writing. The other asserts the shipped pack is short in EXACTLY tiers 3 and 4, with a message that prints every tier's lines/target and what it currently sustains. That is green today and red the day the content lands, which is the same posture D47 chose and for the same reason: failing the build on "not written yet" would block every unrelated change until a content task nobody is mid-way through completes. The content expansion is deliberately NOT done in this session and is not a blocker for anything — it is a parallel task, with community submissions as the long-term tier-4 supply. (e) THE LOG NAMES BOTH NUMBERS NOW. The exhaustion warning was already loud (D47) and stays loud; it now quotes the committed target alongside the rate-derived need: "tier EXTREME has 18 lines ... at 400 scrolls/day this tier needs ~259 lines to sustain no-repeat (committed target: 150)". Once the target is met those two diverge on purpose, and the divergence is the message — a warning at 18/150 means "write more", a warning at 150/150 means "this user is past what we chose to cover", and only the second one is information about users rather than about us. (f) FALLOUT, all in tests. GuiltFiringTest's "every single scroll from 800" becomes "still every 5 at 800"; the two display-gap tests baselined at 800 and stepped by 1, which under the plateau is no longer even eligible, so they step by 5 and the burst test runs 60 scrolls instead of 20 to keep the gap as the thing under test rather than the interval. Separately, GuiltSelectorTest's least-recently-shown fallback test was found to be FLAKY (~1 run in 3) and pre-existing, not caused by this change: it seeded 3 stale lines against a fallback slice of ceil(18 × 0.25) = 5, so two fresh lines sat inside the slice and the weighted draw picked one perfectly legally. Fixed by seeding a full staleness gradient and asserting the draw lands in the older HALF — computed BEFORE the draw, since drawing RECORDS and would otherwise make the chosen line the freshest thing in its own history — rather than mirroring the private slice fraction, which would break on a tuning change that is not a defect. No detection change, no tier/intensity change, no pack change.

D49. The block goes live — on Instagram, on the user's own limit, and always exitable (2026-07-27). The app has counted, nagged and guilted since Phase 1 and has never once stopped anyone. The machinery to do it has existed since D19 — BlockScreenController, overlay_block.xml, the GUARDIAN mascot, BlockPolicy — and has been structurally dormant the whole time, because blockEnabled shipped false on every platform and blocksAtLimit therefore never returned true. That dormancy was correct and deliberate: D19/D24 refused to blackout a screen on markers nobody had verified on a device, and D32 refused to enforce on a count nobody had calibrated. Both preconditions are now met for Instagram AND ONLY INSTAGRAM, so the flip is one platform wide. (a) WHY IG AND NOTHING ELSE. Two independent things have to be true and they guard different failure modes. The surface marker `clips_viewer` was device-toured on 2026-07-24 (D26) and IG is GatingMode.ENFORCED, which is what makes "the block can land only on the reel player" a property of the code rather than a hope — every sibling surface was NO_MATCH, and the near-miss is real: Stories are internally "reels" and emit reel_viewer_*, so a marker of "reel_viewer" or a broadened "reel" would put a full-screen block over someone's Stories. That exact string is now pinned in PlatformRegistryTest. Separately the count is calibrated 49/50 (D11), which is why IG is Maturity.STABLE and therefore why blocksAtLimit — not the raw blockEnabled — is true. YouTube is the instructive case: its surface IS proven (D26) and its advance strategy IS resolved (D34), but it has never been calibrated, so it stays BETA and cannot block however anyone edits blockEnabled. TikTok and Snapchat were never toured at all, and Snapchat is a known OVERcount, which is the worst possible input to a limit. Three tests hold this shut: exactly one platform may have blocksAtLimit and it is Instagram by name; any platform with blockEnabled must be ENFORCED with non-empty markers; and the three unmeasured platforms are asserted false on BOTH flags positively, so promoting one requires coming here and meaning it. (b) THE LIMIT IS THE USER'S. PlatformSpec.dailyLimit is demoted to a DEFAULT; SettingsPrefs.dailyLimit(context, platform) is what the overlay reads, and it is read per count emission rather than cached, because a limit that took effect "next time you open Instagram" is a setting that looks broken. Storage is PER-PLATFORM even though one platform can block today: "100 reels" and "100 Shorts" are different commitments, and a single shared budget would mean promoting YouTube later silently halves everyone's Instagram allowance — per-platform now costs one string concatenation and removes that migration entirely. Every tunable number lives in BlockLimits (default 100, range 20–300, step 10, grace 5 minutes) rather than as literals at the four call sites that need them — the overlay reads the limit, Settings writes it, PlatformSpec defaults it and a button prints the grace, and four homes for one product number is exactly how a slider ends up offering a range the policy does not honour. The Settings slider is rendered once per blocksAtLimit platform rather than as a hardcoded Instagram row, so a BETA platform can never show a limit control it would not honour. clampLimit runs on the way IN to storage and on the way OUT, since a value can arrive from a restored backup or a build with a different range. Writing it turned up a real bug: snapping adds half a step before dividing, so a garbage Int.MAX_VALUE overflowed to negative and clamped to the MINIMUM limit — the one wrong answer that covers someone's screen 280 reels early. Range is now coerced BEFORE snapping, which cannot overflow and stays in range because both ends are themselves on-step. (c) "5 MORE MINUTES", AND WHY IT IS PERSISTED. D19's Unlock was a bypass held in memory and reset on leaving the surface. It is replaced by a timed reprieve: an absolute wall-clock deadline written to SharedPreferences per platform. Persisted because the app made a promise measured in minutes, and a reprieve that a service restart or a crash silently revokes is a promise broken at the worst possible moment; surviving app-exit because a user who steps out to answer a message inside their own five minutes has not used them up. Wall clock rather than elapsedRealtime, the same split D47 drew: persisted state that must survive a reboot is dated, and only a duration measured inside one process (D46's display gap) may use the monotonic clock. The accepted consequence is that winding the device clock BACKWARDS extends the user's own reprieve — a self-harm cheat, not a way to get trapped, and defending it would cost more than it is worth. NOTHING SCHEDULES THE RE-BLOCK: there is no timer, because the render path already compares the deadline against now on every count emission, so the next reel after the grace lapses blocks and no reel before it does. A timer would be a second source of truth for the same instant and would have to be cancelled correctly on every exit path. The boundary belongs to the block (nowMs >= graceUntilMs re-blocks), so five minutes means five, and 0 reads as "expired" rather than needing a separate has-a-reprieve flag. (d) THE BUG THAT WOULD HAVE MADE THE FEATURE LOOK BROKEN. The overlay's surface state is kept alive by a 3-second hysteresis armed by each marker-matched scroll (D28). Once a full-screen block covers Instagram the user CANNOT scroll, so nothing re-arms it — and Instagram is DELTA_Y_FORWARD, so its content-changed path does not re-arm either. The plain runnable therefore fired, dropped the doom surface, called offSurface(), and tore the block down three seconds after raising it, handing the reels straight back. It now RE-POSTS itself while overlay.isBlocking instead of expiring: a showing block means the user is by construction still on the surface, and re-posting rather than simply returning means the normal 3-second behaviour resumes by itself the moment the block comes down, with nothing having to remember to re-arm it. This is deliberately NOT a guard inside offSurface(): that method is also the path that runs when the user LEAVES the tracked app, and a guard there would be a way for the block to outlive leaving Instagram — the opposite of invariant 6. (e) ALWAYS EXITABLE IS NOW AN INVARIANT, AND IT CHANGED THE CODE. Written into CLAUDE.md as invariant 6 rather than left as a class comment, because from this session the app can cover another app's screen. Three concrete consequences. Exit DISMISSES BEFORE starting the launcher intent and does not depend on it succeeding: on a locked-down device where the intent throws, the user must be looking at Instagram rather than at an overlay that would not go away. The Back listener stays on the ROOT with the root focused — a ViewGroup's OnKeyListener only runs when the ViewGroup itself is the focused view, so the obvious "give Exit initial focus for TalkBack" change would have silently stopped Back being handled at all, and an unhandled Back on a WindowManager-added view does nothing, which is precisely the trap. TalkBack order is solved in the LAYOUT instead: Exit moved above "5 more minutes", so traversal reaches the way out before the way to keep scrolling, and the visual hierarchy now matches what an anti-doomscroll app should be nudging toward. Back also consumes ACTION_DOWN as well as ACTION_UP so the framework never sees a half-handled Back. (f) THE WINDOW MODEL: TWO WINDOWS, NOT ONE. The instruction was to make the block the bubble window escalating — attach-once, no add/remove ever. It is deliberately not done that way, and the alternative was put to the user before any code was written. The bubble window is NOT_FOCUSABLE and passes touches through; the block must be FOCUSABLE and trap them. Escalating one window means toggling exactly that flag on the window the user spends all day underneath, and a failure mid-toggle leaves a full-screen focusable overlay up with no block UI on it — an input trap, which is the one outcome invariant 6 exists to prevent. Two windows are failure-isolated: a block that fails to add leaves the bubble untouched, and the bubble can never become focusable at all. D30's no-churn property is not in tension here, and the existing D19 comment already said why — that concern was a construct/destruct cycle every 3–5 seconds on the hysteresis timer, whereas a block is raised and dismissed on the order of twice a day. The bubble window remains attach-once and untouched. (g) THE BLOCK LINE IS DRAWN ONCE PER EPISODE. render() runs on every count emission, and the naive GuiltLines.block(context, count) there would draw a NEW line each time and stamp each one into the 7-day history — an unbroken block would eat a tier's whole pool in a handful of emissions and land the app in D47's exhaustion fallback for the rest of the week, for lines nobody ever finished reading. So GuiltLines now holds a block EPISODE: the draw is pinned for the life of one block and released by endBlockEpisode(), while the RENDER is not — the raw text is re-substituted on every call so {count} and {minutes} stay live even though the sentence does not change. Same split as the ambient pin and for the same reason: a line must never contradict the number beside it. The episode is released on exit, on the reprieve, on leaving the surface, on a locale change (the held line is in a language the user just declined) and on destroy — all through one hideBlock() helper, so a dismissal path cannot forget. (h) PLAY POLICY, the whole list, because this is the highest-risk combination in the codebase — a full-screen overlay over another app, driven by an AccessibilityService. (1) The Accessibility API policy requires the DECLARED function to match the actual one, and accessibility_service_description said only that the service counts. It now states that it also shows a full-screen block, that the user can always leave it, and that they can always ask for a few more minutes. The in-app disclosure (invariant 5) already covered blocking; the system-facing description did not, and that is the one Play reads. (2) EXIT USES A LAUNCHER INTENT AND MUST NOT BECOME performGlobalAction(GLOBAL_ACTION_HOME). Driving another app's navigation through the accessibility API is a materially stronger "misuse of the Accessibility API" signal than starting the launcher, for an outcome the user cannot tell apart — recorded here so nobody simplifies it later. (3) No impersonation: the block is unmistakably ScrollKiller's own screen, own mascot, own colours, no Instagram mark; D44 already drew that line. (4) Play removes apps that make a device unusable, and invariant 6 plus the acceptance runs are the mitigation — the runs are what make it real rather than asserted, which is why HANDOFF puts the Exit run FIRST, before a block is ever deliberately raised. (5) KNOWN LIMITATION, not a violation: on Android 12+ any app may call setHideOverlayWindows(true) and the system will hide our TYPE_APPLICATION_OVERLAY, so if Instagram ever does the block silently will not appear. That argues against ever marketing this as unbypassable. (6) Android filters touches on overlays sitting over system permission dialogs — correct behaviour, worth knowing during testing when a taps-do-nothing moment shows up. (7) Android 13+ gates accessibility for sideloaded builds behind "Allow restricted settings" — test friction, in HANDOFF. (i) ONE DELIBERATE ASYMMETRY: the block does NOT respect the bubble's Settings toggle. Switching the passive counter off is a statement about a pill over your video, not a withdrawal of the daily limit you set. The overlay PERMISSION still gates both, so a user who refuses it gets neither, and detection plus the in-app counter are unaffected either way. No detection change, no tier/intensity/cadence change, no pack change. 211 tests pass.


D50. The challenge engine, and "Walk 20 steps" end to end (2026-07-27). D49's block shipped and verified, but the only way past it was a free tap — a reprieve with no cost, which makes the block a speed bump rather than a decision. This adds the other half of the BrainPal unlock mechanic: you get your time back by doing something physical, which breaks the scroll trance in a way tapping cannot. Scope was deliberately ONE challenge built completely rather than four half-wired ones, behind an abstraction that makes the next three cheap. (a) THE ABSTRACTION, AND WHY IT HAS TWO ENUMS. ChallengeSpec {id, type, target, sensorStrategy, promptRes} + ChallengeRegistry, modelled on PlatformSpec/PlatformRegistry deliberately — that file already proved the pattern for a thing whose per-instance details genuinely differ but whose plumbing is identical. ChallengeType (WALK/JUMP/FACE_DOWN/FOREHEAD) and SensorStrategy (STEP_EVENTS/STEP_CUMULATIVE/ACCEL_PEAKS/ORIENTATION_HOLD) are SEPARATE for exactly the reason PlatformSpec splits `platform` from `advanceStrategy`: what the user DOES and how we MEASURE it are different questions and they do not map one-to-one. D53. Jump 10 counts a free-fall→landing SEQUENCE, and the user picks the challenge (2026-07-25). TWO THINGS, because the second is only a problem once the first exists. (1) JUMP DETECTION. A landing spike alone is not a jump: shaking the phone, setting it down hard, and walking with it in a pocket all exceed any threshold worth using, so a peak-magnitude detector would let someone clear "jump 10 times" from the sofa and the mechanic would be theatre. What distinguishes a real jump is the SEQUENCE — while airborne the accelerometer reads near-zero (it is falling with the phone) and only THEN does the landing spike arrive. So free fall ARMS the detector and a spike counts only while armed; a shake never produces the free-fall phase, so it never arms, so it never counts, and `JumpDetectorTest` pins that with 20 consecutive un-armed spikes scoring zero. THREE FURTHER GUARDS, each for a specific miscount: REFRACTORY_MS=400 (a landing is one spike plus a decaying oscillation — without it one jump counts three or four times and "jump 10" completes in two hops; 400ms also caps the rate at 2.5/s, faster than anyone jumps, so it costs a real jumper nothing); ARM_EXPIRY_MS=1000 (human airtime is 200–500ms, so a "fall" older than a second was the phone being lowered and must not bless the next bump); and BASELINING — the first 10 samples are averaged into this device's own resting magnitude and score nothing, because consumer accelerometers are not calibrated to 9.81 and a device reading 9.4 or 10.2 at rest is ordinary, so every threshold is a FRACTION of measured gravity (FREE_FALL 0.45, LANDING 1.55) rather than an absolute m/s². The measured baseline is discarded for 9.81 when it lands outside 7.0..13.0, which is the one case averaging cannot fix: a user who starts jumping the instant the challenge appears baselines against their own motion. The wide dead band between 0.45 and 1.55 is deliberate — that band is "nothing is happening", and a narrow one is how a detector starts counting fidgeting. Sampling is SENSOR_DELAY_GAME, not _UI: a landing spike is tens of milliseconds wide and _UI (~60ms) can sample either side of one and miss it, which reads to the user as a jump that did not count — indistinguishable from the app being broken. Batching stays off for D50's reason. It is cleared by `showBlockPanel`, `showChooser` and `hide`, which between them cover completion, cancel, Exit, Back and the system taking the window — a screen held awake by a torn-down challenge is the same class of bug as a leaked sensor, so it joins the same discipline list. This required `BlockScreenController` to retain its `WindowManager.LayoutParams`, which it had been discarding; `OverlayController` already held the bubble's for the same kind of reason. (4) HAPTICS, BECAUSE THE RING IS FACE DOWN. The challenge asks the user to point the only feedback the mechanic has at a table. Without a signal their only recourse is to flip up and check — which BREAKS the hold they are checking on and resets it, so they lose the progress, cannot tell why, and conclude the feature is broken. `ChallengeHaptics` gives one long 400ms buzz on completion and a two-pulse waveform on a break: different SHAPES rather than different lengths, because a shorter single buzz is indistinguishable from the long one through a cushion and confusing "done" with "you lost it" is the exact mistake being prevented. `VIBRATE` is a NORMAL permission — granted at install, no runtime prompt, no Settings row, nothing for the user to fix — and a device without a vibrator gets silence with everything else intact. Break detection lives in `ChallengeController` (progress dropping below the last observed value) because that class already watches progress transitions for `onComplete`; the decision to VIBRATE stays in `OverlayController`, because the controller's stated contract is that it decides nothing. The guard `if (now < seen)` matters: a hold sitting at 0 samples ~5x/second and must not buzz every 200ms. (5) RING LABEL. `ChallengeSpec.unit: ProgressUnit {COUNT, SECONDS}` with the label a pure function on the enum, so `ProgressRingView` stays dumb and is handed a string — a view that knew the difference between steps and seconds would be a second place for that rule to live. SECONDS counts DOWN ("18s") because remaining is the only question someone mid-hold has. The ARC still FILLS in both cases rather than draining: effort accumulating is the visual language walk and jump established, and a draining arc beside a filling one for the same 15-minute reward reads as a different kind of thing. (6) SAMPLING is `SENSOR_DELAY_NORMAL` (~200ms), not jump's `_GAME` (~20ms). Jump needed the rate because a landing spike is tens of milliseconds wide and can be missed between samples; a hold has no transient to catch, so 200ms keeps a per-second label honest at a fraction of the power across 30 seconds. Face-down is `z < -7.0` on the accelerometer — deliberately loose, about 45° of tolerance, because phones rest on cushions and camera bumps and a strict -9 would fail a user who did exactly what was asked; the sign, not the magnitude, is what prevents a merely-tilted phone counting. IMPLEMENTED += ORIENTATION_HOLD. PROXIMITY_HOLD (forehead) remains out, deliberately its own strategy so it cannot ride in on this one.

**D55. Forehead 30s needs proximity AND upright, because covered alone is a thumb (2026-07-25). Completes the challenge suite.**

WHY NOT PROXIMITY ALONE. A covered proximity sensor means "something is close", not "this phone is at your head" — a thumb over the sensor while the phone lies on a table satisfies it perfectly, which is a two-second cheat on a thirty-second challenge. So the condition is proximity NEAR **and** the device roughly UPRIGHT (`abs(z) < 4.0`, on edge rather than flat, ~65° of tolerance). Neither half is sufficient and the pairing is the point: upright alone is just holding your phone normally, which is what the user was already doing, and near alone is a thumb. A phone flat on a table reads |z| ≈ 9.8 and can never satisfy the upright half, which is the specific cheat this closes. It is still not uncheatable — nothing available to an accessibility service is — but faking it costs more effort than doing it, which is the honest bar for every challenge here. NEAR IS MEASURED AGAINST THE SENSOR'S OWN RANGE, not a hard-coded centimetre figure: `values[0]` is nominally cm but a great many devices are BINARY, reporting 0 when covered and `getMaximumRange()` when not with nothing in between, so `< 5f` is simply wrong on any device whose maximum range is below 5 and needlessly strict on one reporting real distances. Comparing against the declared maximum is the only portable reading. ONE LISTENER, TWO SENSORS: both are registered to the SAME `SensorEventListener`, so `unregisterListener(listener)` releases both in a single call and `stop()` cannot half-release — do not "improve" this into two per-sensor calls, which is how one gets missed on a future edit. A partial registration (proximity took, accelerometer did not) is the one leak this source can produce, so a failed `start` unregisters whatever landed before returning false. Both readings start NULL and null is not a hold: defaulting to "not covered, not upright" would be a guess, and defaulting the other way would credit time the user had not earned. PROXIMITY_HOLD IS ITS OWN STRATEGY, which was decided before face-down was written: sharing ORIENTATION_HOLD would have admitted forehead into `IMPLEMENTED` for free the moment face-down landed, defeating the gate the registry exists to hold shut. It is also the only strategy whose hardware check can genuinely fail on a shipped device (proximity is near-universal but absent on some tablets and budget handsets), so it is the first real exercise of graceful absence — such a device simply never sees the forehead row. EVERYTHING ELSE CAME FREE from D53/D54 and that is the point of the shape: `HoldDetector` is reused completely UNCHANGED (same 30s, same reset-on-break, same `onHoldElapsed`), as are the haptics, `FLAG_KEEP_SCREEN_ON`, the chooser row, the seconds ring label and the flat 15-minute reward. The increment added one file and four small edits. ROM RISK, recorded because we cannot code around it: proximity does not itself sleep the screen (that is the dialer's `PROXIMITY_SCREEN_OFF_WAKE_LOCK`, which we never request), but several OEM ROMs ship a "pocket mode" that locks the screen when the sensor is covered. `FLAG_KEEP_SCREEN_ON` covers stock Android; if a ROM locks anyway, forehead is not viable on that device and the honest answer is to find out on hardware rather than guess. IMPLEMENTED now equals the full declared set for the first time — a legitimate state, not a bug, and `ChallengeRegistryTest` says so explicitly along with what to do when the next strategy is declared ahead of its code.

**D59. The backend lives in THIS repo: a monorepo with path-filtered CI, because the sync contract has two sides (2026-07-28).**

THE DECIDING ARGUMENT IS THE PARITY TEST, not taste. Phase 3b puts `platform` in Postgres as an ENUM whose members must equal the client's `Platform.id` values, and a mismatch there is not a build error — it is a **silent sync drop**, the worst failure class this backend can have, because the device keeps counting, the batch keeps getting acked, and the number quietly never arrives. The only way to *test* that pair is to have both trees checked out at once, which one repo gives for free and two repos give only by vendoring one into the other's CI and pinning a version. The same logic covers every future contract change: the sync request shape, the ack semantics, the date-boundary contract. In a split repo those land as two PRs that must merge in order, with a window in between where main is inconsistent; here one PR changes both sides atomically and CI proves the pair. THE COST IS REAL AND IS PAID IN CI CONFIG: without path filters every Kotlin commit runs pytest and every Python commit runs a multi-minute Gradle build, which is how a monorepo becomes a tax people route around. So `android.yml` and `backend.yml` each carry `paths:` from the very first commit — the filter is part of the decision, not an optimisation to add later once the annoyance has trained everyone to skip CI. BACKEND MUST NOT BECOME A GRADLE MODULE: `backend/` gets no entry in `settings.gradle.kts` and nothing in the root `build.gradle.kts` references it. The Android build must remain runnable by someone with no Python installed, and the backend by someone with no JDK — two toolchains, one repo, zero coupling at the *build* level. The coupling is at the *contract* level, and that is exactly where CI should be able to see it. REJECTED: a separate `scrollkiller-api` repo. The usual reasons to split (different release cadence, different access control, different teams) do not apply to a solo project shipping one product, and the one thing splitting genuinely gives — an independently deployable service — is already true inside a monorepo, since deployment reads a subdirectory. What splitting costs is precisely the atomic contract change, which is the thing most likely to break. ALSO REJECTED: git submodules, which combine the worst of both — the split repo's version-pinning dance plus a checkout everyone forgets to update.

**D60. The security baseline exists before the first endpoint, and the pipeline is a first-class deliverable (2026-07-28).**

WHY 3a IS NOT "SCAFFOLDING". Every item in the 3a security baseline is cheap to add to an empty service and expensive to retrofit onto a running one, and that asymmetry is the whole argument. A non-root, digest-pinned, multi-stage image written before there is an endpoint is twenty lines of Dockerfile; added after the service is live it is a migration with file-permission surprises. Hash-pinned dependencies from the first requirements file mean the lockfile is a fact; added after months of drift it means auditing what already shipped and hoping. `gitleaks` in CI before the first secret exists is prevention; added after one is committed it is history-rewriting plus credential rotation, and the leaked value is already in every clone. Security invariants are exactly that class: nobody catches a root container in review, because a root container looks like an ordinary Dockerfile. Concretely 3a must produce, on the FIRST-EVER `.github/workflows/` in this repo: the Android build running in CI at all (it never has — every green build to date has been local, so the build's reproducibility on a clean machine is currently unproven), backend `pytest` + `ruff` + `mypy` as blocking gates rather than advisory steps, and the supply-chain trio (Trivy image scan, syft SBOM as a retained artifact, gitleaks) wired as jobs with an explicit and *recorded* pass/fail posture — a scanner whose failures are ignored is worse than no scanner, because it manufactures the feeling of coverage. `/health` MUST NOT TOUCH THE DATABASE, and that is an availability decision, not a performance one: on Neon's free tier the database autosuspends, so a DB-touching health check reports a *sleeping database* as a *dead application*, and the platform then restarts a perfectly healthy service — the check causes the outage it exists to detect. `/readyz` is the one that touches the DB, and only readiness gates traffic. **D65. Reconciliation: displayed = server-acked total + local unacked deltas. The server owns acked history and the date boundary; the device owns what it has observed and not yet had credited (2026-07-28).**

THE CONTRADICTION THIS RESOLVES. SCHEMA.md says the client reconciles to server truth on app open. CLAUDE.md says the device is the source of truth. Both are load-bearing, and naively combined they LOSE DATA in the most ordinary situation there is: the server says 40, Room says 45, five deltas are queued and unacked, "reconcile to server truth" overwrites 45 with 40, and five reels the user actually watched are gone forever. Take the other horn and "the device is truth" means the server's date boundary never applies, so a user crossing midnight in their own timezone keeps accumulating into yesterday — which breaks invariant 2 and every streak built on it. THE RULE, which is neither horn: **displayed = `server_acked_total` + `sum(local deltas not yet acked)`**. The server is authoritative over the history it has *acknowledged* and over *which day a count belongs to*. The device is authoritative over observations the server has not yet credited. Nothing is ever overwritten; a delta MIGRATES from the local-unacked side to the server-acked side at the moment of ack, and the displayed number is unchanged by that migration — which is the property to test, because it is the one a user would notice violated. A number that visibly jumps when a network call returns is the bug, whether it jumps up or down. THIS IS CRDT-SHAPED, DELIBERATELY. `server_acked_total` is a G-Counter: monotonic, only ever increased, and increased only by increments the server has durably recorded. The queued local deltas are pending increments to that counter. Two devices on one account converge without a merge conflict because neither ever *asserts a total* — they assert increments, and increments commute. This is the direct structural reason invariant 1 forbids POSTing absolute counts, and it is worth naming the bug class it closes: BrainPal's. Absolute-count POSTs from two sources race, last-write-wins, and the loser's activity silently disappears. Under delta sync plus this rule the two remaining failure modes are **double-count** — closed by `batch_id` dedupe server-side (D3, and 3d's `INSERT ... ON CONFLICT DO NOTHING` gating the increment) — and **drop**, closed by keeping a delta local until it is *acked*, never until it is merely *sent*. Both are closed by the same mechanism, which is why this is one decision and not two. IT REUSES A LAYER THAT ALREADY EXISTS, which is the strongest evidence the shape is right. D39 already built exactly this reconciliation one level down: `PendingCounts` holds observations detected but not yet persisted to Room, and `TodayMerge` combines them with Room's durable state so the count is monotonic and converges as writes land. The server tier is the same relationship with a slower, less reliable store — Room is to `PendingCounts` as the server is to the sync queue. So this is a third input to a merge that already exists, not a rewrite, and it keeps that layer's existing property of being pure and unit-testable with no device and no network. THE ACK IS THE ONLY STATE TRANSITION THAT MAY DELETE A LOCAL DELTA. Not "the request was sent", not "the response was 200 but the body was not parsed", not "a later batch succeeded" — the specific `batch_id` must come back in the ack list. This is what makes the whole thing safe across cold starts: a request that times out against a spun-down instance may or may not have been processed, and under this rule the answer does not matter — the delta stays local, is resent with the SAME `batch_id`, the server dedupes, and the ack eventually arrives. Retry-safety is not a feature added on top; it falls out of never dropping an unacked delta. WHAT THE SERVER OVERRIDES, precisely, so this is not misread as "the client always wins": the DATE. The client does not decide which day a delta belongs to — it reports observations, and the server assigns them to a day from `users.timezone` (invariant 2). On app open the client takes the server's notion of "today" and its acked total for that day, then adds whatever it holds unacked for that same day. A client-side clock change therefore cannot manufacture or destroy a day's history, which is exactly the hole a device-is-truth reading would have left open. OFFLINE IS THE COMMON CASE, NOT THE EDGE. Signed out, or offline, or the backend not deployed at all: `server_acked_total` is simply 0 and every delta is unacked, so the displayed number is the local total and the app behaves precisely as it does today. That is not a fallback path bolted on — it is the same expression with one term empty, which is what makes "the app must keep working with zero backend, forever" a structural property instead of a promise someone has to keep remembering.

Under the ₹0 constraint, spending a metered budget on infrastructure with no users is the specific kind of waste that later forces a paid upgrade for the wrong reason. WHAT PHASE 3 *DOES* BUILD AHEAD OF ITS CONSUMER, and the distinction is the useful part of this entry: `devices` and `friendships` are created in 3b, unused. That is deliberate and not a contradiction — tables are schema, and adding one later is a migration against live data, whereas an unused table costs nothing and keeps the schema whole and reviewable in a single pass. A Redis integration is *running code with an operational surface*; an empty table is not. The line is: **schema may lead its consumer, services may not.** FCM ALSO NEEDS A CLIENT-SIDE TOKEN and, on Android 13+, a notification-permission prompt — a user-visible ask. Requesting notification permission during a phase that sends no notifications trains the user to decline it, and it would have to appear in a build whose entire premise (3a–3d touch nothing in `app/`) is that the shipped app cannot regress.

**D67. CI runs Temurin, local runs the JetBrains Runtime, and the two are deliberately independent (2026-07-28).**

THE PIN THAT CAUSED THIS. `gradle/gradle-daemon-jvm.properties` carries `toolchainVendor=jetbrains, toolchainVersion=21` — Android Studio's bundled JBR, which is the correct daemon JVM for a developer building from the IDE and is why `JAVA_HOME` has to point at the AS `jbr` directory locally. GitHub's runners ship Temurin and Zulu and have never shipped JBR. So the first-ever CI run of this project's Android build meets a vendor constraint the runner cannot satisfy, and this was identified before writing the workflow rather than discovered in a red build. THE DECISION IS TO NOT RELAX THE PIN. `android.yml` sets Temurin 21 via `actions/setup-java`, and if Gradle's daemon criteria refuses it the fix goes in the WORKFLOW — never in the pin. The reasoning is drift: a vendor pin loosened "so CI passes" quietly changes what every developer builds locally, and the change is invisible because nothing fails, which is the worst shape a build change can have. Local and CI running different JVMs *of the same major version* is not drift; it is two environments each using the JVM that is correct for it. Drift is when one is edited for the other's benefit. WHAT THIS BUYS, concretely: the IDE keeps a daemon that matches its own bundled runtime (no second JVM downloaded on every Studio sync, no toolchain mismatch warnings), and CI keeps a plain vendor-neutral JDK that costs nothing to provision and will still be there when the runner image changes. WHAT IT COSTS: the pair can only be verified by running both, which is precisely what 3a establishes and what nothing before it did. THE FALLBACK LADDER, recorded so a future red build is worked rather than researched: (1) the `foojay-resolver-convention` plugin is already applied in `settings.gradle.kts`, so Gradle may auto-provision a JBR 21 and simply work — cached by `setup-gradle`, a one-time download; (2) failing that, pass `-Dorg.gradle.java.home=$JAVA_HOME`; (3) failing that, a CI-only step rewrites the vendor line before the build, never committed, documented inline. The ladder is ordered by how little it touches. NOTE THE SECOND, UNRELATED ASYMMETRY that the same workflow documents: `lintDebug`'s one known error lives in `local.properties`, which is gitignored and therefore ABSENT on a runner, so CI lint can pass where local lint fails. That is an environment difference, not a fix, and the workflow says so in a comment — because a green CI lint is exactly the kind of evidence someone would otherwise use to close the local finding.

**D68. The repo is private now and public after launch, which makes CI minutes a budget and git history a portfolio artifact (2026-07-28).**

TWO CONSEQUENCES FROM ONE DECISION, and they pull in opposite directions, which is why it is worth writing down. PRIVATE MEANS MINUTES ARE FINITE. GitHub Actions is unlimited on public repositories and capped at 2,000 minutes/month on a private one under the Free plan. An Android build with a cold Gradle cache is the most expensive job in this repo by a wide margin. So `paths:` filters and `concurrency: cancel-in-progress` are NOT hygiene here — they are the budget. Without the filter every docs commit pays for a full Gradle run; without the cancellation three pushes in a minute pay three times for a result only the last one needs. This is also the concrete cost side of D59's monorepo decision, which said the filters were part of the decision rather than a later optimisation: this is why. ONE DELIBERATE EXCEPTION: `security.yml` is not path-filtered. A secret can land in any file — a README, a test fixture, a JSON asset, a workflow — and filtering a secret scanner by path is how you miss the one in the file nobody thought to filter for. It runs in seconds, so the budget argument does not reach it. The rule is: filter the expensive jobs by what they build, never filter the cheap job that looks at everything. PUBLIC-LATER MEANS HISTORY IS PERMANENT. The repo is intended to be opened after launch as the portfolio piece, so every commit written today is written for an audience that does not exist yet and cannot be edited when it does. Practically: no secret may ever enter history (which is why `gitleaks` and `.pre-commit-config.yaml` land in 3a rather than at the first credential — remediation after the fact is rotate-plus-rewrite, and the value is already in every clone); `.env.example` carries placeholders only and says so in the file; commit messages explain WHY, since they are the most-read artifact of a repo someone is evaluating; and the `.gitignore` work that opened 3a (IDE state, 6.7 MB of raw art discards, Python caches, an Obsidian pane layout) is not tidiness but a decision about what a stranger will find. THE COUNTER-ARGUMENT, WEIGHED AND REJECTED: go public now and the minute cap disappears entirely. Rejected because the app is unreleased and the detection heuristics — the marker strings, the debounce values, the calibration in D11 — are the actual product, and publishing them before launch hands a competitor the part that took the longest. The minute cap is a cost we can engineer around; a pre-launch teardown is not.

**D69. Python pins to 3.13, superseding CLAUDE.md's 3.12, because a version you cannot run locally is a gate that only runs in CI (2026-07-28).**

CLAUDE.md specified Python 3.12 when the backend was still hypothetical. The development machine has 3.13.14 and 3.14.3 and no 3.12 at all. The choice was therefore not "which version is nicest" but "what happens to the gates" — and holding 3.12 means every one of them (ruff, mypy --strict, pytest, the coverage floor) can only be run by first installing another interpreter or by going through the container. Both are friction in front of the check that is supposed to run before every push, and a gate with friction in front of it is a gate that gets skipped and then only fires in CI, which is precisely the "it passed locally" failure that 3a exists to end. So the spec moves to 3.13, matching local exactly. 3.13 IS THE RIGHT END OF THE RANGE, not merely the convenient one: FastAPI, SQLAlchemy 2.x, Alembic and asyncpg (0.30+) all support it with wheels, so nothing in the Phase 3 dependency set has to build from source. 3.14 was rejected despite also being installed locally — its wheel coverage across that same set is the thinnest of the three, and a source build failing in CI would have been a bad first signal to debug alongside the Android job's first-ever run. The version is stated in exactly three places, all of which must move together: `backend/pyproject.toml` (ruff `target-version`, mypy `python_version`), `backend.yml`'s `PYTHON_VERSION`, and the Dockerfile's digest-pinned base. CLAUDE.md is corrected rather than left saying 3.12, because a stale spec is worse than no spec — it gets cited.

**D70. A permission prediction may never gate the block attempt. `canBlock` answers only the queryable question, and the observed-failure flag is display-only, because as a gate it latched blocking off permanently (2026-07-28).**

> ⚑ **Read D72 alongside this.** The "the ROM is refusing anyway" framing below — including that
> wording in the `FAILED` copy — was wrong about this device: the block's window was never refused,
> and every failure that framing explained came from our own premature attach check. The CORE of
> this ADR is unaffected and is the reason the truth was findable: a stale signal may darken a
> banner and may never veto an attempt. Banner is navigation, not a rewrite (append-only rule).

THE SYMPTOM, from a device with the overlay permission visibly GRANTED in system settings: `BLOCK PREVENTED at 23/20 on INSTAGRAM: overlay permission missing`, and `entered INSTAGRAM with the block dead`. The count kept climbing, the block never drew, and the user was told to grant a permission they already held. THE FALSE SIGNAL, named precisely because "the permission check is wrong" is the wrong hypothesis: it was NOT `Settings.canDrawOverlays` (true throughout) and NOT an AppOps `checkOpNoThrow` (this app has never called one). It was `PermissionHealth.overlayRuntimeDenied`, backed by the persisted SharedPreferences boolean `overlay_runtime_denied` — D52's record of having once OBSERVED the system refuse our window. THE DEADLOCK, which is the actual bug and is structural rather than a wrong boolean. Three facts, each defensible alone: (1) `canBlock` ANDed in `!overlayRuntimeDenied`; (2) `OverlayController.render` used `canBlock` as an early-return GATE before calling `block.show()`; (3) the only code that ever cleared the flag lived in the SUCCESS branch of `block.show()`. Together they form a latch with no key — any single refusal set the flag, the gate then refused every future attempt, and the clearing code sat behind the gate the flag had closed. Re-granting the permission did nothing. A reboot did nothing. Only clearing app data did. Worse, the ordinary way to set it was not an exotic ROM at all: it was `ShowResult.NO_PERMISSION`, i.e. hitting your daily limit while the permission was legitimately off, which is *literally HANDOFF Run 3*. The permission-integrity verification procedure bricked the feature it was verifying. THE FIX IS TO SPLIT ONE QUESTION INTO TWO, because "may we try?" and "should we reassure the user?" were being answered by one property. `canBlock` is now `accessibilityEnabled && canDrawOverlays` — what the system will let us attempt, freshly queryable, never sticky. `blockObservedBroken` carries the observation, feeds `isFullyActive` and `firstMissing`, and drives the banner exactly as D52 intended. The gate in `render` is DELETED outright: the BLOCK branch always attempts, and the `ShowResult` decides what is recorded and what the user is told. `BlockScreenController.show` likewise stops pre-checking `canDrawOverlays`; it attempts `addView`, and consults the permission only AFTERWARD to word the failure (`NO_PERMISSION` = "grant it" versus `FAILED` = "your settings already say granted and the ROM is refusing anyway"). THIS IS WHAT D52 ALREADY SAID, which is why this is a correction and not a discovery: D52's whole finding was that the permission query lies on these ROMs and only the attempt knows. D51 then added a loud failure report — correctly — and the report was implemented as a gate. **A diagnosis placed in front of an action becomes a sentence.** The general rule worth carrying out of this: a stale signal may darken a banner and may never veto an attempt, and anything persisted is stale by construction. SELF-HEAL, so an already-latched device recovers without clearing data: `ensureAttached` clears the flag whenever the bubble's window attaches, and sets it when that `addView` fails. An attached bubble is live proof the device will give us an overlay window; it happens on every Instagram open rather than only at a limit crossing; it is the cheap frequent observation correcting the expensive rare one. THE COST, accepted: the app now inflates and attempts a block on a device where it genuinely cannot draw one. `BlockRetryPolicy`'s 30s cooldown already bounds that to one attempt per 30s per surface — the retry storm D52 closed stays closed — and the alternative is the state this ADR exists to end.

**D71. The block window is OWNED from the moment `addView` returns, not from the moment it succeeds. An untracked full-screen overlay trapped a user off their own home screen — P0 against invariant 6 (2026-07-28).**

THE REPORT: the block appeared full-screen, Exit did nothing, the other two buttons did nothing, hardware Back did nothing, and the user could not reach their home screen. That is invariant 6 — "the block screen is ALWAYS exitable... a block that cannot be dismissed is a P0, no product reason outranks this" — failing completely, and it is the highest-severity defect this project has produced. THE MECHANISM, one early return. `show()` verified the attach with `if (!root.isAttachedToWindow) { ...; return FAILED }` — the correct instinct, and D52's own lesson that `addView` returning is not proof the window exists — but it returned while the root was STILL INSIDE THE WINDOWMANAGER, and `view` (the field that is both the handle and the idempotence guard) was only ever assigned after a verified attach. So the window existed and nothing referenced it. Every symptom follows mechanically: `isShowing` was false, so `hide()`'s opening `val v = view ?: return` made Exit, snooze, challenge-completion and every other dismissal a silent no-op — the listeners fired and did nothing, which is the worst possible failure shape because it is indistinguishable from a dead touch path; `root.requestFocus()` was never reached, so the root-focused `OnKeyListener` never ran and Back did nothing either; `OverlayController.isBlocking` stayed false, so the service's surface hysteresis expired and the window outlived leaving Instagram; and being `TYPE_APPLICATION_OVERLAY` + `MATCH_PARENT` + `OPAQUE` + focusable, it outranked the launcher, which is the "could not get to home" part. Then, 30 seconds later, the retry cooldown lapsed and a SECOND full-screen window was stacked on top — so dismissing the tracked one merely revealed a dead one underneath, and Exit "did nothing" a second way. THE FIX IS TO RECORD OWNERSHIP ON THE ACTION, NOT ON THE OUTCOME. `attachedRoot` is assigned in the statement immediately after `addView` returns, before anything is verified or decided, and is cleared only by `removeFromWindow` — the single place `removeView` is called. Every post-`addView` path is then obliged to keep the window or remove it, and none may merely return. `hide()` is unconditional (it tears down whatever exists, tracked or not) and `sweepOrphan()` runs on leaving the tracked app and on service destroy. In a correct build the sweep finds nothing, and that is the point: if a future edit reintroduces a skipping return, the window dies on leaving Instagram instead of covering the launcher indefinitely, and it logs loudly enough to find. THE SECOND, INDEPENDENT DEFECT found in the same pass: Back was handled by an `OnKeyListener` on the root, and a ViewGroup's OnKeyListener only runs while that ViewGroup is ITSELF the focused view. The escape hatch was therefore conditional on a focus arrangement nothing enforced and no test asserted — already broken on the trap path (focus never requested), and breakable in normal operation by TalkBack, a keyboard or a dpad moving focus onto any Button. `BlockRootView` now overrides `dispatchKeyEvent`, which `ViewRootImpl` calls on the root for every key event before any focus-based routing, so Back escapes regardless of what holds focus or whether anything does. **The way out must not be a consequence of the UI being in a good state.** A THIRD hazard, fixed while here: the three panels are `wrap_content` inside a centred stack with no scrolling, so at a large font scale or on a short screen the content overflows and Exit is laid out past the bottom of the display. An Exit that exists but cannot be touched is the same trap with a nicer cause; the stack now sits in a `ScrollView fillViewport="true"`, which keeps the centring when content is short and scrolls when it is not. OBSERVABILITY, because the most expensive unknown during triage was whether taps were REACHING the buttons at all: every button, every chooser row and Back now log twice, once on entry and once after the handler with the state that says whether anything happened. "The touch never arrived" and "the handler ran and was a no-op" need opposite fixes and were indistinguishable from outside the device. AND THE TRAP IS NOW REPRODUCIBLE ON DEMAND: `BlockFailureInjector` (DEBUG-only, armed over adb in the same shape as the `DIAG_LABEL` tour stamp, compiled out of release) forces either the throw or the never-attached path. It ships deliberately. The bug reached a real device and was found by a person; the failure cannot be triggered by hand on a healthy phone; and without a way to force it, the only available evidence that the fix works is the ABSENCE of a bug that was already rare — which is not evidence. It converts "we think we fixed the trap" into a repeatable device check.

**D73. YouTube blocks at its limit, reversing D57. The count is still uncalibrated, so eligibility comes from an explicit `blocksWhileUncalibrated` override rather than from declaring it STABLE (2026-07-28).**

OWNER DECISION, and it reverses a decision this project made four sessions running. D57 closed YouTube at BETA as a v1 call: the Shorts acceptance capture (15 swipes landing 15 ±2; 30s idle on one Short moving the count by zero) was requested repeatedly and never produced, and promotion was refused on absent evidence because `blocksAtLimit` is what decides whether the app covers someone's screen. That evidence is still absent. What changed is not the evidence but the weighing of it: leaving a self-declared doomscrolling surface unenforced indefinitely, for want of a calibration run that keeps not happening, is its own product failure — the user hits their YouTube limit and nothing happens. The concern was raised and the direction reaffirmed, so it ships. THE MECHANISM IS THE POINT, because there were two ways to do this and only one is honest. The tempting one is `maturity = STABLE`, which is a single-word edit and makes `blocksAtLimit` true for free. It is wrong twice: `Maturity` documents "the count is calibrated against real swipes", which would become a false statement in the source, and `isBeta` drives the dashboard's Beta badge, so flipping it silently withdraws the app's own disclosure that the YouTube number is unmeasured — a claim change, and STORE_COPY.md's whole posture is that we do not make claims we cannot support. The other way is the one D32 itself prescribed for exactly this contingency: *"If a Beta platform ever legitimately needs to count toward limits, split the flag deliberately and record why."* So `blocksWhileUncalibrated` is a second, separately-named condition on `blocksAtLimit`; `maturity` stays BETA and keeps its badge; and the two questions D32 correctly refused to let one knob answer — "is this count calibrated" (no) and "may this count enforce a limit" (yes) — are now answered separately and on the record. WHAT THIS ACTUALLY RISKS, stated so it is not rediscovered as a surprise: the block may fire a few Shorts early or late, and if the per-item identity flaps during playback the count could advance without a swipe. WHAT IT DOES NOT RISK is the block landing on the wrong screen, and that distinction is the entire basis for accepting the first risk. YouTube is `GatingMode.ENFORCED` on `reel_recycler`, a marker device-toured on 2026-07-24 (D26) and deliberately narrowed to that one proven id — the `shorts_*` guesses were dropped at D28 precisely because the home feed carries a Shorts SHELF whose ids could false-match. An unmatched marker UNDERCOUNTS; it never counts the subscriptions feed. So the failure mode is "the block does not fire", not "the block covers the wrong thing", and that asymmetry is what makes an uncalibrated blocker tolerable at all. THE LINE THIS DOES NOT CROSS: TikTok and Snapchat remain barred, and not by convention — `PlatformRegistryTest` now asserts that the override is only legal on an ENFORCED platform with non-empty markers. Both are SHADOW: TikTok counts app-wide, and Snapchat actively counts Chat/Stories/Map scrolls as "snaps". Their numbers are wrong about WHAT they counted, not merely by how much, and no product argument reaches them. The precedent set here is narrow and the test is what keeps it narrow. WHEN THIS ADR EXPIRES: the day someone runs the two acceptance captures, `maturity` goes to STABLE and `blocksWhileUncalibrated` should be DELETED in the same commit — an override that no longer overrides anything is a live invitation to reuse it somewhere it does not belong.

**D72. The premature attach check was the entire root cause. `isAttachedToWindow` was read one frame before the framework could set it, and three ADRs blamed the ROM for it (device-confirmed, 2026-07-29).**

CONFIRMED, and the confirmation is unambiguous. The instrumented build's own transcript, in order, from one block: `attachedSync=false (expected false if the premature-check hypothesis holds)` → `PENDING_ATTACH` → `block: ATTACH LANDED (listener) — the window exists` → SHOWN → `block: PROBE next-frame attached=true`. That sequence IS the proof. The synchronous read returns false and the framework's own callback fires moments later on the same window: nothing refused anything, the window was healthy the whole time, and the only defect was that this class asked whether the attach had landed before the platform had any opportunity to land it.

THE MECHANISM, stated once so it is never re-derived. `View.isAttachedToWindow()` returns `mAttachInfo != null`. `mAttachInfo` reaches the view tree in `host.dispatchAttachedToWindow(...)`, which runs inside `ViewRootImpl.performTraversals()`, which is scheduled through the Choreographer by the `requestLayout()` in `ViewRootImpl.setView()`. `WindowManager.addView` therefore CANNOT leave the view attached by the time it returns — not on a slow device, not on a hostile ROM, not ever. Reading the flag on the next statement is not a race that usually loses; it is a check that cannot ever pass. The code had a 100% false-negative rate on a healthy window, and we spent three sessions attributing the result to the device.

WHAT THIS CORRECTS, explicitly, because leaving it standing would keep costing time.

**D52's central attribution is WITHDRAWN.** D52 concluded that this is "a MediaTek ROM that revokes SYSTEM_ALERT_WINDOW at runtime" and that "`Settings.canDrawOverlays()` KEEPS RETURNING TRUE while AppOps refuses the op". That is not what was happening. The ROM never refused the block's window. Every `FAILED` verdict that reasoning rested on was produced by our own one-frame-early read, and the `Operation not started op=SYSTEM_ALERT_WINDOW` line was over-read — taken as the cause when it was, at most, incidental system chatter next to a failure we had manufactured ourselves. D52's *reframing* — "the authoritative signal is not a permission query, it is whether the window actually exists" — was exactly right, and is the sentence that eventually produced the fix. It was simply implemented with a question that could not return the truth.

**D70's `FAILED` copy — "your settings already say granted and the ROM is refusing anyway" — was wrong about this device**, and D70's framing of the affair as the ROM lying inherits the same error. What D70 got right stands untouched and is worth more than what it got wrong: a stale signal may darken a banner and may never veto an attempt, and anything persisted is stale by construction. That principle is what made this build able to attempt a block at all, which is what made the evidence collectable. The `OVERLAY_BLOCKED_BY_SYSTEM` gap and its copy are KEPT, because they are now correctly scoped: they can only be reached after the window has had `BlockLimits.ATTACH_DEADLINE_MS` to attach and has not, which is a real refusal rather than a misread. The trigger became honest; the words did not have to change.

**D71 is not corrected and never depended on any of this.** The trap it fixed was real, was a P0 against invariant 6, and its cause was structural — ownership inferred from success rather than recorded on the action. D72 explains what *drove* the code down that path so reliably: the attach check failing every single time is what kept sending a healthy window into the untracked-return branch. But D71's fix is correct on its own terms, and it is what makes a pending window safe to leave on screen while the probes resolve. Note the through-line, because it is the cleanest summary of the whole saga: the same premature check produced BOTH shapes of the bug. Before D71 the misjudged window was left in the WindowManager, attached a frame later, and became the un-dismissable full-screen trap. After D71 it was removed a frame early and nothing appeared at all. One misread, two opposite symptoms, three ADRs.

THE MODEL IS NOW PERMANENT, not a probe. `ShowResult.PENDING_ATTACH` and its three observation points stop being "a hypothesis under test" and become how this class works: the framework's `onViewAttachedToWindow` callback is the primary and earliest honest answer; `View.post` is the next-frame confirmation, where a healthy window MUST read attached; and the 250ms deadline is the backstop that decides a genuine refusal. `show()` returning `PENDING_ATTACH` is a normal, successful-so-far outcome and the caller must never treat it as failure — no warning, no runtime-denied flag, no cooldown. Success is reported asynchronously through `onWindowConfirmed`. The irony worth recording: `OnAttachStateChangeListener` had been wired up since D52 and its ATTACH callback was a no-op. The correct, framework-provided answer to "did the window attach?" was sitting in the file, being ignored in favour of a synchronous read that could not work.

THE BUTTONS ARE VERIFIED LIVE, which closes the other half of the saga. The same capture shows `TAP challenge.open → done`, `TAP chooser.option[forehead_30] → done`, and `TAP challenge.exit → done → launcher started`. Block, chooser, challenge and exit all work end to end on a real device. Invariant 6 is now demonstrated rather than argued: the way out was taken and it worked. D71's per-tap logging is what made that readable — "the touch never arrived" and "the handler ran and was a no-op" need opposite fixes and are indistinguishable from outside the device.

NO REBUILD WHILE SHOWN. The capture contains two block cycles (seq 83 and 85), which is the correct re-fire shape: exit, still over limit, re-enter the surface, block again. That a continuously-shown block never rebuilds is guaranteed STRUCTURALLY rather than by observation — `showInternal` returns `ALREADY_SHOWING` on `view != null` before any inflation (updating only the guilt line), and returns `PENDING_ATTACH` on `attachedRoot != null` before any inflation, and both fields are cleared only by `removeFromWindow`. Inflating a second `block_root` therefore requires an intervening teardown by construction. This is D52's churn defect staying fixed, now with a second guard covering the window between `addView` and a confirmed attach — the gap the pre-D71 build stacked two full-screen overlays through.

THE GENERAL LESSON, and it is the expensive one: **before attributing a failure to a hostile environment, prove your own measurement can succeed under ideal conditions.** Three ADRs described a device that was misbehaving. The device was fine. The check was asking a question whose answer was fixed before it was asked, and the cost of never testing the instrument was two device sessions, a P0 trap that reached a real user, and a permission flag that latched blocking off until app data was cleared. A diagnosis that cannot fail its own null hypothesis is not a diagnosis.

NOT CHANGED HERE: detection, thresholds, limits, gating, storage, sync, the retry cooldown, or the guilt pack. `BlockFailureInjector` stays (DEBUG-only, compiled out of release) and is now MORE valuable, not less: with the real failure understood, it is the only way to exercise the genuine-refusal path that `ATTACH_DEADLINE_MS` guards.

A second test now pins boundedness INDEPENDENTLY of the inequality, so if the tap is ever deleted for good, only the inequality test goes with it.

WHAT D74 GOT RIGHT AND IS KEPT: move the button, the string and the handler TOGETHER, in either direction. A string with no control is invisible; a control with no handler is a dead button on a screen covering another app, which is the exact failure shape D71 spent a P0 on. Both ADRs also agree on the point that matters most, and it is worth stating in both places so neither side of the argument is ever made on the wrong grounds: **this was never an invariant-6 control.** A snooze is not an exit — it defers the block and keeps the user in the app. Exit and hardware Back are what invariant 6 names, they are present on all three panels, and neither has ever touched these constants. The open question is therefore a product one — does the block deserve a free escape hatch — and not a safety one. It stays until that call is made.

**D76. One daily scroll limit across every blocking app, superseding D19/D49's per-platform limits. The budget is the doomscrolling day, not the app (2026-07-29).**

WHAT WAS WRONG, and it is a product bug rather than a code one. D19 put the limit on `PlatformSpec.dailyLimit` and D49's Settings gave each blocking platform its own slider. So a user with Instagram at 100 and YouTube at 100 could scroll 99 reels and 99 Shorts — 198 short videos — and be blocked by neither, because each app was only ever measured against itself. The app's entire premise is that a doomscrolling *day* is the thing being limited; splitting the budget per app quietly contradicted it. D49's counter-argument was that "100 reels" and "100 Shorts" are different commitments. That is true of how people *talk* about apps and false about what the limit is *for*.

THE SECOND FAILURE MODE was worse because it was silent and got worse over time: every platform arrived with its own fresh allowance, so ADDING a platform RAISED the effective ceiling. D73 turning YouTube on doubled everyone's real budget overnight and nothing said so. A limit that loosens itself whenever the app improves is not a limit.

THE SHAPE. One `daily_limit` key, one slider, one number. `BlockPolicy.overlayFor` is unchanged — the arithmetic was never the problem — but what the overlay hands it is now `BlockPolicy.blockingTotal(summary.perPlatform)` against `SettingsPrefs.dailyLimit(context)`.

TWO QUESTIONS THAT LOOK LIKE ONE, AND MUST NOT BE MERGED. *What counts toward the limit* is now global. *Where the block may draw* stays per-platform: `PlatformSpec.blocksAtLimit` for the surface the user is standing on. Keeping them separate is the safety property — spending the budget on Instagram must never put a full-screen block over an app we are not cleared to block, so a user over the limit inside a SHADOW app sees the bubble and never the block. One number decides *whether* the day is spent; a different, per-platform predicate decides *whether we may act on it here*.

WHY `blockingTotal` IS NOT THE GRAND TOTAL, which is the subtle part. The bubble shows the grand total across everything tracked (D35) and that is right for a passive counter. It is the wrong input for a limit: TikTok and Snapchat run SHADOW on untoured markers, and Snapchat is a KNOWN overcount — it counts Chat/Stories/Map scrolls as "snaps" (D32). Folding a number we have admitted is wrong into the sum that covers someone's screen is exactly the failure D32 and D73 exist to prevent; the user would be blocked out of Instagram because they scrolled their Snapchat inbox. So the SAME predicate that decides whether a platform may *trigger* the block also decides whether it may *contribute* to it. A platform earns its place in the budget by being trustworthy enough to enforce on. This does mean the Today tab's total and the limiter's total can differ, and that is correct rather than a bug — Settings names the covered apps (`settings_limit_covers`, built from `blocksAtLimit`, never hardcoded) so the scope is stated rather than guessed.

THE MIGRATION, which is the only part with no obviously right answer. Rule: **sum the limits the user actually chose.** Each half matters. SUM, because it preserves the ceiling they already had — someone with Instagram 60 and YouTube 45 could previously reach 105 before either blocked, and a unified 105 leaves them exactly where they were. Taking the max (60) would silently TIGHTEN their limit on upgrade, and that is the one direction a migration must never move on its own: the user hits a block far earlier than they asked for and reads it as a bug. WHAT THEY ACTUALLY CHOSE, because summing untouched DEFAULTS inflates the result — a user who only ever moved the Instagram slider to 60 would otherwise get 60 + YouTube's default 100 = 160, a ceiling they never asked for. So only keys explicitly present in SharedPreferences are summed, only for platforms that could actually block (a SHADOW platform's stored limit was never enforced, so folding it in invents budget out of a control that did nothing), and a user who set nothing gets `DEFAULT_DAILY_LIMIT`. Runs once, on the first read after upgrade, guarded by the presence of the new key. The old `daily_limit_<platform>` keys are deliberately NOT deleted: a migration that destroys its own input cannot be re-run or audited if the collapse rule turns out to be wrong, and a few stale ints cost nothing.

COPY. `settings_limit_subtitle` says "short videos", not "reels": the total spans platforms that count reels, shorts and snaps, so naming one of them would be wrong — the same reason D37's bubble panel line carries no unit noun.

NOT CHANGED: detection, gating, the per-platform *grace* deadline (a reprieve is still granted on the surface you earned it on), `PlatformSpec.dailyLimit` as a per-spec default (still the fallback source for a fresh install), or `blocksAtLimit` itself. Tests pin the boundary, that two platforms' counts spend one budget when neither alone reaches the limit, and that no SHADOW platform can add a single item to the limiter's input.

**D77. STRICT MODE: the free "5 more minutes" is deleted for good — challenge or exit, no free bail. This is the product call D75 was holding the door open for (2026-07-29).**

THE SEQUENCE MATTERS, because this constant has now moved three times and the record should say why rather than look like thrash. D74 deleted the snooze as a scope addition alongside D73. D75 restored it, on the grounds that the deletion had never actually been asked for and that narrowing escape options deserves a deliberate decision — and said in terms that it stays "until that call is made". The call is now made: delete it. So D77 is not a reversal of D75; it is the decision D75 explicitly deferred, arriving as intended.

THE PRODUCT REASONING. A free tap that defers the block is a bail-out with no cost, sitting next to a reprieve that has one. For most people it dominates: nobody walks twenty steps for a smaller version of what one tap gives free, which is exactly why D50 had to assert an inequality between the two constants to keep the challenge from shipping dead on arrival. Removing the free option removes the need for that guardrail and makes the screen say one thing instead of two — you can leave, or you can earn your way past. That is a coherent stance for an anti-doomscroll app in a way that "leave, earn your way past, or just tap here" is not.

WHAT WAS DELETED, all of it and not merely the UI: `GRACE_MINUTES`, `GRACE_MS`, `block_snooze`, the button in `overlay_block.xml`, `BlockScreenController`'s `onSnooze` parameter and its wiring, and `OverlayController.onSnooze`. D50's asserted inequality goes with it — it constrained a comparison that no longer has two sides — replaced by a boundedness assertion that stands on its own. The persisted grace deadline (`SettingsPrefs.graceUntilMs`) is UNCHANGED in shape; it simply has one writer now instead of two.

THE PLAY-FACING STRING, which is the easiest thing to miss and the most expensive to get wrong. `accessibility_service_description` — the text the SYSTEM shows under the Accessibility toggle — promised "you can always leave the block, and you can always ask for a few more minutes". Deleting the snooze made the second clause false, in the one string Play policy requires to match the service's actual function. It now reads "You can always leave the block." A stale promise there is not a copy nit; it is a policy claim about what the app does.

**INVARIANT 6 IS UNTOUCHED, AND THIS IS THE PART TO BE CAREFUL ABOUT.** A snooze was never an exit — it deferred the block and kept the user IN the app. Invariant 6 names Exit and hardware Back; both are on all three panels, and neither has ever depended on these constants. But the ACCEPTED CONSEQUENCE is real and needs stating: on a device that can run no challenge at all (`ChallengeAvailability` empty — no step sensor, no accelerometer, no proximity, or the motion permission declined for the step specs), the block panel is now **Exit and nothing else**. That is a strictly harder block, and still a fully escapable one, and "leave the app" being the sole option on an anti-doomscroll app's block screen is a defensible place to land rather than a degradation to apologise for.

It is also the state where a regression would be worst, because Exit is now the ONLY control on that panel — an edit that hid, renamed or reordered it turns "strict" into "trapped" with nothing between the user and a P0. So this ADR ships a test. `BlockEscapeTest` asserts against the SHIPPING `overlay_block.xml` that every panel carries its own Exit, that no Exit has a visibility or enabled attribute, that Exit precedes the challenge button in traversal order, that `block_challenge` defaults to `gone` (so the sensorless rendering IS the default rendering), that `block_snooze` is absent, that the root is `BlockRootView` (focus-independent Back, D71), and that the stack sits in a `fillViewport` ScrollView so Exit is reachable at any font scale. It reads XML rather than driving the controller because `BlockScreenController` needs a real Context and the unit-test `android.jar` is a throwing stub — the precedent is `GuiltPackTest`, which parses the real bundled asset for the same reason: a resource that only fails on a device is a resource nothing is guarding. HANDOFF Run J is the device half.

IF THIS IS EVER REVERSED AGAIN: the button, the string and the handler move together, in either direction. A translated string with no control is invisible; a control with no handler is a dead button on a screen covering another app, which is the failure shape D71 spent a P0 on.

**D78. The app opens on a welcome screen, not on a permission request. Pass A of the appeal work: value before the ask, a quiet neutral tier, and empty states that are not failure states (2026-07-29).**

THE PROBLEM, found by researching the category rather than by staring at our own screens. First run was Disclosure → Accessibility → Overlay → Dashboard, which means the very first thing a new user saw was a request to switch on an **Accessibility Service** — the most invasive permission Android offers, and the one users are most reasonably suspicious of — before the app had shown them a single thing of value. The 2026 digital-wellbeing consensus is explicit that this is backwards: show value, then ask, and profile progressively. This was almost certainly this app's largest first-run drop-off, and nothing in the codebase would ever have surfaced it, because the flow was *correct* — it was just unpersuasive.

THE FIX IS ONE SCREEN THAT ASKS FOR NOTHING. `WelcomeScreen` shows the HEALTHY mascot, one question, one sentence, a dead counter, and a button into the existing disclosure.

**INVARIANT 5 IS UNTOUCHED, and the distinction is worth stating precisely because it looks like the rule being bent.** Play policy requires an in-context disclosure BEFORE the user is sent to enable the service. It does not require that disclosure to be the first pixel the app ever draws. The welcome screen requests nothing, grants nothing, and deep-links nowhere; it explains and hands off. Adding a step in FRONT of the disclosure is legal. Putting anything that REQUESTS the permission in front of it would not be, and that is the line a future edit could cross without noticing — which is why the routing moved out of an untested `when`.

**THE ROUTE IS NOW A PURE FUNCTION WITH A TEST.** `OnboardingRoute.stepFor(welcomeSeen, accessibilityEnabled, canDrawOverlays, overlayStepDismissed)` replaces the inline `when` in `MainActivity`. That block was survivable at three arms; adding a screen ahead of a policy-mandated one is not a change to make in an expression nothing asserts. `OnboardingRouteTest` pins that the disclosure is unreachable-past while accessibility is off (exhaustively over the other two flags), that welcome hands off to the disclosure and never past it, and that the route is total across all sixteen input combinations.

**THE `welcomeSeen && !accessibilityEnabled` GATE, which is the non-obvious half.** Gating the welcome on `!welcomeSeen` alone would shove a "here's what this app does" introduction at an EXISTING user on their first launch after upgrading — someone who granted the permission weeks ago, whose `welcome_seen` pref is false only because the key did not exist before. It would read as the app having reset itself. If the service is already on, the introduction has demonstrably already happened, whatever the flag says. The pref is written on the way OUT of the screen, not on the way in, so a user who force-quits mid-read gets it again rather than losing it to a launch they never finished.

**THE COPY CLAIMS NOTHING ABOUT THE USER.** The first draft opened with "You scroll about 2 hours a day" — a statement about a person we have not measured. STORE_COPY.md's rule against unsupportable claims governs in-app copy, not only the listing, which is the same trap D77 caught in `accessibility_service_description`. Replaced with a question — "How much do you actually scroll?" — which claims nothing and is better copy anyway: it opens the curiosity gap that motivates granting a permission people are right to be wary of. For the same reason the preview card shows a REAL ZERO rather than a staged counter ticking upward: a fake demo would be the first thing the app ever said to the user, and this product's entire pitch is that its numbers are honest.

**THE QUIET TIER (`ON_LIGHT_MUTED`, `ON_LIGHT_FAINT`).** Every colour in `Brand` was either IDENTITY (cap, brain, brim) or STATE (healthy/cracking/fried). There was no neutral — so a screen needing a divider, a gridline or a "nothing here yet" ground had nowhere to get one and would have invented its own, which is precisely how the five drifting ARGB lists D58 consolidated came into being. Both are cobalt-biased rather than true greys, because a pure mid-grey beside this palette reads as unconsidered. They land in `Brand.kt` and not in the Compose theme for D58's original reason, unchanged: the block screen and the bubble cannot read a theme, so a brand colour lives in that file or it does not exist. Naming follows the existing `ON_DARK_MUTED`/`ON_DARK_FAINT` pair exactly — the fact that the light-side twins were simply missing is what confirms this was a gap rather than an addition.

**EMPTY STATES, AND WHY THE TONE IS THE DESIGN.** Three screens rendered blank with no data: Today's "By app" card was a titled empty box, and the Apps tab was a bare heading over literally nothing. In most apps an empty state means something is missing. In THIS app it means the user has not doomscrolled today — the outcome the entire product exists to produce. So it must not borrow the visual language of failure: no error colour, no apology, no sad illustration. A hairline rather than a card, because drawing a container around nothing makes the nothing look like a broken component. It is also the first thing a brand-new user sees immediately after granting an Accessibility Service, so it doubles as proof the app is working and simply has nothing to report yet.

ALSO CORRECTED HERE: STORE_COPY.md still listed "two sanctioned ways past" the block, naming "5 more minutes" — stale since D77 deleted it. That file is the pre-submission claims gate, so a stale entry there is a compliance defect rather than a documentation one, and it is exactly the class of miss D77 caught in the service description.

NOT IN THIS PASS, deliberately: the Insights screen (Pass B). It needs range queries, streak computation and a ViewModel before any UI, because every `DailyCountDao` query is `WHERE date = :date` — the rows are kept forever (invariant 4) but nothing can read history yet. Splitting it out keeps this pass free of data-layer work and lets that one be judged on its own. Milestones and the block restyle (Pass C) follow it. NOT TOUCHED: detection, limits, gating, the overlay, the block, or any safety invariant — the bubble is not in this diff at all.

**D79. The daemon JVM pin drops its vendor and keeps its version, correcting D67. A bare `toolchainVendor` is a build that cannot start, and foojay does not rescue it (first CI run, 2026-07-29).**

THE FAILURE, from the first CI run this project ever had:

```
Unable to download toolchain matching the requirements
({languageVersion=21, vendor=JetBrains, implementation=vendor-specific,
nativeImageCapable=false}) from 'null', due to:
No defined toolchain download url for LINUX on x86_64 architecture.
```

`gradle/gradle-daemon-jvm.properties` carried `toolchainVendor=jetbrains` alongside `toolchainVersion=21`. GitHub's runners ship Temurin and Zulu, never JBR, so the daemon could not start at all — this failed before a single task ran.

**D67 WAS INTERNALLY CONTRADICTORY, and that is the actual finding.** It stated two things that cannot both hold: that CI runs Temurin and local runs JetBrains "deliberately", and that "the pin is DELIBERATELY NOT RELAXED... if Gradle's daemon criteria refuses Temurin, the fix goes in this file — never in the pin." But a vendor-pinned daemon does not merely *prefer* JBR, it *requires* one, so no change confined to the workflow could satisfy it except downloading JBR on every run. The instruction D67 left for its successor was unfollowable, and it was written without the evidence that would have shown that — there had never been a CI run.

**THE VENDOR LINE WAS NEVER CHOSEN.** The file's own first line reads `#This file is generated by updateDaemonJvm`. That task captures the vendor of whatever JVM is current, and the generating machine builds through Android Studio's bundled JBR. So a machine-specific accident was preserved as though it were a decision, and then defended by an ADR written around it. Worth noting as a pattern: an auto-generated file that lands in a commit acquires the authority of a deliberate choice unless someone checks, and the comment D67 wrote *on top of* it made that authority look researched.

**FOOJAY IS NOT THE ESCAPE HATCH, and assuming it was cost a round.** `settings.gradle.kts` applies `foojay-resolver-convention` 0.10.0, which makes it reasonable to expect Gradle to auto-provision a JBR. It does not. The foojay resolver serves ORDINARY Java toolchains; the daemon criteria goes through `DaemonJavaToolchainProvisioningService`, which consults only explicit `toolchainUrl.<OS>.<ARCH>` entries in the properties file. With none defined it resolved a download URL of `null` — which is exactly what the message says, once you know the two mechanisms are separate. This is now written into the workflow header so the next reader does not repeat the inference.

**THE FIX: drop the vendor, keep the version.** This is not a relaxation of D67's intent, it is the restoration of it. D67 wanted "local and CI... to run different JVMs of the same version", and a version-only pin is precisely that mechanism. Local still runs JBR because Android Studio's JVM is what a developer has; CI runs the runner's preinstalled Temurin; both are held to Java 21, which is the property that actually protects the build. Verified: `gradlew --version` now reports `Daemon JVM: Compatible with Java 21, any vendor`, with the launcher still on JBR locally.

**WHY NOT THE OTHER TWO OPTIONS.** Installing JBR in CI (`actions/setup-java` does support `distribution: jetbrains`) would honour the letter of "never relax the pin", but it entrenches an accidental line and pays a 30–60s download on every Android run — JBR is not in the hosted toolcache and Temurin is — against a 2,000-minute budget D68 treats as a real constraint. Adding `toolchainUrl.LINUX.X86_64` is what the error literally asks for, but it hardcodes a JBR tarball URL that rots on every release and changes local resolution too. Neither buys anything, because **there is no build-correctness reason to demand a vendor for a Gradle daemon at all** — JBR matters for running the IDE, not for building. That question is what should have been asked before the pin was defended.

**THE RULE THAT REPLACES D67's:** a vendor pin must ship WITH the matching `toolchainUrl` entries for every platform the build runs on, or with a runner that installs that vendor. A bare vendor line is not a strict build; it is a build that cannot start on any machine that does not already happen to have that JDK.

NOT CHANGED: the Gradle version, the wrapper, `foojay-resolver-convention` (still correct for ordinary toolchains), the workflow's Temurin setup, or anything in the app. Verified locally with CI's exact command minus `lintDebug`, which fails only on the machine-specific `local.properties` PropertyEscape error the workflow header already documents as unable to fire on a runner — 308 tests pass, `assembleDebug` and `compileReleaseKotlin` green.

**D80. Scrolling TIME is rolled up daily before the raw events are pruned, so an honest number survives invariant 4. DB v4 adds `daily_minutes` (2026-07-29).**

THE PROBLEM, and it is a schema fact rather than a preference. The Insights screen (Pass B) wants "time saved" derived from real sessions instead of a flat count × 6s. Sessions need timestamps. This app has exactly one source of timestamps, `scroll_events`, and **invariant 4 deletes it after seven days**. `daily_counts` is kept forever but carries no time at all — `(date, platform, count)`. So a 30-day view could show session-accurate time for its first week and nothing but a flat guess for the rest, which is two different measurements presented as one series.

REJECTED IMMEDIATELY: extending raw retention. Invariant 4 is not a tuning knob — it exists so the app never accumulates a long-lived, timestamped behavioural log of a person's scrolling. Buying a nicer chart with a permanent record of when someone was on their phone is the wrong trade, and it is the trade a privacy-pitched product least gets to make.

THE SHAPE: **compute while the evidence exists, keep only the answer.** A rollup pass runs immediately before each prune, distils each day's raw timestamps into one integer, and writes it to a new `daily_minutes` table. The raw log then disappears exactly on schedule. What survives is one row per day — the same shape, cardinality and privacy posture `daily_counts` has had since D14. Nothing is retained that was not already retained in kind.

**ORDERING IS THE WHOLE DESIGN.** `maybePrune` became `rollUpAndPrune`. Pruning first would discard the timestamps before the number is derived, which is the entire failure this ADR exists to avoid; the two operations are not independent and must never be reordered or split across passes.

**PAST DAYS AND TODAY ARE WRITTEN WITH OPPOSITE CONFLICT RULES, and this is the subtle correctness core.** The prune cutoff is ROLLING (`now − 7d`), so the oldest day does not vanish at once — it bleeds events gradually through the day. A second rollup of such a day would see only the survivors and overwrite a complete figure with a partial one; the number would silently SHRINK days after it was correct, and nothing would look wrong. So past days use `insertIfAbsent` (IGNORE — first write wins, and the first write for a completed day is complete, since a finished day keeps all its events for roughly six more days), while today uses `upsert` (REPLACE — it is still accumulating, every pass strictly dominates the last, and its events are hours old so a partial read is impossible).

**SESSIONS, not first-to-last.** `SessionRoller` splits a day's timestamps wherever silence exceeds `SESSION_GAP_MS` (5 min) and sums each sitting's span. Measuring first-to-last across a day would count the eight hours between a morning scroll and an evening one AS SCROLLING — the single worst thing this number could do. The gap value is chosen on an asymmetry rather than a guess: over-splitting costs accuracy in a figure nobody reads (how many sittings), under-splitting corrupts the figure everybody reads (how long), so when in doubt it splits. Each session also credits `TAIL_SECONDS` for the item still on screen when it ended — reusing `TimeEstimate.AVG_SECONDS_PER_ITEM` rather than inventing a second constant, so the flat and session estimates stay anchored to one assumption. Without the tail a one-event session would be zero, recording someone who opened Reels, watched one and left as having spent no time.

**SECONDS, NOT MINUTES, in storage.** The feature is spoken about in minutes and the UI will render minutes, but a REAL column accumulates float error when a screen sums thirty rows and turns every test assertion into an epsilon question. Integer seconds is exact, sums exactly, and converts at the edge.

**A NEW TABLE, NOT A COLUMN ON `daily_counts`.** That table is PK `(date, platform)` and deliberately mirrors the server shape (D14), so a column would either break the mirror or force the server to grow one. Time is also a per-DAY quantity: a sitting that moves from Reels to Shorts is one sitting, not two.

**THE RAMP, ACCEPTED AND DOCUMENTED.** A rollup can only start from the day it ships. Every day older than that has already had its timestamps pruned, so its time can never be more than a flat estimate — the history does not exist to recover. B2 must therefore RENDER the boundary rather than blend across it, which is what `observeEarliestRolledDate()` is for. It self-heals in about a month. Stating it here so the Insights screen is not written as though the series were uniform.

MIGRATION 3→4 creates the table and back-fills nothing, because nothing is back-fillable. `MigrationSqlTest` is new and asserts every hand-written `CREATE TABLE` against Room's exported schema JSON: a mismatch throws `IllegalStateException` on the UPGRADE launch, on a user's device, and cannot fail on a fresh install — so it survives every ordinary test. Both prior migrations carried a comment claiming they matched the generated schema; that claim was true and entirely unenforced. The test also pins that the exported version matches the declared one and that no version step lacks a migration. It was mutation-checked: deleting one space from the SQL fails it.

NOT TOUCHED: detection, counting, the overlay, the block, `daily_counts` itself, or the prune's seven-day window. `clearAll()` now also clears `daily_minutes`, since a time history for days whose counts were just wiped would be a leak of exactly the thing the user asked to delete.

**D81. Streaks are computed, never stored, and they are PROVISIONAL until the server day boundary lands (2026-07-29).**

`StreakCalculator` is a pure function over daily totals: current run ending today, and the best run inside a caller-chosen window. No Android imports, no clock — `today` and `from` are parameters, which is what makes it testable and what makes the Phase-3 migration a change of caller rather than of logic.

**THE PROVISIONAL PART, which is the reason this is an ADR and not just a function.** A streak is *entirely* a claim about which day a count belongs to, and that question does not have its final answer yet. D14 records the device-local `LocalDate` as an INTERIM boundary; invariant 2 says the real one is the user's timezone computed SERVER-side, arriving in Phase 3. So a count recorded at 00:30 local may later migrate to the previous day — joining two runs, or splitting one. **A "best streak" displayed today can legitimately change.**

The consequence is a constraint on Pass C, recorded now because it is much cheaper than discovering it later: **milestones must DERIVE from this function, never cache its output as a durable achievement.** An awarded "7-day streak" badge that becomes arithmetically false after the Phase-3 boundary shift is worse than no badge — it is the app contradicting its own history, on a screen whose entire job is to be trusted. Deriving costs nothing; the data is already there.

TWO DEFINITIONS a reasonable implementer would get the other way, so both are pinned by tests:

**A day is under at `total < limit`**, matching `BlockPolicy` exactly. The block fires at `count >= limit`, so `<=` here would call the day you were blocked a success — the streak would disagree with what the user actually experienced.

**A day with no row counts as UNDER.** `daily_counts` rows are created lazily on first advance, so an absent day means zero scrolls: phone off, app unused, on holiday. Treating a gap as a BREAK would punish someone for a day they did not doomscroll at all, which inverts the point of the number. It also means "best" is bounded by the caller's window rather than by history — a 7-day view can never report a 30-day best, which is why `from` is a parameter.

**Today is judged on where it currently stands**, not deferred to midnight: over the limit already means current = 0. That is honest — the user blew it and the screen should not pretend otherwise for up to 24 hours — and it means the streak can be lost later in the same day, which is correct rather than a glitch. Rows dated in the FUTURE (a clock change, a restored backup) are ignored, so they cannot extend a streak the user has not lived.

NOT BUILT HERE: any UI. This is Pass B1, data only — deliberately split from the Insights screen so a chart bug could never leave a half-migrated database behind.

**D82. The Insights screen, on B1's data. The Apps tab is replaced; the long view buckets into weeks; the time tile names what it measured (2026-07-29).**

Pass B2 — a screen and a ViewModel. No new storage, nothing written to Room, nothing that can reach detection or the overlay.

**THE APPS TAB IS GONE, AND NOTHING WAS LOST WITH IT.** It showed per-platform bars for TODAY only — the same data the Today tab's "By app" card already carries — so it was partly redundant before this screen existed. Insights supersedes it by adding the dimension it never had: a range. Keeping both would have shipped two tabs of near-identical bars differing only in time window, which is how navigation starts to feel unconsidered. The `AppsTab` composable was DELETED rather than left unreferenced, and the nav icon is reused because it still means the same thing.

**THE CHART CARRIES ONE SERIES, AND THAT IS A DESIGN DECISION RATHER THAN A SIMPLIFICATION.** Bars are the daily (or weekly) TOTAL, nothing more. A single series needs no legend — the heading names it — and, more importantly, no categorical palette. A multi-series chart would have required hues validated for colour-blind adjacency, and D58's identity colours were sampled from the mascot for brand reasons and never validated for that. Rather than invent colours D58 forbids, the chart uses one hue and lets LABELS carry identity — exactly the call the old `AppsTab` documented and the bubble's breakdown panel already ships. Three surfaces, one rule.

The only colour exceptions are STATUS, not identity: over-limit bars take the cracking orange, the in-progress bucket takes coral. That is the one sanctioned reuse of a reserved colour, and both are additionally communicated by something other than hue — position relative to the limit line, and a label reading "This week so far".

**THE LIMIT LINE, and why the plot scales to include it.** A bar without the threshold it is judged against is a number with no verdict, and the limit is the single thing this app is about. The plot's ceiling is `max(tallest bar, limit)` rather than the tallest bar, so the line is always on the chart. Scaling to the bars alone would push it off the top precisely when the user is comfortably under — which is when seeing the headroom is most encouraging.

**THIRTY THIN BARS WOULD HAVE BEEN UNREADABLE, so the long view buckets by week.** Owner call, and correct: at phone width thirty bars are three or four pixels each, individually untappable, and they present day-to-day noise as signal. A month view is asked a different question than a week view — "is this getting better" rather than "what happened on the 14th".

**THE WINDOW SNAPS BACK TO A MONDAY, which is the non-obvious part.** Four complete calendar weeks plus the current partial one, so **exactly one bucket is ever partial: the last**. A literal trailing 30 days would clip the OLDEST week too, producing a short first bar that looks like a real dip but is only an artifact of where the window fell. Two partial buckets are two things to explain; one is a caption. The consequence is that the long view covers 29–35 days depending on the weekday, so the control reads "Weekly" rather than "30 days" — a label claiming a precise thirty would be false about a third of the time. Weeks start Monday (ISO-8601) rather than `WeekFields.of(locale)`, because a locale-derived boundary makes every bucket edge and every test depend on device region.

**THE PARTIAL BUCKET IS LABELLED, NOT MERELY COLOURED.** An in-progress week is genuinely shorter than the ones beside it, and without a label a Tuesday reads as a collapse in usage. It says "This week so far". Same principle as the time caption below, and as D80's refusal to blend measured with estimated time: when a number covers less ground than its neighbours, say so rather than letting the shape imply something untrue. The partial bucket also counts ONLY days that have happened — summing the whole calendar week would read rows that cannot exist, and would silently inflate the current week if a clock change ever created one.

**THE TIME TILE NAMES WHAT IT MEASURED.** D80's ramp: rollups only exist from the day it shipped, so the session-derived figure can cover less of the range than the counts do. Rather than sum a partial window and present it as the range total, the caption reads "Time measured since 29 Jul · earlier days show counts only", and disappears once the rollup catches up. `TimeEstimate.hoursLabel` takes SECONDS specifically so a flat count estimate cannot be formatted into the slot reserved for a measurement.

**TODAY'S BAR AGREES WITH THE TODAY TAB BY CONSTRUCTION.** The repository's range reads compose `observeTodaySummary()` rather than reading `daily_counts` directly, because today's Room row lags the in-memory pending counts by a DB round trip (D39/D65). A range query trusting the table alone would draw a final bar one or two lower than the hero numeral one tab-switch away — the D35 defect, in the place it is most visible. Composing the existing Flow means there is one merge rule in the class and both paths run it. The per-platform read cannot use the same override, because its date dimension is collapsed and today's contribution is not separable afterwards; it queries up to YESTERDAY and adds today's merged per-platform counts on top. Subtracting an assumed Room value instead would mis-count exactly when the two disagreed, which is the only moment it matters.

**STREAKS ARE RECOMPUTED EVERY EMISSION, never cached** — D81 is explicit: the day boundary is interim (D14/invariant 2) and a stored streak can become arithmetically false in Phase 3. The daily average divides by ELAPSED days rather than the nominal window, or a young current period would drag it down and read as an improvement that has not happened.

**PERFORMANCE.** One immutable `InsightsUiState` per emission — every sum, gap-fill, bucket and streak computed once in the ViewModel, never during layout or draw. Bars are weighted `Box`es inside a `Row`: no `Canvas`, no custom measure, nothing derived while rendering. `flatMapLatest` on the range means exactly one window is ever observed, so switching tears the old queries down rather than leaving both collected. A separate `InsightsViewModel` rather than growing `DashboardViewModel`, which already owns today's counts, the guilt line, permission health and every Settings toggle — folding a second screen into it is how that class becomes the God-class CLAUDE.md bars.

NOT IN THIS PASS: milestones (C1 — and it must DERIVE streaks, never cache a badge), the block restyle (C2), and the launch-jank work (P, which starts by measuring). Nothing here touches storage, detection, the bubble or the block.

**D83. The punishment escalates: a guilt line stays up 6.5s, and every challenge gets harder each time it buys a reprieve (2026-08-03).** FIVE DAYS OF REAL USE, TWO FINDINGS, ONE MECHANIC. Both are about a moment where the app asks something of the user and the user does not actually receive it. (1) THE DISPLAY WAS TOO SHORT TO READ. `GuiltCadence.DISPLAY_MS` goes 4s to 6.5s. This is not a taste complaint being indulged: an unread line was never shown, and the pack, the four tiers, the weighted no-repeat rotation, the daily deck and the whole cadence curve exist to put ONE line in front of somebody who then reads it. Four seconds is fine for "you've scrolled 200" and much too short for the lines carrying the product's voice, which are the longer ones and the ones actually worth reading -- the pill collapsed back to the count mid-sentence, every day, for five days. Six and a half covers the pack's longest lines at an unhurried pace with room to look up at the bubble first, which matters because the line is not what the user was looking at when it appeared. THE DERIVATION DID ITS JOB, AND THAT IS THE POINT WORTH RECORDING: `MIN_GAP_MS = DISPLAY_MS + COUNT_VISIBLE_MS` recomputed to 8s with no second edit and no call site to chase, because D46 refused to write 5.5 as a literal. There is no `4_000` or `5_500` anywhere in the tree -- `OverlayController` posts the collapse from `GuiltCadence.DISPLAY_MS`, `GuiltFiring` gates from `GuiltCadence.MIN_GAP_MS`, and `GuiltCadenceTest`, `GuiltFiringTest` and `GuiltPoolMath` all read the symbols -- so a product decision about legibility cost exactly one constant. D46's guarantee survives unchanged: every line still gets its whole readable life and the user still gets the counter back before the next one, because the gap is still the display plus a counter-only window by construction. WHAT IT COSTS is frequency and nothing else: the practical ceiling falls from ~11 lines a minute to ~7.5, still relentless at the top of the curve, and seven lines that get read beat eleven that do not. THE SCHEDULE IS UNTOUCHED and so is the content bill -- `GuiltPoolMath.firesPerDay` advances its clock FROM `MIN_GAP_MS` every step, deliberately so the gap never binds in the sizing simulation, so every T3=40 / T4=150 figure is unchanged. Eligibility is measured in scrolls and display in seconds; only the second one moved. Suppression staying PENDING rather than dropped (D46's third load-bearing edge) is what makes a longer gap safe: no line and no tier crossing is lost, each is deferred to the first emission after the gap elapses. `GuiltCadenceTest` gains a floor assertion at 6s -- deliberately BELOW the shipped 6.5 -- because it pins the LESSON rather than the tuning: a future edit chasing frequency may lower the display, but not back under the point where the pack's longer lines stop being finishable. (2) AN ADDICTED USER DOES NOT RESPECT A STATIC CHALLENGE. Walk twenty steps is a genuine interruption the first time and muscle memory by the third block of the day: stand up, pace the kitchen without looking up, sit back down, resume. Since D77 deleted the free "5 more minutes", a completed challenge is the ONLY reprieve -- the challenge IS the entire price of buying time -- and a price that never moves gets absorbed. So the target escalates, per challenge, per completed reprieve, within a day. TWO CURVES, because the units are not alike. Counts step by ten (`walk_20` becomes 20/30/40/50/60/70/80; `jump_10` becomes 10/20/30/40); holds double (`face_down_30` and `forehead_30` become 30/60/120s). Doubling a count compounds far too fast -- walk would reach 160 in three reprieves, which is a walk around the block rather than a break from the sofa -- while doubling a duration is simply how anybody describes a duration's next rung. `EscalationCurve` is a property of the SPEC, for the same reason `sensorStrategy` is: it is per-challenge data, not a branch on `ChallengeType`, and the next challenge picks its curve from a written menu. ONE CAP, SHARED: `CAP_MULTIPLE = 4`, so the ceiling is derived from each spec's base rather than being a second per-spec number that can drift from the base it is meant to bound (the same rule that keeps `CHALLENGE_GRACE_MS` derived from its minutes). THE CAP IS AN INVARIANT-6 DEVICE, NOT A DIFFICULTY KNOB, and this is the part to be careful about. Uncapped escalation is uncapped in the only direction that matters: within a day of heavy use, doubling reaches numbers no human completes, and a challenge nobody can finish is a reprieve that does not exist. The block would still be dismissible -- Exit and Back never read any of this -- but "the only way to buy time is now impossible" fails the SPIRIT of invariant 6 while keeping its letter, and a screen covering somebody else's app is not where to be clever about that distinction. THE HOLDS CAP AT TWO MINUTES SPECIFICALLY because D54's anti-cheat is reset-on-break: failure probability compounds with duration, a four-minute face-down hold surrenders everything to one twitch at 3:59, and the ring is pointing at a table so the user cannot even see it happen. That reads as broken rather than strict, and D9's anti-uninstall principle applies to the mechanic and not just to the copy -- D50 said so in as many words. Forty jumps is likewise the most aerobic thing this app will ever ask for, and is where `jump_10` stops. `targetFor` is TOTAL: `uses` is coerced non-negative, the result is coerced to the cap, and `DOUBLE` multiplies UP TO the cap rather than shifting -- `target shl uses` goes NEGATIVE around 27 uses and a naive `coerceAtMost` would accept that happily, producing a challenge that completes instantly, which is the same feature failing in the other direction. Bounded operation first, exactly as `BlockLimits.clampLimit` ranges before it snaps. `ChallengeEscalationTest` pins the cap against `Int.MAX_VALUE`, `Int.MIN_VALUE` and the overflow neighbourhood, structurally across every enabled spec so the next challenge added inherits the guarantee rather than needing its own line. ESCALATION IS APPLIED EXACTLY ONCE, AND WHERE. `OverlayController.offerable()` maps the available specs through `ChallengeEscalation.escalated(spec, ownUses, otherUses)` at the single point a challenge is offered, and the raised SPEC -- not a bare "effective target" -- is what flows onward. The target is read in four places (the chooser row's label, the challenge panel's prompt, the ring's label, and the `ChallengeProgress` the sensor counts into), and threading a second number to all four alongside the spec is precisely how the prompt ends up promising sixty seconds while the engine counts thirty. That is the drift D50's promptRes-is-a-format-string rule exists to prevent, applied one level up: every one of those call sites keeps reading `spec.target` and none of them learns that escalation exists. `id` is deliberately unchanged, so `forId`, the surprise-me exclusion and every greppable log line still key on a stable identifier across rungs. The chooser row closes over the escalated spec, and "Surprise me" draws from `offerable()` too, so both paths carry the same rung and neither can hand the sensor a target the user was never shown. Escalating an already-escalated spec would COMPOUND -- the raised number would be read as a base -- which is exactly why there is one application point, and a test pins that reason rather than merely the arithmetic. IT ESCALATES ON COMPLETION ONLY, read from `ChallengeController.active` before `hideBlock` nulls it, so what escalates is provably the challenge that just completed. Not on start and not on cancel: somebody who opens the chooser, reads the rows and backs out has bought nothing, and charging them for looking is the same mistake as banking partial progress across blocks (D50g). RESET IS DAILY, and it is a property of the READ rather than a job that runs. `SettingsPrefs.challengeUsesToday` returns an EMPTY MAP whenever the stored day key is not today, so there is nothing to schedule, nothing to run at midnight, and no way for a device switched off across the rollover to wake up still escalated -- the same shape as `GuiltFiring` baselining on a day change rather than being told about one. Daily because the whole app is denominated in days: the limit is daily (D76), the counts are daily, the guilt cadence baselines per day, streaks are per day (D81). Escalation crossing midnight would be the only mechanic here that does not, and a fresh morning opening at "hold it for two minutes" charges the user for yesterday. The alternatives were weighed. Decay after N clean hours is a stronger anti-addiction rule and is the better SECOND move -- it needs a persisted last-block timestamp, a decay function, and it gives the user a number they cannot predict. Never resetting was rejected outright: within days every challenge pins at its cap and escalation degenerates into a static challenge at a higher number, which is the exact thing this feature exists to fix. Device-local `LocalDate`, the same interim D14 boundary the counts and the cadence use; it moves to the server when they do. The stale-day branch SWEEPS every challenge's counter rather than only rolling the day stamp -- a real bug and not untidiness, because `challengeUsesToday` gates on ONE shared day key, so writing today's stamp over yesterday's counters would make every challenge the user did NOT complete today read back at yesterday's rung. Settings, Clear data drops it beside `clearGrace`: a wipe that left escalation standing would ask eighty steps of somebody whose history now says they have not scrolled at all. THE REWARD DOES NOT ESCALATE, and that is D53 re-affirmed rather than overlooked. `CHALLENGE_GRACE_MINUTES` stays flat at 15 for every challenge at every rung. Pricing an escalated hold above an escalated walk would re-punish precisely the user who picked walking because they cannot jump -- choice here is accessibility, not optimisation. D50's reward asymmetry has no competitor left to be dominated by, since D77 deleted the free tap and the asserted `CHALLENGE_GRACE_MS > GRACE_MS` went with the thing it constrained; escalation therefore raises the PRICE of buying time across a day while the payout stays fixed, which is the intended direction. THE ROTATION HOLE IS CLOSED BY A SPLIT CHARGE, NOT BY PICKING A SIDE. Purely per-challenge state is dodgeable: rotate walk to jump to face-down to forehead and all four stay near base, so the price stops climbing after the third block of the day, which is exactly the absorption this feature exists to prevent. Purely GLOBAL state closes it and costs too much — with one shared counter both holds sit pinned at their 120s cap from the SECOND reprieve of the day even if the user has never done a hold, so the middle of every ladder stops existing and escalation collapses back into the static-challenge-at-a-higher-number failure it replaced. So a challenge is charged its OWN reprieves plus one for every `GLOBAL_DIVISOR = 2` earned elsewhere (`ChallengeEscalation.effectiveUses`). A full lap of four now leaves walk 40, jump 30 and both holds at 120s rather than leaving everything near base, so cycling is no longer a discount — while the challenge actually being leaned on is always strictly the hardest (four reprieves all on walk gives walk 60 against jump 30), which is the signal real use surfaced and the whole reason to keep per-challenge state at all. Integer division rounding DOWN is deliberate: the first reprieve elsewhere is free here, because otherwise a single completion would raise all four at once and the model would be pure-global with extra steps. `effectiveUses` is total for the same reason `targetFor` is — both operands are persisted preferences, and `own + other/2` overflows Int at the top of the range, where a naive Int sum would wrap NEGATIVE and `coerceAtLeast(0)` downstream would quietly turn it into a base-target challenge, i.e. a free reprieve. THE CORRECTION THIS CARRIES, recorded because the first draft of this ADR argued the opposite: per-challenge state was described as PROTECTING the limited-mobility user, and it did the reverse. Rotation dilution was only ever available to somebody who can physically do several challenges — a user with no pedometer who cannot jump in a first-floor flat at 2am had exactly one option and therefore no discount at all, while a user with all four got a fourfold one. Per-challenge dilution scaled with mobility. Charging part of every reprieve to the whole set is what makes the rate the same for both, so the split closes an equity hole as well as an evasion one. Both numbers come from ONE preferences snapshot (`SettingsPrefs.challengeUsesToday` returns the whole map): read separately they could straddle midnight, with own returning 0 from the new day against a total still reflecting the old one, pricing a fresh challenge as though it had been used. The total sums every ENABLED challenge rather than the available ones, because a reprieve earned this morning with a challenge whose permission was revoked since was still a reprieve. INVARIANT 6 IS UNTOUCHED AND THE ARGUMENT IS SHORT. Escalation writes to exactly one field, `ChallengeSpec.target`. It never touches the block panel, Exit, Back, `hide()` or `sweepOrphan`; Exit is first on all three panels and is reached without reading any of this. `ChallengeAvailability` is not modified and reads no target, so escalation can make a challenge harder and can never make one disappear -- a sensorless device still gets Exit alone, and `BlockEscapeTest` still pins it (D77). The cap guarantees no rung is unreachable. No detection change, no cadence-schedule change, no pack change, no storage change, no change to how the block decides to fire. 371 tests pass across 38 suites (+17 `ChallengeEscalationTest`, +1 `GuiltCadenceTest`).

**D84. Three more challenges — shake, flip, balance — and the two that were rejected for cause (2026-08-03).** Piece 2 of the five-days-of-real-use set. The suite was four and every one of them had a precondition: walk needs a room and a pedometer, jump needs floor space and a downstairs neighbour who is out, and the two holds ask for patience rather than effort so they are the only option left for anyone seated. That leaves a real user — on a train, at a desk, in a shared room, in a first-floor flat at 2am — choosing between two passive challenges, which is barely a choice, and D53 established that choice here is ACCESSIBILITY rather than flattery. WHAT WAS ADDED, AND THE GAP EACH ONE FILLS. `shake_30` is the first challenge that is genuinely tiring and genuinely available everywhere: it needs no space, no permission, no noise and no standing up, so it is the effort option for everybody the first four served badly. `flip_10` is the ATTENTION one — walking and jumping can both be done on autopilot with the mind still in the feed, but turning a phone over ten times cannot, because each turn has to complete before the next registers; it is the cheapest to perform and the hardest to do absent-mindedly, and it is the only challenge that takes the screen out of view on every second count. `balance_20` is the third hold and fills the gap the other two leave: face-down and forehead both ask you to stop and wait, which a determined user does while thinking about the feed, whereas balancing demands continuous fine motor attention and any thumb pressure tips it. ALL THREE ARE PLAIN ACCELEROMETER READS, and that was a selection criterion rather than a coincidence. The step sensors are the only ones behind a runtime permission and proximity is the only one that is genuinely absent on shipped hardware, so an accelerometer challenge inherits the most permissive availability answer the app has. The practical effect is the one that matters: a user who declined the motion permission, or whose device has no pedometer, now loses ONE row out of seven rather than one out of four. THE SHAKE DETECTOR, AND THE TRAP THAT LOOKS LIKE A TUNING PROBLEM. The obvious implementation counts oscillations of `sqrt(x²+y²+z²)`, reusing the magnitude `JumpDetector` already computes. It cannot work, and it fails in a way that reads as a badly tuned threshold rather than as a wrong idea: shake a phone along X and the magnitude is `sqrt(a²+g²)`, which is **always at or above g and never below it**, because magnitude has no sign. There is nothing to cross, so a zero-crossing counter reads zero shakes no matter how hard the phone is shaken, and the natural response — lowering the threshold — makes it count noise instead. So gravity is ESTIMATED and SUBTRACTED: a slow per-axis low-pass converges on the gravity vector and what remains is the motion the user is adding. `GRAVITY_ALPHA = 0.95` is deliberately slow (~400ms at `SENSOR_DELAY_GAME`), because a filter fast enough to track a 2–5 Hz shake subtracts the shake along with gravity and reports nothing — the same bug in a second costume. `TYPE_LINEAR_ACCELERATION` would do this in hardware and is rejected for D53's reason: absent on some devices, and on others synthesised with a filter whose lag smears the transitions being counted. THRESHOLDS ARE ABSOLUTE HERE WHERE JUMPDETECTOR'S ARE FRACTIONS OF GRAVITY, which is not an inconsistency and is worth stating because it looks like one. JumpDetector reads a signal that still CONTAINS gravity, so a device whose resting magnitude is 9.4 or 10.2 shifts all of its thresholds and they must be relative to what that device calls gravity. Gravity is already removed here, so what is measured is the user's own motion in m/s² and an absolute number is the honest way to say "this hard". `SHAKE_ON = 6.0` is ~0.6 g of ADDED motion: carrying the phone, walking with it in hand and setting it down all stay well below, and a committed shake clears it several times over. `SHAKE_OFF = 2.5` is hysteresis, because a single threshold chatters at its own boundary and turns one shake into five, and `REFRACTORY_MS = 120` catches the ringing hysteresis does not. A JUMP WILL REGISTER SHAKES and that asymmetry is deliberate: jumping is strictly harder than shaking so there is no exploit in it, while the reverse — shaking clearing the jump challenge — is exactly what D53's free-fall arming prevents and still prevents. THE FLIP DETECTOR: THE DEAD BAND IS THE DEBOUNCING. Only Z beyond ±7 counts as an orientation at all; everything between is "in transit" and is not an observation. A phone standing on edge, being carried, or propped against something therefore reports nothing rather than flickering between two verdicts, which is what a single threshold at zero would do — turning one slow turn into a dozen counted flips, so "flip 10" would complete by putting the phone down carelessly. No refractory window is needed on top, because the phone physically cannot re-cross the band without being turned over again. THE FIRST SETTLED ORIENTATION SCORES NOTHING: the challenge opens with the phone screen-up because the user just tapped a button on it, and counting that observation would hand out a free flip on every attempt — the same "first observation baselines and fires nothing" rule `ChallengeProgress.onCumulative`, `JumpDetector` and `GuiltFiring` all live by. `ORIENTATION_FLIPS` is its own strategy rather than a flavour of `ORIENTATION_HOLD` even though it reads the identical axis, because a hold is defined by nothing happening and a flip by something happening: merging them would produce one class whose meaning depended on which caller it had. Sampling is `SENSOR_DELAY_UI`, a third rate the project did not previously use, and the reasoning is stated because "just pick one of the existing two" is the tempting move — the holds' `_NORMAL` (~200ms) can sample a brisk flip-and-back only in transit and never count it, while jump and shake's `_GAME` (~20ms) is 10× the cost for a state change that has no transient to miss. THE BALANCE DETECTOR: LEVEL IS MEASURED LATERALLY, NOT FROM Z. The obvious test is `z > 9.0` and it is wrong across devices for the reason `JumpDetector.PLAUSIBLE_GRAVITY_RANGE` already documents — a resting magnitude of 9.4 or 10.2 is ordinary, so a fixed Z floor silently means 17° of tolerance on one phone and 28° on another. The LATERAL component `sqrt(x²+y²)` is `g·sin(tilt)`, so the same number means very nearly the same ANGLE everywhere: `MAX_LATERAL = 2.5` is ~15° on any device, and a test pins that it still holds on a sensor reading 10.4. Z is read only for its SIGN, to require screen-up rather than accept a phone level and upside down, which would otherwise be the face-down hold wearing a different name. THE TREMOR FLOOR IS THE WEAKEST ANTI-CHEAT IN THE SUITE AND IS DOCUMENTED AS SUCH RATHER THAN QUIETLY SHIPPED. Level alone is trivially defeated because a table is more level than any hand, so the phone must also be ALIVE: a held phone carries a small tremor, a resting one carries only sensor noise, and `MIN_TREMOR = 0.06` sits between them. That is a threshold between two CONTINUOUS quantities, unlike the others — jump needs a free-fall phase shaking cannot fake, forehead needs covered AND upright so a thumb on a table fails, a flip needs the phone physically turned over — so on a very quiet sensor a table could clear it and a very steady hand resting on a knee could fail it. It is set LOW, favouring the false pass over the false fail, because a user doing exactly what was asked while the ring refuses to move concludes the app is broken (D50's standing rule), whereas the false pass costs a reprieve to somebody who at least had to put the phone down flat and stop scrolling. If a device run shows a resting phone completing it, the fix is that one constant, and HANDOFF Run Q asks for exactly that check. HOLDDETECTOR IS REUSED UNCHANGED FOR THE THIRD TIME. `BalanceDetector` answers a boolean and `HoldDetector` times it, exactly as `OrientationHoldSource` does — so balance inherits reset-on-break, the counting-down seconds ring, the completion and break haptics and `FLAG_KEEP_SCREEN_ON` without a line of new code. That is the payoff D54 bought by keeping the timing logic pure and separate from what was being timed, and D55 collected once already; a third hold cost one small class rather than a subsystem, which is the strongest available evidence the abstraction was drawn in the right place. ESCALATION CURVES ARE DECLARED AT BIRTH, which is the entire reason this piece was sequenced AFTER D83 rather than before. `shake_30` and `flip_10` take `PLUS_TEN` (30→120, 10→40); `balance_20` takes `DOUBLE` and `ProgressUnit.SECONDS` (20→40→80) like the other holds. Twenty rather than the holds' thirty because balancing is harder per second — the other two reach a stable resting state and this one never does — and 160s of balancing a phone on an open palm would be a wall rather than a challenge, which the shared 4× cap is what prevents. Building these first would have meant editing all seven specs twice. THE CHOOSER IS ORDERED EFFORT-FIRST, passive last, and the new rows are interleaved beside the existing option each is closest to rather than appended as a block: the list is read as a menu, a seven-row chooser needs grouping by kind to stay scannable, and opening on the easiest row would make "put the phone down for 20s" the default read. A test pins the order, flagged as a product decision rather than a correctness property, because it is invisible in the data. **TWO CANDIDATES WERE REJECTED FOR CAUSE, and recording why is half the value of this ADR.** A DEEP-BREATH TIMER cannot be built honestly: no sensor this device has can verify that anybody breathed. It would be a countdown the user stares at, which is strictly WORSE than `face_down_30` — that at least enforces not looking — and shipping it would put a challenge in the registry whose "physical behaviour" is unenforced, breaking the anti-cheat discipline D53 and D54 established and that `ChallengeRegistry.IMPLEMENTED` exists to hold shut. HOLD-STILL is defeated by its own intent: a phone on a table is stiller than one in a hand, so the cheat IS the desired behaviour, and "put it down and wait" is already `face_down_30` minus the flip — strictly easier and redundant with a challenge that ships. A SPIN / TURN-AROUND challenge was designed and dropped on SAFETY: under D83's escalation it would reach four to eight consecutive full rotations, and dizziness and a fall risk for somebody doing this half-asleep at 2am is a hazard the app cannot see and cannot mitigate. That is a different kind of rejection from the other two and is recorded separately so a future session does not rediscover the idea and ship it. INVARIANT 6 IS UNTOUCHED. The new specs add rows to the chooser and nothing else; every panel keeps its own Exit listed first, Back is still `BlockRootView.dispatchKeyEvent`, and `ChallengeAvailability` is unchanged in structure so graceful absence works identically — a device that can run none of them still shows Exit alone and `BlockEscapeTest` still pins it. The reward stays flat at 15 minutes for all seven at every rung (D53, re-affirmed at D83). No detection change, no storage change, no pack change, no change to how the block decides to fire. 399 tests pass across 41 suites (+8 `ShakeDetectorTest`, +9 `FlipDetectorTest`, +8 `BalanceDetectorTest`, plus registry and escalation updates). NOT VERIFIED ON DEVICE: all three are new sensor code and HANDOFF Run Q is owed — and Run P, D83's, is still owed too.

**D85. Pack goes **72 lines to 155**. Free-only pools by tier: T1 24, T2 24, **T3 40**, T4 48; with premium, 26 / 26 / 45 / 58. **TIER 3 IS CLOSED, PERMANENTLY, AND THAT IS THE HEADLINE.** Its band is finite — 100..149, firing every 10 scrolls — so consumption is capped at five a day at ANY scroll rate, which is why D48 could name 35 as a ceiling rather than a moving target and 40 as the number that ends the discussion. At 40 FREE lines it is done: no future user, at any rate, on any day, exhausts it inside the seven-day window. `GuiltPoolMathTest`'s tier-3 assertion is now the INVERSE of the one it replaced — it asserted the shortfall, it now asserts the closure — and tier 3 has dropped out of the `short` list that the build tracks, which is precisely the transition that assertion was written to force. VOICE: the new lines lean much harder into Hinglish and desi Gen-Z register than the original 72, which were Indian-English but fairly neutral — *arre*, *bhai*, *yaar*, *chalo*, *chal*, *bilkul*, *theek hai*, *bas thoda aur*, *sasta dopamine*, *timepass*, alongside internet-native *NPC*, *delulu*, *cooked*, *aura*, *the ick*. A line reading "you have watched a lakh of these" would have passed the parser, passed the build, and shipped exactly the D47 bug the guard exists to prevent: a baked-in magnitude that is wrong at every count but one, re-shown all day by D46's cadence. The words are now banned and tested. The transferable lesson is the one worth keeping: **a content guard has to widen when the CONTENT's register changes, not only when the code does** — the guard was correct for the pack it was written against and silently became incomplete the moment the voice moved, with nothing in the build to say so. AUTHORING WENT THROUGH THE GUARD BEFORE THE FILE, not after: every new line was checked against a mirror of `offendingNumber` (plus id-uniqueness, category, access and a 110-character panel-width limit) and the writer refused to touch the asset unless all 83 passed, so a bad line could never reach a diff for someone to argue about. **THE MONETISATION FIELD IS `access`, NOT `tier`, AND THE RENAME IS DELIBERATE.** The request was for a `free|premium` "tier" per line. "Tier" already means something load-bearing here — `GuiltTier` is the INTENSITY band (1..4) that decides how hard a line may hit — and a second unrelated "tier" on the line itself would collide in every log line, every conversation and every future reader's head. They are genuinely independent axes: there are premium lines at every intensity and free lines at every intensity, and a test asserts the former, because a premium set clustered at the top would mean "pay to be insulted harder at the moment your free pool is thinnest", which reads as extortion rather than as extra. So the wire value is `access` and `GuiltTier` keeps the word it had first. MISSING AND UNRECOGNISED ARE TREATED DIFFERENTLY, and the asymmetry is the interesting part. **Absent → FREE**, because every pack written before this field existed is entirely free content — that is a fact about the corpus rather than a guess, and it meant the 72 existing lines did not have to be touched at all, so the diff is 83 additions and no edits. **Unrecognised → PREMIUM**, because an access tier this client cannot verify entitlement for is one it should withhold rather than give away; `"trial"` from a future pack must not become free content on an old client. Defaulting both cases the same way would have to pick one of those two mistakes for both, and they are not the same size. Premium lines are marked explicitly in the JSON and free ones simply omit the field, which keeps the common case quiet in a file people hand-edit and makes the fail-safe direction the silent one. **THE GATE IS REAL FROM DAY ONE, WHICH IS THE POINT OF BUILDING THE STUB NOW.** `GuiltPack.pool` gained `includePremium`, defaulting to FALSE — a call site that forgets the argument under-serves rather than leaks, and a REQUIRED parameter would simply have been passed `true` by whoever was in a hurry. The filter sits SECOND, above tone and intensity, and it is the **only** step in that chain with no widening fallback: every other filter loosens when it would return nothing, and this one must not, because a fallback here would hand paid content to a free user in exactly the situation where the free pool is thin, i.e. constantly. A free pool too small to stand alone is therefore a CONTENT bug, caught by a test over the bundled asset (`the free pool stands alone at every tier`), not something papered over at render time. Entitlement rides on `GuiltNow` alongside the day and the two clocks, because it is an ambient fact about the MOMENT of the draw in exactly the way they are: held as a field on the selector it would keep serving paid lines to somebody whose subscription lapsed until the process restarted. For the same reason `isPremium` joined the `Pinned` key — the pin's whole job is to hold a drawn line until one of its inputs changes, and entitlement is now one of its inputs. `Entitlements.isPremium` is the seam, reading a `SettingsPrefs.premiumOverride` flag that defaults false, so shipped behaviour is "everybody is on the free pack" — which is correct, because nobody can buy anything yet. **Building the stub rather than deferring the whole thing is what makes the free pool testable today**: without a gate, `access` would be a field nothing reads, no test could prove free users are adequately served, and the day billing lands it would be a change to the selection path instead of a change to one function body. When Play Billing arrives, replace that body and delete or DEBUG-fence the override — it must never survive as a way to unlock content in a release build, and that instruction is written at both ends. NOT DONE, deliberately: no purchase flow, no paywall UI, no price, no Play Billing dependency, and no user-visible mention of premium anywhere — this is content and a gate, not a monetisation launch, and `docs/STORE_COPY.md`'s claims rule will apply to whatever the offer eventually says. 407 tests pass across 41 suites (+7 `GuiltPackTest` premium-gating, +2 `GuiltTextTest`, `GuiltPoolMathTest` coverage pins rewritten). No engine change, no cadence change, no tier-threshold change, no detection, storage or block change.

**D86. Piece 3 — the bubble moves, the launcher finally has a mark, and tier 4 stops being a rounding error (2026-08-04).**

The last of the five-days-of-real-use set, and deliberately last (D83 said so): it renders what the other three produced — a seven-row chooser, escalated targets, and a pack that has now grown twice — so designing it earlier would have meant designing it twice. Three things shipped together: motion on the overlay bubble, a real brand mark plus a corrected nav glyph, and 62 new tier-4 lines. **MOTION IS SPLIT INTO A PURE POLICY AND A THIN APPLIER, AND THAT IS THE WHOLE DESIGN.** `BubbleMotion` is plain Kotlin with no Android imports — durations, the four reveal styles, the transform each one starts from, and the rule that selects one; `BubbleAnimator` is the half that calls `ViewPropertyAnimator`. Same split as `ShakeDetector` beside `AccelShakeSource` (D84) and `HoldDetector` beside the holds (D54), for the same reason: what a phone can tell you about animation is whether it *feels* right, and what it cannot tell you is whether the motion is eating something. **THE BUDGET IS THE LOAD-BEARING PART, AND IT IS TIED TO `DISPLAY_MS` BY A TEST.** D83 raised the guilt display from 4s to 6.5s for exactly one reason — lines were collapsing back to the count mid-sentence, and an unread line is a line that was never shown, so the pack, the tiers, the rotation and the whole cadence curve were paying for nothing. Every millisecond of entrance animation hands part of that purchase back. So `revealBudgetMs` is DERIVED from its two constants (it cannot be quoted independently and go stale, the same rule that keeps `MIN_GAP_MS` from ever being written as a literal) and `BubbleMotionTest` asserts it against `DISPLAY_MS / MOTION_BUDGET_DIVISOR`. The divisor is 20, so at the shipped 6.5s display motion may spend 325ms and currently spends 280. **The number is not the point; the test is.** The way D83's lesson gets un-learned is one plausible-looking constant bump at a time, by someone who has not read D83 — and tying the ceiling to `DISPLAY_MS` also means a future retune of the display carries the motion ceiling with it automatically, rather than leaving a second number to notice. **ONLY DRAW-TIME PROPERTIES. NEVER LAYOUT, NEVER WINDOW PARAMS.** Alpha, scale and translation are composited by the render thread and change nothing about a view's measured size. Animating a width, a margin, or anything on `WindowManager.LayoutParams` would relayout every frame — which is D30's surface churn arriving sixty times a second instead of once per hysteresis cycle, on a window that draws over somebody else's video. `BubbleMotion.Reveal` cannot express anything else even if a caller wanted it to, which is the useful form of that rule: not a comment, a type. The panel's open/close is the sharp case — the `VISIBLE`/`GONE` flip is D37's single deliberate window resize and it has already happened before the first animated frame, so what animates is the panel's CONTENTS catching up inside a box that is already its final size. Closing is not animated at all, because a fade-out has to hold the window at its expanded size for the duration and the pill would appear to hang before shrinking. **`settle()` EXISTS BECAUSE A LEAKED ANIMATOR ON AN OVERLAY IS PERMANENT.** In an Activity, a view abandoned at alpha 0.4 by a cancelled animator is fixed by the next screen. Nothing recreates this window: it is attached for the life of the AccessibilityService, so a half-animated child stays half-animated until the service dies. Hence one method that cancels everything and asserts every property back to a named rest value without asking what was running, hence the rest values being the identity transform (a test pins that too, since `settle` asserts them blind), and hence the call sitting inside `setBubbleShown` rather than at its four callers — every hide path funnels through that method, so a fifth caller added later cannot forget it. The common case is not exotic: at the cadence floor a line fires every five scrolls, so a reveal is routinely still in flight when its own line's display window expires, and a reveal that outlived its line would animate the *count* into place using the line's entrance. `collapseNudge` settles BEFORE it re-renders, not after. **ONE METHOD MAY TOUCH THE ROOT, AND IT MUST NOT TOUCH ALPHA.** The bubble is hidden by setting the root to alpha 0 while keeping its surface alive (D30). The tap acknowledgement is the only animation pointed at the root, so it restores scale ONLY (`settleScale`) — an end action that "restored" alpha to 1 would flash the whole overlay back over somebody's video every time a stale tap resolved. That is a two-line method whose entire justification is a five-year-old invariant, which is why both ends carry the note. **THE REVEAL STYLE IS CHOSEN, NOT RANDOM, AND THE TIER IS HALF THE INPUT.** Four styles (fade, rise, pop, sweep); the TIER picks the palette and the LINE picks within it. The tier half means the motion carries information — a line that pops in has told you something about your count before you have read a word of it — and it escalates the way the content already does: tier 1 gets only the calmest style, because the app has just started speaking at all (it is silent below 50, D41) and its first act must not be a flourish. Each tier keeps the calmer options and gains a pushier one, *except* tier 4, which drops the plain fade deliberately: at the top of the curve a fade is indistinguishable from the count simply changing, which is precisely what the line most needs not to look like. The seed half means consecutive lines at one tier do not all enter identically, which is the same absorption argument `ChallengeEscalation` makes about a static challenge, one surface over. FNV-1a over the line text rather than `Random`, so it is a pure function a test can pin and a given line always has its own entrance; the hash is `ushr`-ed before the modulo because FNV overflows into the sign bit constantly and a negative index is the classic hash-selection crash — asserted across five thousand seeds including non-ASCII, because this runs inside a `Flow.onEach` where a throw cancels the collection and kills the count (the failure mode D72's work already catalogued). **THE MASCOT IS EXCHANGED AT THE TROUGH OF ITS OWN DIP.** One `ImageView` cannot cross-fade with itself, and stacking a second one to do it properly would add a view to a window that draws over other apps — for a transition that fires at most TWICE A DAY (`BrainState` flips at 50 and 150). So the art shrinks and fades, the drawable is swapped at the point where nobody can see which one is on screen, and it comes back. Indistinguishable from a cross-fade, no extra view. The dip stops short of zero: inside somebody else's app there is no page transition to explain a vanishing element, so a mascot that disappears reads as the overlay breaking rather than as the character reacting. The FIRST art is set with no animation at all — `lastArt == 0` means the bubble is being populated, not reacting, and animating that would make the pill visibly assemble itself several times an hour. **TWO PIECES OF DRIFT FELL OUT OF LOOKING AT THE ART, AND NEITHER WAS ON ANY LIST.** (1) The launcher icon was still the scaffold placeholder — a chevron in `#7C4DFF`, a purple that appears nowhere else in this app, whose own comment said "replace with real branding later". Replaced with a mark that says what the app does in one shape — a down-chevron (the scroll) meeting a solid coral bar (the block) — plus a `<monochrome>` layer, which is a separate drawable and not a reuse of the foreground for a reason worth knowing: the foreground distinguishes its two shapes by COLOUR, and a themed launcher throws colour away, so the monochrome version re-states the same idea with geometry. D82 kept it on the grounds that it "still means the breakdown by app"; it does not, because Insights is about a range of DAYS, and the tab carrying the 7-day and weekly charts was pointing at a picture of a phone. **D87. The premium pass — spring physics indoors, bounded time on the overlay, and the tint that was snapping (2026-08-04).**

Asked for a UI that feels more premium, and for the mascot transition to carry real animation. Research first, and the research had one clear answer: the current Android direction (Material 3 Expressive) **replaces duration-based easing with spring physics**, and that is most of what separates a UI that feels premium from one that is merely correct. A tween arrives at a fixed time no matter how far it travelled, so every transition has the same rhythm regardless of what happened; a spring's timing falls out of the distance and the physics, which is why it reads as an object moving rather than as a value being scheduled. The rest of the premium checklist — an 8pt spacing grid, legibility-first type hierarchy, micro-animation that guides rather than performs — this app already satisfies via `Brand.SPACE_DP`, D58's full type scale and D86's budget rule. Motion was the gap. **SO THE APP NOW HAS TWO MOTION SYSTEMS, DELIBERATELY, AND THE SPLIT IS THE DECISION.** In-app surfaces move on springs (`DampingRatioLowBouncy`, `StiffnessMediumLow`). The overlay bubble does not, and cannot: a spring has **no bounded duration by construction**, and `BubbleMotionTest` asserts the bubble's motion budget against `GuiltCadence.DISPLAY_MS` — an unbounded settle cannot satisfy a budget, and the reading time D83 bought is not negotiable. The dashboard is our own Activity window: it draws over nothing, competes with no sentence, and D30/D35's no-churn rules genuinely do not reach it. Two systems for a written reason beats one system applied where it does not fit, and beats two systems that arrived by drift. Within the spring transition, **opacity stays on a tween on purpose**: a bouncing alpha overshoots past 1.0, clamps, and what survives looks like a dropped frame rather than like spring. **THE HOLE D86 LEFT, AND WHY IT IS THE INTERESTING PART.** D86 animated the mascot through a dip and left the pill's accent as a bare `setTint`. So on the two moments that matter — mint→orange at 50, orange→red at 150 — the colour flipped on ONE FRAME while the character was still mid-dip. The eye catches the instant colour change, concludes the state has already flipped, and then watches the mascot turn up a third of a second late. **Animating one part of a composite and leaving the rest instant is worse than animating none of it**, because the mismatch reads as a glitch rather than as a missing feature — and it is a failure mode that only appears once you have started animating, which is exactly why D86 did not see it. The tint now crossfades via `ArgbEvaluator`, over `tintCrossfadeMs` **derived from `mascotSwapMs`** so no future tune can leave the colour behind. `ArgbEvaluator` rather than lerping channels by hand, because a hand-rolled version is the code that looks right and produces a muddy grey through the middle of every transition. **THE MASCOT NOW TURNS RATHER THAN BEING EXCHANGED.** A dip-and-return is a replacement: the old art leaves, the new arrives, the eye reads two events. Adding a small rotation through the trough makes it one object reacting. It rides the same draw-time matrix the scale already uses, so it costs nothing extra — no view, no pass, no layout. Eight degrees, and the number is load-bearing: past roughly ten, a tilt on a 40dp pill inside somebody else's video stops reading as a reaction and starts reading as the overlay being broken or askew, which is the impression this surface can least afford. It unwinds to level, `REST_ROTATION` joins the identity transform `settle()` asserts blind, and a test pins the ceiling. **ONE NEW LEAK PATH, CLOSED EXPLICITLY.** The tint crossfade is a `ValueAnimator`, not a view-property animation — so `settle()` cannot see it. That is the same class of leak D86 built `settle` to prevent, arriving through the one door it does not cover, and on a window nothing recreates it would mean a pill left at a colour belonging to no `BrainState` at all. `BubbleView` therefore holds the animator, cancels it in `settleMotion`, and SNAPS to the target rather than leaving it wherever it stopped. First draw is still instant for both halves — a bubble being populated is not a bubble reacting. No new palette (D58 holds), no new window, no change to the budget, and nothing here runs on the block screen, so invariant 6 is untouched.

Sources consulted for the premium/motion direction: Material Design 3 motion guidance and the M3 Expressive motion-physics write-up; general 2026 mobile UI practice on spacing, typography and micro-motion.


**D88. One budget, one reprieve — the per-platform grace was a bug, and it was reported by the person using it (2026-08-04).**

Reported as: *"I did exercise in Instagram but in YT shorts it is again blocking."* Exactly right, and the cause is a piece of drift with a clear date on it. **D76 made the daily limit GLOBAL** — one budget for the whole doomscrolling day, summed across every platform cleared to block, because a per-app limit meant the same person could spend three separate hundreds. What D76 did not move was the REPRIEVE. `SettingsPrefs.graceUntilMs` stayed keyed by platform, which had been correct while each platform carried its own limit and quietly stopped being correct the moment the budget was shared. So the shipped behaviour was: hit the global limit inside Instagram → block → walk twenty steps → Instagram's grace key is set → open YouTube Shorts → the global count is still over the global limit and YouTube's own grace key is zero → blocked, immediately, having just done the exercise. **The user paid the price once and was charged once per app.** THREE SEPARATE DECISIONS SAY THIS IS WRONG, which is the part worth keeping. D76: there is ONE budget. D77 (strict mode): a completed challenge is the ONLY way past a block, so being charged twice for one block is being charged for something that does not exist. D83: escalation is deliberately charged across the WHOLE challenge set — own uses plus half of every other challenge's — specifically so the price cannot be dodged by switching challenge. The system had already decided, in three places, that the price of buying time is global; the reprieve was the one piece still denominated per-app. A reprieve is what the challenge BUYS, and it has to be in the same currency as the thing it is spent against. THE FIX IS A DELETED PARAMETER, and that shape is deliberate. `graceUntilMs(context)` no longer takes a `Platform` at all, and `setGraceUntilMs(context, atMs)` no longer takes one either. The old bug is not merely untested now — it is **unwriteable**, because there is no per-platform key to write to. That is worth more than a test, and is the same instinct as D70's `canBlock` losing the field it must not gate on rather than gaining a comment saying not to. Legacy per-platform keys are READ as a fallback (the max across platforms, since where it was earned is precisely what no longer matters) so a reprieve bought minutes before this update is honoured rather than silently revoked, and they are cleared by Clear-all-data so the fallback cannot resurrect a stale deadline. They are not deleted from the file, for D76's own reason: a migration that destroys its own input cannot be re-run or audited. A SECOND, SMALLER BUG FELL OUT OF THE SAME FUNCTION. `onChallengeComplete` had `val platform = currentPlatform ?: return` sitting ABOVE the line that wrote the reprieve — so if the current surface had been lost between finishing the challenge and handling the completion, the user did twenty steps and got nothing at all. The user finished the exercise; the fifteen minutes are owed whether or not we still know which screen they are on. WHAT DID NOT CHANGE, and a test pins it beside the new ones: **gating stays per-platform**. `blocksAtLimit` answers "may we cover THIS screen" rather than "has the day's budget run out", so a SHADOW app still shows the bubble at any count and with any grace — going global on the budget must not make the block leaky. **D89. Sync is near-live, the leaderboard cache drops to two seconds, and invariant 3 is amended (2026-08-04).**

The design said counts flush "every 60s, or on Wi-Fi/app-background", and the working brief defended it as offline-first. The owner pushed back with an argument that is simply correct: **you cannot doomscroll offline.** Instagram and YouTube Shorts need a connection to serve the next reel, so the device is online at exactly the moments it has something to report. Offline-first remains right about where TRUTH lives — Room is still the source of truth and the app must work with zero backend, forever — but it was being used to justify a batching delay it does not actually justify. The requirement is ~2s, and it is a product requirement rather than a preference: the Phase 4 feature is scroll BATTLES, and a battle whose scoreboard is a minute stale is not a battle, it is a nightly digest. **PUSH: a 2s debounce while a reel surface is active.** The first unsent delta schedules a flush 2s out and everything arriving inside that window coalesces into it. At the app's own measured ~6s per reel that is roughly one request per reel; a fast scroller gets several folded into one, which is the debounce doing its job in the direction that matters. **Idle costs nothing** — no delta means no timer and no request, so a phone in a pocket is silent, which is the property a fixed 60s poll never had. Immediate flush on app-background and on connectivity regained are kept from the original design. Nothing about invariant 1 changes: deltas only, never absolute counts, each with a client UUID `batch_id` the server dedupes, and the queue clears only on ack. **READ: poll `GET /friends/today` every 2s, and ONLY while a friends screen is visible** — stopped on background, on screen-off, and on navigating away. **A WebSocket was considered and rejected**, which is the part worth recording because it is the obvious "real-time" answer. Three reasons: the number changes every six seconds, so a persistent connection is being held open to deliver an update per six seconds; a long-lived connection is the first casualty of Render's free-tier spin-down, so the socket path needs reconnect-and-backoff logic that a poll simply does not have; and a poll gated on screen visibility is provably zero-cost when nobody is looking, whereas a socket has to be explicitly torn down to reach the same place. Revisit if sub-second is ever needed, which it is not — a reel takes six seconds to watch, so sub-second precision is measuring noise. **⚑ THIS AMENDS INVARIANT 3, AND THAT IS THE HEADLINE.** `CLAUDE.md` said *"Leaderboard reads cached 30s."* A 30s cache means a friend's number can be 30s stale on top of a 2s push, so the worst case was over half a minute — which would have made the 2s push pointless while looking like it worked. The cache is now **2s while a friends screen is open, 30s otherwise**, and the server-side cache is what keeps N friends watching each other costing ONE Redis read per 2s rather than N. The half of the old invariant that was actually protecting something is unchanged and restated: **the client never talks to Redis, and nothing polls when nobody is looking.** **THE COST, computed rather than assumed**, using the app's own figures (6s/reel, a 320-reel heavy day): ~320 writes/user/day, ~9.6k/month. Upstash's free 500k commands/month therefore holds to roughly **50 users**, and that — not battery, and not Neon — is the binding constraint on the ₹0 rule. Neon's free compute-hours (~191/month, i.e. 6.4h/day of awake compute) are comfortable at this scale. Render's free spin-down turns out to be *helped* by this design: 2s pushes from any active user keep the instance warm, so the 50s cold start only ever hits the first user of the morning. When the free tier is outgrown the first move is a longer debounce for non-battle users, not a paid plan — and none of it may be taken without an explicit decision here (the ₹0 rule). **ONE DEPLOYMENT BUG FIXED WHILE PREPARING FOR THIS.** The Dockerfile runs on `python:3.13-slim-bookworm`, and *-slim strips the IANA timezone database. D87's `assert_tzdata_available()` refuses to boot without it — deliberately, because the alternative is a container that starts, passes its health probe, and silently misdates every count. So without a fix the first real deploy would have failed outright. `tzdata` is now installed in the RUNTIME stage (not the builder — the venv is what gets copied forward, and `/usr/share/zoneinfo` is not in it), folded into the existing user-creation layer with the apt lists removed in the same `RUN` so no package index survives into the shipped image.

**D83. Milestones are DERIVED from history on every read, never awarded and stored. Warmth lives here; the block keeps the guilt (2026-07-29).**

Pass C1. No new storage, no change to detection, counting, the overlay or the block.

**NOTHING IS EVER PERSISTED, and that is the whole design rather than an optimisation.** D81 established that a streak is entirely a claim about *which day a count belongs to*, and D14's device-local boundary is INTERIM — invariant 2 replaces it with server timezone truth in Phase 3. A count recorded at 00:30 local may migrate to the previous day, joining two runs or splitting one. So a badge awarded and stored today can become **arithmetically false later**, and the app would be contradicting its own history on the one screen whose entire job is to be believed. Deriving costs nothing (the data is already loaded for the trend) and guarantees a milestone is always a true statement about the counts as they currently stand.

Two consequences, both accepted rather than worked around. **Clearing data clears the milestones** — correct, because they are a VIEW of the history and the user asked for the history to be gone. And **raising the limit can retroactively earn one** — also correct: the milestone means "you stayed under YOUR limit", so if the limit moves, past days genuinely change category. A stored badge could not express either; this is the upside of deriving, and both are pinned by tests.

**THE WALK STARTS AT THE FIRST DAY WITH DATA, which is the one place this could have been actively dishonest.** Days with no row count as under — same rule as `StreakCalculator`, because a lazily-created row means zero scrolls and a day the user did not doomscroll is the outcome the product exists to produce. But if the walk began at an epoch instead, every absent day before installation would count, and a fresh install would instantly hold a streak of centuries. So the window opens at `min(dates)` and a fresh install earns exactly nothing.

**ALL-TIME, unlike the Insights trend.** `StreakCalculator` is deliberately bounded by its caller's window so a 7-day chart cannot report a 30-day best (D81). A milestone asks the opposite question — "have you EVER" — so it reads `observeAllDailyTotals()`, which reuses the existing range query with an open lower bound rather than adding SQL: the ISO-8601 key sorts lexicographically as it sorts chronologically (the reason D14 chose it), so `BETWEEN '0000-01-01' AND today` is every row up to today and nothing after. Today's pending merge (D82) therefore applies to it for free.

**A day AT the limit is not under**, matching `BlockPolicy` exactly — the block fires at `count >= limit`, so awarding a milestone for the day you were blocked would contradict what the user actually experienced.

**THE TONE IS THE FEATURE.** The block screen keeps the guilt (D33/D49); this is its counterweight, and D9 anticipated the need while D78's research confirmed it — an app that only ever scolds gets uninstalled out of shame, which fixes nothing. So a LOCKED milestone shows PROGRESS toward itself, never a reproach: "4 of 7", not "you failed to reach 7". Earned rows take the healthy mint; locked ones stay in D78's quiet tier, so the card reads as a set of things to walk toward rather than a wall of failures. Names are achievements, not instructions — "A quiet week", not "Stay under for 7 days".

**NO CHALLENGE MILESTONES.** "Walked it off five times" is the obvious one to want and it cannot be built: challenge completions are not persisted anywhere. Adding a counter for it is a storage decision, and this pass adds none. Everything shipped is provable from `daily_counts`, kept forever since D4.

**D62. The data layer: two database URLs that are not interchangeable, an ENUM that stores wire values, and a SCHEMA.md the build parses (2026-08-10).**

WHY THIS ADR EXISTS NOW AND NOT IN JULY. D60 reserved D61–D64 and refused to write them, on the grounds that all four are claims about how real infrastructure behaves — pgbouncer's transaction mode, prepared statements, Neon's autosuspend — and a confidently-worded guess in an append-only log is harder to dislodge than an open question. That condition is met here: every pooling claim below was read out of the installed `sqlalchemy/dialects/postgresql/asyncpg.py` rather than recalled, and the one that mattered most is the one memory had wrong. So D62 is written; D61, D63 and D64 stay reserved.

THE BLOCKER FROM 2026-08-04 WAS GONE, AND THAT IS THE ONLY REASON THIS SESSION HAPPENED. 3b was left half-finished because `pip-compile --generate-hashes` could not reach PyPI, and adding `sqlalchemy`/`asyncpg`/`alembic` to `requirements.in` without regenerating the lockfile would have left the two files disagreeing — hash-pinning that is one edit out of date is worse than none, because it still looks enforced. The network was reachable this time; both lockfiles are regenerated and CI installs them with `--require-hashes` unchanged.

**FOUR SETTINGS MAKE THE POOLED CONNECTION SURVIVE PGBOUNCER, AND ONE OF THEM READS LIKE A MISTAKE.** asyncpg prepares every statement it runs and caches the result per connection, naming them in numeric order. Behind a transaction pooler neither half of that holds: the connection you cached against is not the one you get back (`InvalidCachedStatementError`, under load, never in testing), and the numeric names collide across clients sharing a backend (`DuplicatePreparedStatementError`, on a statement that is perfectly valid). So: `statement_cache_size=0` for asyncpg's own cache, `prepared_statement_cache_size=0` for SQLAlchemy's dialect-level one — **two independent caches, two switches, and turning off one while assuming the other followed is the trap** — and `prepared_statement_name_func` returning a uuid so names cannot collide. The fourth is `poolclass=NullPool`, which looks like a pessimisation and is not. SQLAlchemy's own asyncpg documentation escalates it to a *warning*: a pooled connection behind pgbouncer accumulates prepared statements nothing will ever discard. **PGBOUNCER IS THE POOL, and it is a process closer to the database than we are** — pooling twice is the bug. It also answers Neon's autosuspend for free, since there is no idle connection left to go stale and therefore nothing for `pool_pre_ping` to notice. All four are asserted in `tests/test_db.py`, because none of them is visible in review: every one is an ordinary-looking keyword argument whose absence fails intermittently, in production, months later.

**THE TWO URLS, AND WHY THERE IS NO FALLBACK.** `DATABASE_URL` is the pooled endpoint and `app/db.py` reads only it. `DATABASE_URL_DIRECT` is the direct endpoint and `migrations/env.py` reads only it, **raising if it is unset rather than falling back**. The reason is specific and not "DDL is scary": Alembic takes a CONNECTION-SCOPED advisory lock so two deploys cannot migrate simultaneously, and under transaction pooling "the connection" is whatever backend the pooler hands out per transaction — so the lock can be taken on one backend and released against another, and the mutual exclusion it exists to provide is quietly absent. A fallback would make the wrong endpoint the *convenient* one, and it would work on a small schema, in testing, most of the time, and fail during a concurrent deploy against a large table, which is the least recoverable moment available. `Settings.database_url_direct` is declared so both names are documented together and then deliberately imported nowhere; a test parses `env.py`'s AST and fails if the pooled name appears in a string literal or if it imports `app.config`. Parsed rather than grepped, because that module argues at length about why it does not fall back, and a text search finds the prose arguing against the thing it is looking for.

**`values_callable` IS THE MOST CONSEQUENTIAL LINE IN THE MODELS.** SQLAlchemy's `Enum` persists member NAMES by default. Without it the database holds `INSTAGRAM` while the client, `app/platforms.py` and `test_platform_parity.py` all speak `instagram` — and **nothing raises**, because `Platform.INSTAGRAM` round-trips through its own name perfectly well. It surfaces much later as a hand-written query or a Phase 4 leaderboard read that filters on the documented value and returns nothing. That is the same invisible-partial failure shape `app/platforms.py` was written to prevent, arrived at from the other side, so it gets the same treatment: a test, not a comment. The type is constructed ONCE in `app/models/columns.py` and shared, because a `sa.Enum` with a name is a database type rather than a column decoration — two instances with one name are two Python objects claiming one `pg_type` row, and the duplicate only announces itself during `CREATE TYPE`. Related and easy to miss: `devices.platform` is an OS, not an app. `SCHEMA.md` calls both columns `platform`, so `DevicePlatform` is a separate type named `device_platform`, and a test asserts the two value sets are disjoint — otherwise `android` becomes a legal `daily_counts.platform`.

**docs/SCHEMA.md IS NOW EXECUTABLE, AND THE COMPARISON IS TWO-DIRECTIONAL ON PURPOSE.** `test_schema_parity.py` parses the six table declarations out of the markdown and compares them against `Base.metadata` — tables and columns, both ways. The tempting weaker version is "the doc must be a subset of the models", and it removes all of the value: an under-specified doc passes forever, which is exactly the state being prevented. The failure mode this catches is undramatic and therefore likely: somebody adds a column, the models follow, the doc does not, nothing breaks, and six weeks later a question about what the server stores is answered from a file that no longer knows. Same instinct as the Kotlin-parsing parity test and the health-import walk (D60), stated once more: **where a rule spans two things that can drift, the test has to look at both.** The one change this forced was honest — `sessions` gained `created_at` in the doc as well as in the model.

**THE MIGRATION DOES NOT IMPORT THE MODELS, AND A TEST CLOSES THAT LOOP.** A migration is a historical fact; the models are a present-tense description. Importing one into the other means a column added next year silently rewrites what revision 0001 claims to have done, and a migration whose meaning changes retroactively cannot be replayed onto a fresh database with any confidence. The enum values are therefore spelled out in the revision, and that duplication is the point. What stops the two drifting is `test_migrations.py`, which renders the whole chain with `alembic upgrade head --sql` — **offline, no database, which is also the exact artifact a reviewer should read before a migration touches anything** — and checks every mapped table, every mapped column, every constraint name and the enum's value set against the metadata. The platform-values assertion is written against the WHOLE rendered chain rather than against revision 0001, so a later `ALTER TYPE platform ADD VALUE` keeps it green; a test pinned to the initial revision would have to be edited instead, and a test that teaches people to edit tests is worse than no test.

⚑ **TWO TRAPS FOUND BY RUNNING IT, BOTH SILENT.** (1) **Alembic re-applies the naming convention to names you give it.** `name="ck_daily_counts_count_non_negative"` went through the `ck_` rule a second time and came out as `ck_daily_counts_ck_daily_counts_count_non_negative`. Not an error — a database whose constraint names no later migration can predict, which is precisely what the convention exists to prevent. `op.f()` marks a name as final and is now applied uniformly, including to the primary and foreign keys, which survived without it only by coincidence (their conventions do not interpolate `%(constraint_name)s`). (2) **The backend test suite could not run on this project's own dev machine.** `zoneinfo` reads the SYSTEM tz database; Linux has `/usr/share/zoneinfo` and **Windows has none at all**, so `assert_tzdata_available()` killed the suite in `conftest` before a single test ran. It had never been noticed because CI is Linux and nobody had run the backend gates locally — the gate was passing in the only place it had ever been executed. `tzdata` is now a DEV dependency; the runtime image keeps getting its copy from the Dockerfile's apt package, which the base image's security updates patch, rather than from a lockfile that moves only when someone remembers.

**/readyz DOES A REAL `SELECT 1` NOW, WITH A TIMEOUT AND A DELIBERATELY BROAD EXCEPT.** SQLAlchemy connects lazily, so a healthy-looking engine object proves nothing — the only way to answer "can this process serve a request end to end" is to make it serve one. Three distinct answers, because they have three different fixes: unconfigured (503, "database not configured", still an honest and supported state), unreachable (503), ready (200). The 5s `asyncio.wait_for` is not about speed: an unroutable host has no timeout of its own worth relying on, and a probe that hangs is indistinguishable from one that fails except that it also occupies a worker. The `except Exception` is intentional — every failure mode here has one correct answer, and letting an exception escape returns 500, which reads as "the application is broken" rather than "the database is not there yet", a difference that matters on a platform which restarts unhealthy services. The traceback is logged and deliberately kept out of the response, because the reason a database is unreachable usually contains its host and this endpoint is unauthenticated (D60). Startup connects to nothing at all: doing so would turn a few seconds of Neon cold start into a crash loop, and being not-ready is a state `/readyz` can report and recover from.

**`devices` AND `friendships` ARE CREATED UNUSED**, which is D66's line held exactly where it was drawn: schema may lead its consumer, services may not. A table costs one `CREATE TABLE` in a migration being written anyway; a Redis client with no friend groups to serve is infrastructure with nothing to do and a metered free tier to spend.

WHAT 3b DID NOT DO. No live-Postgres job in CI, because nothing here needs one — the schema is checked by rendering DDL. That stops being true at 3d, where `INSERT ... ON CONFLICT` under concurrency is the thing being tested and no rendering of it proves anything. No `family_id` on `sessions` either: D63 will need one for refresh-token reuse detection, and it belongs to the sub-phase that designs it. Migrations exist so schema can change; pre-building a column for a design that is not written yet is guessing with extra steps.

STATE AT THE END: **167 backend tests, all four gates green (`ruff check`, `ruff format --check`, `mypy app`, `pytest`), 100% coverage floor held.** Nothing under `app/src/` was touched — 3a–3d do not touch the Android tree, which is what keeps the shipped offline app unable to regress while the backend is built.
